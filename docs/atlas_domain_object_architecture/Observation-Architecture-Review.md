## 7. Proposed Ontology Under Review

*"An Observation is a permanent, independently identified Domain Object whose entire semantic content is that specified observational content has been admitted into a Case. The Observation itself makes no assertion that the content is true, false, verified, reliable, complete, or accepted as knowledge."*

**This formulation is not verbatim OE-002 §5.1** and is treated in this review as a candidate to be tested, not as governing text. OE-002 §5.1, quoted in full since this entire review turns on its exact wording:

> **Definition.** Observation is a permanent Domain Object that preserves informational content without asserting that the content is true.
>
> **Identity.** Observation has stable identity independent of its content. Its identity does not depend on any indication of origin.
>
> **Responsibility.** Observation is responsible for preserving informational content as it stands, without commitment to its truth, verification, reliability, or authority.
>
> **Ownership boundary.** Observation is origin-neutral: its own definition neither requires nor prohibits any particular origin for its content. Where an indication of origin is present, it is optional, non-defining content, not part of what makes an Observation valid.
>
> **Relationships.** Observation requires no other Domain Object to exist validly. Observation is root-eligible: it MAY be the first Domain Object accepted into a Case. Observation MAY be referenced by other Domain Objects defined in this document; nothing in Observation's own definition requires this.

OE-003 §4.1 (`ObservationAccepted`), read for corroboration: *"Fact established: that specified informational content has been preserved by the Case, without asserting it is true, verified, reliable, or authoritative."* This is the closest OE-003 comes to the word "preserved by the Case" — it does not use "admitted," either.

## 8. Exact Semantic Proposition Analysis

**One accepted Observation records exactly this proposition, per OE-002 §5.1 and OE-003 §4.1 read together**: *specified informational content has been preserved by the Case, without any assertion that the content is true, verified, reliable, or authoritative.* This is a complete proposition, not a pointer toward an unspecified payload, *at the ontological level* — OE-002 deliberately leaves the *internal structure* of "informational content" unspecified, exactly as it deliberately leaves Judgment's "characterization" format unspecified (no "discrete status vocabulary" is assigned to either). This is the identical, already-established discipline: OE-002 forces the *presence* of content and the *absence* of a truth/reliability/authority claim about it; it does not force any particular internal shape for that content. A candidate ontology statement is complete if it states this proposition; it is incomplete if it merely gestures at "some payload exists" without stating the truth-independence half of the proposition, or if it substitutes a different verb (e.g., "admitted") that shifts the proposition's own subject from *the content's preservation* to *the object's own acceptance event* (a different, general fact governed by OE-006, not by OE-002 §5.1 at all).

**The proposed ontology under review fails this test as worded.** "Whose entire semantic content is that specified observational content has been admitted into a Case" makes the proposition *about admission* (an acceptance-layer, OE-006-governed fact, general to every Domain Object) rather than *about preservation without a truth claim* (OE-002 §5.1's own, Observation-specific fact). This is the load-bearing finding of this review (Section 10).

## 9. Observational Content Analysis

Testing each candidate structure for "observational content" against OE-002 §5.1's own silence on internal format: **text** — the currently-shipped realization (`Statement`, a non-empty stripped string) is a fully conformant, minimal, non-inventive realization, exactly paralleling `Characterization`'s own free-text treatment for Judgment. **A proposition, a claim, an expression** — these are informal descriptions of what free text *can* carry; none is separately, canonically required as a distinct structured form. **A structured value or typed payload** — not currently forced; would be a future, additive content-type extension, not required today (parallel to Judgment Design §11's own deferred "structured proposition language" question — permitted, not forced). **An external reference or a Domain Object reference** — OE-002 §5.1's Relationships clause states Observation "requires no other Domain Object to exist validly," meaning content need not, and by default does not, take the form of a reference to another Domain Object; a future, narrower content-type (e.g., "this Observation's content is an external artifact") is not excluded by OE-002 but is also not required, and is not resolved by this review (Section 13.7, Candidate G). **A set of assertions or an opaque artifact** — neither is canonically forced; both remain open, non-blocking future extensions.

**Atlas Core does not need to define observational content's internal structure now.** OE-002 §5.1's own silence on format, read the same way as Judgment's identical silence on characterization format, is a genuine, permanent, non-blocking underdetermination (Doctrine §7) — the minimum semantic contract (content exists, is preserved, carries no truth/reliability/authority assertion) is fully stated without resolving the format question.

**Does observational content have identity independent of the Observation, or is it part of the object?** Per OE-002 §5.1's own Identity clause ("Observation has stable identity independent of its content"), content is *part of* the Observation's own record, not a separately-identified object the Observation merely targets — unlike Knowledge Reference, whose entire structure is a pointer to a separately-identified, separately-accepted object. **Can two Observations carry semantically identical content while remaining distinct objects?** Yes — addressed fully in Section 25 (Cardinality) and Section 13.13-equivalent analysis below; identity is independent of content (§5.1's own Identity clause), the same already-established principle governing Knowledge Reference and Judgment. **May one Observation contain more than one independent claim?** OE-002's own singular framing ("informational content," never "contents" or "a set of...") — the identical interpretive method the Judgment Implementation Design used to conclude Judgment's own subject is "exactly one... never more than one" — supports one Observation representing one preserved content-item, atomically, not an unbounded compound document (developed fully in Section 25).

## 10. Admission Analysis

**"Admitted into a Case" is genealogical/general, not a distinct semantic contribution of Observation's own.** Testing against the required distinctions: it is not a *semantic* assertion about the content itself (that role is already, fully stated by OE-002 §5.1's "preserves... without asserting truth"); it *is* an ordinary instance of *acceptance* (OE-006 §3: "the actual admission of the candidate Domain Object... together with the occurrence of its corresponding Domain Event"), a fact general to every one of the six adopted types, not distinctively Observation's own; it describes *lifecycle* only in the trivial, general sense every accepted object has a lifecycle moment (INV-008's atomicity), not an Observation-specific lifecycle; it does not describe *genealogy* in the narrower sense of provenance/origin (that is `source`'s own, separately-addressed role, Section 12); it *duplicates* Case ownership (INV-002) and the general acceptance model (OE-006) rather than adding to either; it does not introduce any undefined process beyond what OE-006 already, generally defines.

**Per this task's own instruction ("If admission is genealogical rather than semantic, remove it from the ontology"): admission is removed from Observation's own ontology statement.** The corrected statement (Section 32, Correction 1) tracks OE-002 §5.1's own text directly: preservation of content, without a truth/verification/reliability/authority claim — never "admission" as the object's own defining operation. This finding is also the precise reason Candidate H (Section 21) is rejected: treating admission/entry-into-a-Case as Observation's *own* semantic content is one step away from treating Observation itself as a capture *event*, which is OE-003's domain, not OE-002's, and which Doctrine §9 forbids one document from redefining on another's behalf.

## 11. Truth-Status Analysis

Six propositions must be kept distinct, tested individually: (1) **the existence of an Observation** — not itself truth-apt; it is a permanent record that certain content was preserved, and that record's own existence is neither true nor false, only accepted or not-yet-accepted. (2) **The content represented by an Observation** — plausibly truth-apt in the ordinary sense (a factual claim like "revenue was 100" could, informally, be true or false), exactly parallel to Judgment's characterization content (Section 12 of the Judgment Pre-Commit Architecture Review) — but OE-002 §5.1 is explicit that *accepting* the Observation never asserts this content's truth. (3) **A source report** (if a source is indicated) — the report itself may be truthful or not about what the source actually said, but this is outside Observation's own contract entirely: OE-002 §5.1 states origin is "optional, non-defining content, not part of what makes an Observation valid," so Observation makes no claim about a source report's own accuracy. (4) **An assertion within the content** — if the preserved content itself contains an assertoric claim, that claim's truth is a fact about the *content*, addressed by point (2), never elevated to a fact about the Observation object. (5) **Atlas accepting the Observation as a valid object** — this is OE-006's general Valid/acceptance determination (structural completeness: content present, Case assigned), never a determination about the content's truth. (6) **Atlas accepting the content as knowledge** — this is explicitly, categorically *not* what Observation does; that operation belongs to Knowledge Reference (Section 14) and, in a different sense, to Judgment's characterization (Section 15); OE-002 §5.1's own Responsibility clause forecloses this for Observation directly ("without commitment to its truth, verification, reliability, or authority").

**Exactly which proposition is truth-apt, and which is not**: the object's own existence and Atlas's acceptance of it (points 1, 5) are not truth-apt — they are facts about record-keeping, not claims. The content itself, and any assertion embedded in it (points 2, 4), are plausibly truth-apt in the ordinary sense, but their truth is never asserted, endorsed, or evaluated by the act of accepting the Observation. Source-report accuracy (point 3) is outside Observation's contract by explicit textual exclusion. Knowledge-acceptance (point 6) is a different Domain Object's own function entirely, never Observation's.

## 12. Source and Genealogy Analysis

Testing whether the represented proposition is *incomplete* without identifying who or what supplied the content — comparing directly "Revenue was 100" against "Source S reported that revenue was 100": **OE-002 §5.1 settles this directly and explicitly, not merely by omission.** The Ownership-boundary clause states Observation "is origin-neutral: its own definition neither requires nor prohibits any particular origin for its content," and that where an indication of origin is present, "it is optional, non-defining content, not part of what makes an Observation valid." A proposition that is *complete only with* the source identified would make source *constitutive* — directly contradicted by this text. Therefore **an Observation represents "Revenue was 100," not "Source S reported that revenue was 100."** Source, where present, is *metadata about the content's origin*, never part of the proposition the Observation itself asserts (or, more precisely, never part of the content it preserves without asserting).

Evaluating each candidate origin-adjacent concept against the required ontology/genealogy/metadata distinction: **observer, agent** — excluded, for the identical reason Agent was excluded from Judgment and Knowledge Reference (actor identity excluded from Domain Object content generally, per the fourth prior investigation's own established conclusion, reused here as precedent); no canonical text requires or permits Observation to carry an actor field beyond the optional, non-defining `source` OE-002 itself licenses. **Source, sensor, document, system** — all fall under OE-002 §5.1's own explicitly-licensed, optional, non-defining "indication of origin" — permitted, never required, never constitutive. **Timestamp of occurrence** — this is `observed_at`'s own role (Section 24, field analysis); not textually forced by §5.1 the way Outcome's retrospective timing is explicitly forced by OE-002 §5.6, but not forbidden either — a genuine, non-blocking open point, classified precisely in Section 24. **Timestamp of receipt** — not canonically distinguished from `recorded_at` (INV-015: acceptance time is event time); a second, distinct "received_at" would be redundant unless a concrete asynchronous-ingestion need is demonstrated later. **Method of collection, provenance** — either redundant with the licensed `source` field or excluded under the same "authority/reliability" textual exclusion as below. **Confidence, reliability** — directly, textually forbidden: OE-002 §5.1's Responsibility clause names "verification, reliability, or authority" explicitly among what Observation does not commit to. **Measurement unit** — presupposes a structured numeric content type not currently adopted; premature, not forced.

**Conclusion: source is metadata/genealogy, licensed as optional and explicitly non-defining by OE-002 §5.1 itself — not removed by this review's own invented distinction, but by the governing text's own words.**

## 13. Alternative Ontology Analysis

**Candidate A — Recorded Fact.** Proposition: "An Observation is a recorded fact." Required fields (implied): content, recorded-at. Tested against OE-002 §5.1: "fact" imports an implicit truth claim ("fact" ordinarily denotes something true), directly contradicting the Responsibility clause's explicit truth-independence. **Rejected** — imports truth.

**Candidate B — Sensor-Derived Information.** Proposition: "An Observation is sensor-derived information." Tested: makes the ontology channel-dependent, directly contradicting the Ownership-boundary clause's explicit origin-neutrality ("neither requires nor prohibits any particular origin"). Excludes human-reported and imported content without textual basis. **Rejected** — contradicts origin-neutrality.

**Candidate C — Recorded Information.** Proposition: "An Observation is recorded information." Tested: "recorded" is genealogical (same defect as Candidate A's own framing, minus the truth-import, but still conflating the acceptance-layer fact with the object's own content), and "information" alone is too broad to distinguish Observation from Knowledge Reference's or Judgment's own content-adjacent material — it does not state the distinguishing operation (*preserves as-is*, versus *characterizes* or *relies on as knowledge*). **Rejected** — insufficiently distinguishing; fails the Historical Decision Record's own reducibility test (Section 5, Doctrine).

**Candidate D — Admitted Observational Content (the prompt's own candidate).** Tested exhaustively in Sections 8–10. **Rejected as worded**; the underlying, already-adopted type (OE-002 §5.1 itself) is not rejected — only this specific restatement is corrected (Section 32, Correction 1).

**Candidate E — Source Report.** Proposition: "An Observation records that a specified source presented a specified claim or payload." Tested: makes source *constitutive* (mandatory to complete the proposition), directly contradicted by OE-002 §5.1's own explicit "optional, non-defining" language (Section 12). Collapses toward a relation/report object distinct from what OE-002 actually defines. **Rejected** — direct textual contradiction.

**Candidate F — Case-Level Assertion Without Endorsement.** Proposition: "An Observation is a Case-owned assertion whose content is represented without endorsement." Tested: "assertion" ordinarily connotes a truth claim being put forward (even an unendorsed one still purports to say something is so) — OE-002 §5.1 deliberately uses "preserves," not "asserts," precisely to avoid this connotation; risks conflating Observation with Judgment's own characterization function (which *does* assert a settled position, without endorsing its truth) or with a weak/implicit Knowledge Reference. Closer than most rejected candidates, but reintroduces exactly the ambiguity OE-002's own word choice avoids. **Rejected** — needless risk of conflation with Judgment.

**Candidate G — External Artifact Reference.** Proposition: "An Observation is a reference to an external artifact made available to a Case." Tested: too narrow — OE-002 §5.1's "preserves... content" language does not require content to be an external pointer, and direct, first-hand textual observations (no external file at all) must remain representable; forcing all content into a reference shape is unforced and would exclude the ordinary case. A legitimate *future, narrower content-type option* for imported files, not the whole ontology. **Rejected as the general ontology**; noted as a viable future content-type extension (Section 9), not resolved further here.

**Candidate H — Capture Event.** Proposition: "An Observation is the historical event in which content entered a Case." Tested: conflates OE-002's object-level domain (permanent Domain Objects) with OE-003's event-level domain (`ObservationAccepted`) — the identical distinction INV-008 keeps ("acceptance and event occurrence are the same architectural moment," not that the object *is* the event); also risks violating the permanence framing by treating the object as a momentary occurrence rather than a permanent record. **Rejected** — Doctrine §9 forbids one document's fact (OE-003's event) from being smuggled into another's (OE-002's object).

**Candidate I — No Distinct Observation Object.** Tested against Case, Judgment, Knowledge Reference, Reasoning Trace, external artifacts, and API input records, per this task's own required explicit rejection: Knowledge Reference asserts *reliance* on an *already-accepted* target (requires prior acceptance, never root-eligible, is a bare pointer with no content of its own) — Observation requires no target, is unconditionally root-eligible (Section 5.1's own text), and *carries* content directly, not a pointer to it; collapsing the two would either force every Observation to reference some other, already-accepted object (contradicting Observation's own root-eligibility and no-Domain-Object-required text) or force Knowledge Reference to carry raw content (contradicting its own bare-reference definition, OE-002 §5.2). Judgment *characterizes* a subject (records a settled assessment/position) — a Judgment consisting only of "preserved content" with no genuine characterization would, by the same non-collapse argument already established twice in this series, collapse into Knowledge Reference (Judgment Design §11) or simply *be* an Observation misclassified — the Historical Decision Record's own "Decision History: OE-002" section names "preservation of content (Observation)" and "characterization (Judgment)" as two of the six independently-demonstrated, non-derivable semantic operations underlying the adopted six-type set; treating them as one would directly contradict this already-settled, Final finding. An external artifact, an API input record, or "no Atlas object at all" would each fail to provide independent identity, permanence, Case ownership, or eligibility to be referenced by other Domain Objects — all of which OE-002 §5.1 explicitly grants Observation and which downstream objects (Knowledge Reference, Judgment, Reasoning Trace, Decision, Outcome) already rely on being available (each names "any of the six adopted types" as an eligible target, Observation included). **Candidate I is explicitly, decisively rejected.** This rejection is itself governed by OE-002 §4/§5.1's own Final adoption and the Historical Decision Record's own settled distinctness finding — this review does not reopen that adoption from scratch (no Doctrine §8 forcing function exists to do so), it independently re-derives why the adoption is correct, as required.

**No superior alternative ontology was found.** The corrected Candidate D (Section 32, Correction 1) — tracking OE-002 §5.1's own text directly — is the smallest, most textually faithful, internally consistent formulation; every tested alternative either imports an excluded concept (truth, channel-dependence, source-constitutivity, event/object conflation) or fails to distinguish Observation from an already-adopted, differently-operating type.

## 14. Comparison with Knowledge Reference

Knowledge Reference (OE-002 §5.2) *identifies another already-accepted Domain Object* and records reliance on it *as knowledge*, with no content of its own — it is a bare, same-Case, prior-accepted pointer (INV-004/005/014), never root-eligible (its own reference is mandatory). Observation *carries* its own content directly, requires no target, and is unconditionally root-eligible. Observation does not target another object; does not record reliance; introduces its own, internally-carried content rather than *external* semantic content borrowed from elsewhere; makes no epistemic relation to anything; is not itself "knowledge" in Knowledge Reference's own sense (it makes no reliance claim); *can* later become the target of a Knowledge Reference (an ordinary, generic instance of Knowledge Reference's own "no specific Domain Object type is required" rule — not a special Observation-Knowledge-Reference relationship); and otherwise exists entirely independently of whether any Knowledge Reference ever targets it. **The two objects do not duplicate one another** — different responsibility (preserve vs. rely-on-reference), different content-bearing structure (content-carrying vs. bare pointer), different root eligibility (unconditional vs. never).

## 15. Comparison with Judgment

Judgment (OE-002 §5.4) *characterizes* an identified subject — its own characterization content is canonically *forced*, precisely because a Judgment without it would collapse into Knowledge Reference (Judgment Design §11). Testing whether a Judgment could express every valid Observation: only by *adding* a characterization Observation itself does not make and does not require — meaning the reduction would either strip Judgment's own forced-characterization requirement (contradicting OE-002 §5.4) or force every Observation to carry an assessment it does not, by its own definition, make. Testing whether "observed," "reported," "detected," or "measured" inherently express a Judgment: **no** — these words describe the *act of noticing or recording* something, not an assessment of what the content *means*, whether it is *reliable*, or what *position* the Case holds regarding it. "Revenue was reported as 100" preserves that this content was noticed; it does not, by itself, assert "this figure is trustworthy" or "this confirms the thesis" — statements that *would* be Judgment's own territory if a Case chose to make them, as a *separate*, later, referential-form Judgment characterizing the Observation as its subject (an ordinary, permitted, generic instance of Judgment's own "no specific Domain Object type is required" rule, not a special Observation-Judgment relationship). **Observation is not merely a weak or implicit Judgment** — it lacks the one component (forced characterization content) that makes Judgment what it is, and possesses one component (unconditional, form-independent root eligibility) Judgment's referential form categorically lacks.

## 16. Comparison with Reasoning Trace

Reasoning Trace (OE-002 §5.3, as finalized in its own Implementation Design, read for corroboration only) *represents already-accepted Domain Objects as providing epistemic support* — it requires at least one supporting object (INV-013), is never root-eligible, and records a *support relationship*, not content of its own. Observation does not *supply* support in Reasoning Trace's own, technical sense (that is a fact about how a *Trace* characterizes its own supporting set, not about Observation's own definition); does not *record* support (it has no support-relation field of any kind); it merely *contains material that could later be cited* as a supporting object by some future Reasoning Trace — exactly the same "ordinary, generic possibility" already established for Judgment-as-a-possible-Trace-support in the Judgment Pre-Commit Architecture Review, reused here by direct structural analogy, not assumed beyond what OE-002 §5.3 and the Reasoning Trace Implementation Design actually establish (this review does not assume any fact about Reasoning Trace's own supported-claim question beyond what is already, independently settled).

## 17. Comparison with Decision and Outcome

Decision (OE-002 §5.5) records a *settled practical commitment regarding what is to be done*; Outcome (OE-002 §5.6) records a *determinate state of affairs treated as realized*. Testing whether Observation could accidentally absorb either: nothing in OE-002 §5.1 requires or forbids a Case from placing decision-like ("we bought X") or outcome-like ("the position lost 10%") free text inside an Observation's own content field — this is a genuine, worth-recording **non-blocking authoring-discipline risk**, not an ontological defect: the identical situation already exists, and was already correctly *not* treated as a defect, for Judgment's own free-text `characterization` field (which could equally be misused to encode support-relation, decision, or outcome-like content). OE-002 does not require, and per Doctrine §2/§3 architecture must not invent, content-level semantic policing of free text beyond the structural contract each type's own definition states. **Observation does not absorb Decision's or Outcome's own ontology** — it has no commitment-to-action semantics and no realized-state-of-affairs semantics built into its own definition; a Case that misuses free text to encode either is an authoring-discipline matter outside this architecture's own scope, not a field-level gap to close. Decision and Outcome are not yet fully corrected in this repository (DO-IMP-006/007, per the Reconciliation Plan); this review records that dependency precisely and does not invent their own ontology beyond OE-002 §5.5/§5.6's already-published text.

## 18. Relationship to Evidence

**Evidence has no canonical disposition in this repository's governing sources.** Per the Reconciliation Plan's own Section 21 (Q1, cited exactly, not paraphrased beyond quotation): *"Question, Interpretation, Conclusion, Evidence have no canonical disposition at all — a genuine open architectural dependency, not resolved here."* This review does not invent an Evidence ontology, and does not resolve whether Observation replaces, narrows, overlaps with, or remains wholly independent of Evidence. **This is recorded precisely as a genuinely open, pre-existing architectural dependency, not created or worsened by this review, and not blocking**: nothing in OE-002 §5.1 requires this question to be answered before Observation's own contract can be stated or implemented, and nothing about closing Observation's own `case_id` gap (Section 24) depends on Evidence's disposition being settled first.

## 19. Identity and Permanence

Observation follows the approved identity model exactly (Implementation Architecture Approval §8): a dedicated `ObservationId` (UUID-wrapped, fresh per capture), a `@dataclass(frozen=True)` entity, `recorded_at` assigned once at capture via an injectable clock, no speculative lifecycle field, insert-only repository (`add`/`get` only, confirmed by direct inspection of `atlas/core/domain/observation/repository.py`). **What makes one Observation the same object over time**: its `id` alone (OE-002 §5.1 Identity clause: "stable identity independent of its content"). **Can content ever be updated?** No — the entity is frozen; no `update` method exists anywhere in the domain, application, or persistence layers. **Can source or metadata be corrected?** No, for the identical reason — any correction is a *new* Observation, never an in-place mutation. **Can malformed content be repaired?** No — malformed input is rejected at construction (via `MissingStatementError`/`MissingSubjectError`/`InvalidObservedAtError`, confirmed present in `exceptions.py`), never silently repaired after acceptance. **Must a correction create a new Observation?** Yes — matching the identical discipline already established for Judgment's own "revised assessment is a new, separate Judgment" rule (Design §24), reused here by direct structural analogy since OE-002 imposes the identical general permanence contract (INV-009/011) on every Domain Object, Observation included. **Can an Observation be deleted?** No. **Superseded?** Only in the general, non-erasing sense INV-011 already permits for every type (a later object MAY supersede or reinterpret an earlier one without erasing it) — no dedicated `supersedes` field exists or is required. **Invalidated?** No dedicated invalidation mechanism exists or is canonically forced; if a Case later determines an Observation's content was wrong, that determination is itself recorded as a further, separate fact (e.g., a Judgment characterizing the Observation), never a mutation of the Observation itself — identical to the discipline already established for an "accepted Judgment later shown wrong" (Judgment review §12). **Can it remain permanently accepted while later Judgments reject or contradict its content?** Yes, without qualification — this is exactly what permanence plus truth-independence together require: the Observation's own valid, permanent existence is entirely independent of whatever any later object says about its content's truth.

## 20. Case Ownership

Observation must belong to exactly one Case (INV-002), identically to every other Domain Object. **The already-shipped implementation currently lacks `case_id`** — confirmed directly by inspecting `atlas/core/domain/observation/entity.py` (fields: `id, subject, statement, observed_at, recorded_at, source, note` — no `case_id`) and `atlas/core/infrastructure/persistence/observation/table.py` (columns: `observation_id, subject, statement, source, note, observed_at, recorded_at` — no `case_id` column), matching exactly what the Reconciliation Plan's own DO-REC-026 entry states and what the Knowledge Reference and Judgment persistence regression suites already independently assert about Observation's current column set. This is a real, already-identified, narrowly-scoped gap (a single required-field addition, not a multi-field redesign, since Observation has no alternate-form/matter-reference structure to correct — unlike Decision or Outcome) — not resolved by this review, since this review performs no implementation.

## 21. Referential Invariants

**Observation has no outgoing Domain Object reference of its own.** OE-002 §5.1's Relationships clause states plainly: "Observation requires no other Domain Object to exist validly." `source`, where present, is plain, optional, non-defining text (Section 12) — explicitly not a typed Domain Object reference, and this review does not treat it as one, per this task's own instruction not to treat external identifiers as typed Domain Object references unless the accepted architecture permits it (it does not: `DomainObjectType`'s six members are Domain Objects only, and `source` names no Domain Object at all). Consequently: INV-004 (same-Case reference) and INV-005 (prior acceptance) have no application to Observation's own capture path — Observation itself asserts nothing referentially that needs verifying. These invariants become relevant only from the *other* direction: when Knowledge Reference or Judgment (or, in the future, Decision, Outcome, Reasoning Trace) verify an *Observation* as their own target, entirely on the referencing object's own side, exactly as already implemented and approved (Implementation Architecture Approval §§14, 18–19). The no-deferred-invariant rule (OE-006 §5/§9/§16) is therefore satisfied trivially for Observation's own capture — there is no applicable referential invariant left unestablished, because none applies to Observation's own outgoing structure at all. Dependency ordering and DAG consequences (Implementation Architecture Approval §16) are likewise inapplicable to Observation's own capture path for the identical reason, though Observation's *existence as a valid, already-accepted target* is exactly what makes the DAG argument work for whichever future object references it.

## 22. Root Eligibility

**Observation is structurally, unconditionally root-eligible.** OE-002 §5.1's Relationships clause states this directly: "Observation is root-eligible: it MAY be the first Domain Object accepted into a Case." INV-012 states the identical fact from the invariant side: "Observation MAY be the first accepted Domain Object in a Case." This follows structurally from Section 21's own finding — Observation has zero outgoing reference fields, so it can never fail a prior-acceptance check (there is none to fail), unlike Knowledge Reference and Reasoning Trace (which structurally *cannot* be first, since each requires an already-accepted target) and unlike Judgment/Decision/Outcome's own form-conditional root eligibility. **This is unconditional, not form-dependent** — Observation has only one form (content-preservation), never a referential alternative form the way Judgment, Decision, and Outcome each do.

**Canonical root eligibility (settled, unconditional) is distinct from current capture availability**: today, `POST /observations` already exists and is already reachable end-to-end (per `ObservationCaptureAPI003.md` and the currently-committed router), but without a `case_id` field — meaning the currently-shipped capture path is not yet fully INV-002-conformant, even though it is fully root-eligible and otherwise content-conformant. **This review-only package does not enable, and is not expected to enable, corrected (Case-conformant) capture availability** — that is the scope of a distinct, future implementation package (matching the Reconciliation Plan's own DO-REC-026/DO-IMP-013 entry), not performed here.

## 25. Cardinality and Semantic Unity

**One Observation represents one preserved content-item, atomically — not an unrestricted compound document.** OE-002 §5.1's own singular noun-phrase framing ("informational content," never "contents" or "a set of...") is read the same way the Judgment Implementation Design read Judgment's own singular "an identified subject" framing to conclude exactly-one-or-none cardinality — the identical interpretive method, applied consistently. This is the one coherent semantic boundary the text supports without inventing additional structure.

Testing the required examples against this boundary: **one market price** — a single, atomic Observation; clean fit. **An income statement containing hundreds of values** — the *whole statement*, taken as a single preserved artifact, is one Observation's content (the "item" being the document as a unit, not each line); if individual line items later need independent identity, reference-eligibility, or characterization, *each* would need its own, separate Observation (or a future Judgment/Reasoning Trace referencing the whole) — OE-002 does not force a granularity decision here, and none is invented by this review; this is a genuine, non-blocking implementation-granularity choice, deferred until a concrete need (e.g., a Judgment wanting to characterize one specific line item) actually arises. **A paragraph containing several claims** — the same reasoning applies: the paragraph as a whole is one Observation's content unless and until a concrete need to reference or judge one claim independently forces splitting it into multiple Observations. **An image, an entire PDF, a table, a time series** — each is representable as one Observation's content under the current, text-first realization only to the extent it can be reduced to text (e.g., a caption or transcription) or, in the future, under Candidate G's narrower external-artifact extension (not resolved here). **A source report with both true and false statements** — fully representable as one Observation, since Observation asserts nothing about truth in the first place; a report's internal mix of true/false claims is a fact about the *content*, never a fact the Observation object itself needs to resolve or flag.

**If the model permits compound payloads (the income-statement/paragraph case), individual parts cannot later be independently referenced, judged, supported, or contradicted without violating identity and permanence** unless a *separate* Observation is captured for the part that needs independent treatment — this is not a defect; it is the correct consequence of atomic identity (INV-006) applied consistently: an object's identity cannot be subdivided after the fact without creating a new object. **Atomicity is defined precisely enough to implement**: one Observation, one `statement` value, whatever granularity that value's own author chooses at capture time — the boundary is drawn by the capturer's own choice of what to preserve as one unit, not by Atlas Core itself imposing a granularity rule.

## 32. Required Corrections

**Correction 1 — Ontology statement wording.**
*Problematic statement*: "whose entire semantic content is that specified observational content has been admitted into a Case."
*Why incorrect*: conflates the general, OE-006-governed acceptance/admission fact (true of every Domain Object) with Observation's own distinctive, OE-002 §5.1-governed semantic operation (preserving content without asserting truth); risks collapsing toward Candidate H (capture event) if read literally.

*Replacement statement*: "An Observation is a permanent, independently identified Domain Object that preserves specified informational content, without asserting that the content is true, verified, reliable, or authoritative. Indication of origin, where present, is optional and non-defining."
*Classification*: changes terminology/documentation only — does not change ontology (OE-002 §5.1 is unchanged and unaffected), does not change fields, does not change architecture.
*Blocking*: blocks only how a future implementation package's own design brief should *state* Observation's ontology — does not block this review's own approval of Observation as a Domain Object, since OE-002 §5.1 already, independently governs regardless of this prompt's own wording.

**Correction 2 — `case_id` addition.**
*Problematic statement*: none in the ontology itself; the gap is in the already-shipped code (`atlas/core/domain/observation/entity.py`, `.../persistence/observation/table.py`), which has no `case_id` field or column.

*Governing source*: OE-002 §3; INV-002; Reconciliation Plan DO-REC-026 (engineering-planning, non-normative, but accurately describing an already-settled invariant's own consequence).
*Replacement*: add `case_id: CaseId` (domain), `case_id String NOT NULL, indexed` (persistence), `caseId` (API request/response) — no other field changes required.
*Classification*: field/architecture correction (additive), not an ontology change — OE-002 §5.1 already required this; the correction closes an implementation gap, not a definitional one.
*Blocking*: blocks full INV-002 conformance and blocks Observation from becoming a currently-capture-enabled target for Knowledge Reference/Judgment — does not block this review's own outcome, since this review is scoped to ontology/architecture correctness, not to closing the gap itself (that is a distinct, future implementation package).
