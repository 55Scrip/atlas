## 7. Implemented Architecture Overview

Four packages, one coherent layering convention: domain (`entity.py`, `value_objects.py`, `exceptions.py`, `repository.py` Protocol) → persistence (`table.py`, `sqlalchemy_repository.py`) → application (one capture/create service per package) → API (`schemas.py`, `dependencies.py`, `router.py`, `errors.py`), wired into one shared `atlas/core/infrastructure/api/app.py` composition root. Case is the ownership boundary with no semantic content. `DomainObjectType`/`TypedDomainObjectReference` are the shared, reused-not-reinvented polymorphic reference mechanism. Knowledge Reference is the first, and so far only fully-shipped, required-single-reference Domain Object. Judgment is the first, and so far only fully-shipped, Domain Object with both a root-eligible internal-content form and a non-root referential form built atop the identical shared reference mechanism.

## 8. Domain Object Identity Approval

Every one of Case, Knowledge Reference, and Judgment: (a) carries a dedicated, independently-generated typed identifier (`CaseId`, `KnowledgeReferenceId`, `JudgmentId`), each a `@dataclass(frozen=True)` wrapping a `uuid.UUID` with `default_factory=uuid.uuid4`, each with a `__str__` returning the raw UUID string — confirmed structurally identical across all three by direct inspection; (b) is itself a `@dataclass(frozen=True)` entity, immutable at the Python level; (c) belongs to exactly one Case (Knowledge Reference, Judgment — `case_id: CaseId`, non-nullable) or is itself the ownership boundary (Case); (d) carries `recorded_at`, assigned exactly once, inside its own `create`/`capture` classmethod, via an injectable `clock` parameter, never user-supplied; (e) carries no speculative lifecycle field (no status, draft, pending, or approval state) anywhere; (f) is insert-only at the repository level (`add`/`get` only — confirmed by direct inspection of all three `repository.py` Protocols; no `update` or `delete` method exists anywhere in `atlas/core/domain/{case,knowledge_reference,judgment}/` or their persistence counterparts); (g) has no value-based identity accident — each entity's default, field-by-field dataclass equality compares equal only when every field, including the always-fresh-per-instance `id`, matches, so two content-identical instances remain distinct, confirmed explicitly by dedicated tests in both the Knowledge Reference and Judgment domain test suites; (h) has no replacement or supersession mechanism — no `supersedes` field, no in-place mutation path, exists anywhere.

**Case, Knowledge Reference, and Judgment follow one coherent identity model with no divergence found.** No implementation-unsafe divergence exists.

## 9. Case Ownership Approval

`case_id: CaseId` is required and non-nullable on both Knowledge Reference and Judgment (confirmed by direct inspection of both `table.py` schemas: `Column("case_id", String, nullable=False, index=True)` in each). `DomainObjectType` correctly excludes Case (confirmed: six members, no `CASE`, per `atlas/core/domain/shared/domain_object_type.py`'s own docstring, which states explicitly "Case is deliberately excluded" and cites the Type-Set Discrepancy Investigation as its own settled basis) — Case cannot be used as a polymorphic reference target anywhere: attempting `targetType: "Case"` is rejected by Pydantic's own enum validation at 422 before reaching any service, confirmed by dedicated tests in both the Knowledge Reference and Judgment API test suites.

**On CaseRepository validation's absence in every capture service**: confirmed, by direct inspection, that `CaseService`, `KnowledgeReferenceService`, and `JudgmentService` each accept `case_id` as given, with no dependency on `CaseRepository` and no call verifying the named Case actually exists. This is intentional, consistent, and architecturally acceptable, for three independent reasons verified directly rather than assumed: (1) it is applied *uniformly* across every module that has a `case_id` at all — not a gap unique to one package; (2) no governing source (OE-002 §3.1, OE-004 INV-002) states or implies an obligation on a referencing module to verify its owning Case's prior existence — INV-002 states only that every Domain Object *belongs to* exactly one Case, a fact about the object's own field, not a validation duty on its capture path; (3) Case itself has no semantic content that could be violated by a non-existent `case_id` (Case's own committed docstring: "no further field is canonically required"), so there is no invariant this omission could be silently weakening. **Future packages can reuse this ownership model without ambiguity — it is already exercised twice (Knowledge Reference, Judgment) with identical results, and no formal correction is required before further implementations.**

## 10. Canonical Domain Object Type Set Approval

`DomainObjectType(str, Enum)` (`atlas/core/domain/shared/domain_object_type.py`) has exactly six members — `OBSERVATION`, `KNOWLEDGE_REFERENCE`, `REASONING_TRACE`, `JUDGMENT`, `DECISION`, `OUTCOME` — confirmed by direct inspection; no `CASE` member; no implementation-only member has been added by either downstream package. Both `knowledge_references_table` and `judgments_table` generate their respective CHECK constraints from `tuple(member.value for member in DomainObjectType)` directly (confirmed in both `table.py` files) rather than a hand-duplicated literal list, so the two can never drift apart — this was independently verified by dedicated tests in both persistence test suites (`test_check_constraint_accepts_every_adopted_target_type`/`..._subject_target_type`) re-run fresh as part of this review's own regression pass (Section 24). API parsing uses the identical enum in both packages via the shared `TypedDomainObjectReferenceSchema` (`atlas/core/infrastructure/api/shared/typed_reference_schemas.py`), never a locally re-declared string field, so a future type cannot silently appear through a stringly-typed path — any string outside the six values is rejected by Pydantic's own enum validation before reaching either service. Canonical eligibility (OE-002 §5.2/§5.4: "no specific Domain Object type is required" as target) is kept explicitly, textually distinct from current capture availability in both packages' own module docstrings and error messages (`TargetTypeUnavailableError`'s own wording, verified identical in intent across both), never conflated.

**The shared type set is ready to govern all remaining packages.**

## 11. Typed Reference Infrastructure Approval

`TypedDomainObjectReference` (`atlas/core/domain/shared/typed_reference.py`) is a `@dataclass(frozen=True)` carrying exactly `target_type: DomainObjectType` and `target_id: uuid.UUID`, with `__post_init__` isinstance-checking both fields and raising `InvalidTypedDomainObjectReferenceError` otherwise — confirmed by direct inspection: one canonical target type, one canonical target identifier, atomic construction, strict enum validation (via the isinstance check plus `DomainObjectType`'s own closed membership), strict identifier validation. Equality and serialization are stable: the frozen dataclass's default equality compares both fields together, and the module's own docstring states this is deliberate so the value object is directly usable inside a set (anticipating Reasoning Trace's own future non-empty support set without redesign). It carries no Case field (no Case targeting is possible — `target_type` cannot be `CASE`, since no such member exists) and, per its own docstring, "no truth, confidence, provenance, or authority semantics."

**Nullable representation is handled safely and consistently at every layer**, verified by direct inspection of both consuming packages: Knowledge Reference requires its `target` unconditionally (no optionality needed, since Knowledge Reference has no internal-content alternative — OE-002 §5.2), while Judgment wraps the identical shared type in `subject: TypedDomainObjectReference | None`, a single atomic optional field, never two independently-nullable primitives — confirmed at the domain layer (one Python field), the persistence layer (two nullable columns plus a dedicated paired-nullability CHECK constraint, `ck_judgments_subject_reference_paired`), and the API layer (`subject: TypedDomainObjectReferenceSchema | None`, a nested optional Pydantic model, never flat optional fields). This demonstrates the shared mechanism already supports both a **required single reference** (Knowledge Reference) and an **optional single reference** (Judgment) without any modification to `TypedDomainObjectReference` itself. **A future non-empty set of typed references (Reasoning Trace) is not designed here** — no current defect forces that decision, and this review does not invent one; the shared value object's own frozen, hashable construction is already compatible with set membership if and when that package is built, per its own docstring's own forward-looking note, which this review verifies as accurate rather than merely restating.

No separate draft, proposal, candidate, pending, or approval status exists anywhere in any of the three entities or their application services — confirmed by direct inspection of all three `entity.py` files and all three application services.

## 13. Permanence Model Approval

All three entities are `@dataclass(frozen=True)`; all three repository Protocols expose exactly `add`/`get`, confirmed by direct inspection, with dedicated tests in the Knowledge Reference and Judgment persistence suites explicitly asserting `not hasattr(repository, "update")` / `not hasattr(repository, "delete")` (Case's own persistence suite does not carry an identical explicit assertion, but its Protocol is textually and structurally identical — confirmed by direct source inspection — so the property holds, merely without a redundant, dedicated test for it; noted as a minor test-coverage asymmetry in Section 24, not a permanence defect).

## 14. Referential Invariant Enforcement Approval

INV-004 (same-Case) and INV-005 (prior acceptance) are each enforced identically in Knowledge Reference's `_verify_target` and Judgment's `_verify_subject`: both first gate on membership in a `_CURRENTLY_CAPTURE_ENABLED_*` frozenset, then perform an existence lookup via the correct repository, then compare `existing.case_id != case_id`. INV-006 (distinct identity) is structurally guaranteed by fresh-UUID generation on every capture, not by any runtime check. No separate "cycle invariant" is numbered in OE-004; the cycle consequence is analyzed in Section 16 as a derived structural fact, not an independently-enforced rule requiring its own validation code.

**"Every applicable invariant must be fully established before acceptance" is applied without exception in both packages** — confirmed by direct inspection of both `_verify_target`/`_verify_subject` methods: there is no code path in either that admits a target/subject whose INV-004 or INV-005 status is anything other than fully, positively confirmed. **Accepted-with-deferred-invariant behavior is confirmed absent** in the current, committed state of both packages (Knowledge Reference's own pre-correction history, in which three of five types were briefly admitted without a same-Case check, was found and corrected before its own commit — per the Knowledge Reference Pre-Commit Architecture Review's own Outcome 2 — and the corrected, uniform-rejection principle was applied to Judgment from its own inception, per the Judgment Pre-Commit Architecture Review's own Section 13).

The five-way distinction — unknown target type; canonical-but-currently-unavailable target type; target not found; cross-Case target; malformed reference — is drawn identically in both packages: unknown values are rejected by Pydantic/`DomainObjectType.parse` (422, or `UnknownDomainObjectTypeError`→400 at the domain-shared level, never reaching either service); canonical-but-unavailable types raise `TargetTypeUnavailableError`; not-found and cross-Case targets raise their own respective, correctly-named exceptions; malformed references (a non-UUID `target_id`, or a `TypedDomainObjectReference` constructed with the wrong Python types) raise `InvalidTypedDomainObjectReferenceError` at the shared layer or Pydantic 422 at the API layer, before either domain module's own service is reached.

**The current validation architecture is reusable, not yet duplicating logic in a way requiring correction** — see the dedicated duplication analysis in Section 25. **No generic registry or graph engine is recommended**, because no concrete defect currently exists that one would fix; the two independent, hand-written verification methods are each small, each object-specific, and each already correctly tested.

## 15. Canonical Eligibility versus Capture Availability

Approved without qualification. Both packages state, in their own module docstrings and error messages, the identical distinction: all six `DomainObjectType` members remain canonical, reference-eligible Domain Object types (OE-002 §5.2/§5.4) at all times; *current capture availability* is a separate, present-state, non-normative fact about which target types' applicable invariants (INV-004, INV-005) can currently be positively established given what else has and has not yet been implemented. Knowledge Reference currently capture-enables only itself (`{KNOWLEDGE_REFERENCE}`); Judgment currently capture-enables Knowledge Reference and itself (`{KNOWLEDGE_REFERENCE, JUDGMENT}`) — the difference between the two sets is itself evidence the distinction is being applied on its own merits per package, not copied as a fixed constant, since Judgment's own repository (built after Knowledge Reference's) newly makes a second type verifiable that Knowledge Reference's own, earlier-committed set could not yet include.

## 16. Acceptance Ordering and DAG Analysis

Verified directly against both services' control flow, not merely asserted from precedent: in both `KnowledgeReferenceService.capture` and `JudgmentService.capture`, the new entity's own `id` is generated only *inside* `capture()` on the entity class, which is called only *after* `_verify_target`/`_verify_subject` has already run to completion. A caller therefore cannot supply, as a target/subject id, the identity of the very object under construction, because that identity does not exist at request-construction time — **direct self-reference is structurally impossible** for this reason alone, independent of any invariant check. **Two-object and longer cycles are structurally impossible**: INV-005 forces every reference to point only to an already-accepted object, and INV-009/INV-011 (permanence, no update, no retroactive reference insertion) preclude closing a cycle after the fact — together these force accepted referential edges into a strict DAG. **Explicit cycle traversal is confirmed unnecessary and confirmed absent** — no graph-walking, visited-set, or recursive-lookup code exists anywhere in either `capture_knowledge_reference.py` or `capture_judgment.py`, verified by direct inspection.

This conclusion holds, verified per the four required cases: **Knowledge Reference targeting Knowledge Reference** (the only currently-enabled Knowledge Reference target type) — impossible to self-reference or cycle, by the argument above. **Judgment targeting Judgment** — identical argument, independently verified against `_verify_subject`'s own control flow. **Judgment targeting Knowledge Reference** — the two entities are different types with independent identity spaces, so a "cycle" in the literal graph-theoretic sense (a Judgment referencing a Knowledge Reference that references that same Judgment back) is foreclosed differently: Knowledge Reference's own currently-enabled target set is `{KNOWLEDGE_REFERENCE}` only, so no Knowledge Reference can currently reference a Judgment at all — the cross-type edge exists in only one direction today, making a cross-type cycle presently impossible for an additional, capture-availability reason on top of the ordering argument. **Future Domain Objects using the same acceptance rule**: the argument depends only on INV-005 and permanence, both adopted, general facts (OE-004 §§8, 10) that any future package inherits automatically by following the same "generate id only after verification" construction order already established twice — no future-specific exception or special case is needed.

**No implementation path was found that could bypass this ordering** — both repositories are insert-only, both entities are frozen, and identity generation is confirmed to occur strictly after verification in both current services.

## 17. Root Eligibility Analysis

Root eligibility is correctly treated, in both Knowledge Reference and Judgment, as a **structural possibility derived from whether capture requires a prior accepted target**, never as stored metadata — confirmed by direct inspection: neither entity's field list (Section 8) contains any root/first/isRoot flag, and neither service performs a dedicated "is this the first object in the Case" check.

**Case's own role relative to root objects**: Case is not itself a member of the referential structure OE-002 §6 describes (it is the ownership boundary, not a Domain Object per §3.1/§4), so root eligibility as OE-002 §6/INV-012 define it does not apply to Case at all — this is not an omission but the already-settled consequence of the Type-Set Discrepancy Investigation's own Outcome 1, correctly reflected by `DomainObjectType`'s exclusion of `CASE`.

**Knowledge Reference's inability to bootstrap through its own capture service** is confirmed structural, not accidental: Knowledge Reference has no internal-content alternative form (OE-002 §5.2 names only the referential form), so every capture requires an already-accepted target, meaning the very first Knowledge Reference in an otherwise-empty Case can never be produced by `KnowledgeReferenceService.capture()` alone — exactly matching INV-012's own statement that Knowledge Reference "MUST NOT be the first accepted Domain Object in a Case." This is a genuine, anticipated, non-blocking consequence, already handled in both the Knowledge Reference and Judgment test suites via direct domain-plus-repository seeding (bypassing the service, never the invariant) — **an expected implementation-order/ontological consequence, not a bootstrap defect** requiring any exception.

**Judgment's internal-content form is confirmed root-eligible**: `JudgmentService.capture()` invokes `_verify_subject` only `if request.subject is not None`, so a subjectless capture request performs zero referential checks and cannot fail on any prior-existence ground — directly exercised by `TestInternalContentFormRootEligibility.test_captures_the_first_ever_domain_object_in_an_empty_case`. **Judgment's referential form is confirmed necessarily non-root**, as a byproduct of the same INV-005 check that already runs for any other reason — no separate, additional root-eligibility validator was added or is needed.

**No genuine bootstrap problem exists anywhere in the current architecture** — only the expected, already-anticipated consequence that a required-reference type (Knowledge Reference) cannot self-bootstrap, which is precisely what INV-012 itself states should be true. **No bootstrap exception was invented**, and none is warranted.

## 20. Error Taxonomy Approval

Verified across all four packages directly: each has its own base `XError(Exception)`; each `NotFoundError` maps to 404; Case has no validation-error subclass at all (correctly, since it has no user-supplied semantic content to validate — confirmed by its own `exceptions.py` docstring, which states this explicitly rather than merely omitting it by oversight); Knowledge Reference and Judgment each carry a structurally identical four-member referential taxonomy (`TargetNotFoundError`, `CrossCaseTargetError`, `TargetTypeUnavailableError`, plus Judgment's own additional `MissingCharacterizationError` for its own required-content field, which Knowledge Reference has no analog for since it has no comparable free-content field). HTTP mapping is consistent: 404 for the aggregate's own not-found case; 400 for every referential/content-validation failure; 422 (via Pydantic, before any service is reached) for malformed shape or an unknown enum value — identical across every package, confirmed by direct inspection of all four `errors.py` files. **Naming and mapping are sufficiently consistent for reuse; the deliberate difference in exception-set size between Case and the two referential types correctly reflects their different semantic contracts, not an inconsistency to correct.**

## 21. Persistence Architecture Approval

Table naming follows one plural-noun convention (`cases`, `knowledge_references`, `judgments`) with a package-prefixed primary-key column name (`case_id`, `knowledge_reference_id`, `judgment_id`) — confirmed consistent across all three `table.py` files. `case_id` is represented identically wherever it appears (`String`, `nullable=False`, indexed). `recorded_at` is represented identically everywhere (`String`, `nullable=False`, `datetime.isoformat()` on write, `datetime.fromisoformat()` on read). Enum CHECK constraints are generated from `DomainObjectType` identically in both Knowledge Reference and Judgment (Section 10). The paired-nullability CHECK constraint is unique to Judgment, correctly, since only Judgment has an optional reference field — its absence from Knowledge Reference's own table is not an inconsistency, since Knowledge Reference's target is never nullable. No invalid polymorphic foreign key exists anywhere — confirmed absent by direct inspection and by dedicated tests asserting `foreign_keys == set()` in both referential persistence suites. Repository reconstruction (`_to_row`/`_to_<entity>`) round-trips every field exactly in all three modules, confirmed by each persistence suite's own `TestEqualsOriginal` class. Insert-only behavior and the absence of update/delete paths are confirmed in Section 13. Transaction behavior is uniform: every `add` executes inside `with self._engine.begin() as connection: connection.execute(insert(...))`, one atomic transaction per insert, identical across all three repositories.

**Duplicate-ID behavior**: the primary-key column in each table (`String, primary_key=True`) structurally guarantees uniqueness at the database level; however, **no test in any of the three persistence suites explicitly exercises inserting two rows with the same id and asserting the resulting `IntegrityError`** — confirmed by a direct search across all three `test_sqlalchemy_repository.py` files, which found `IntegrityError` used only for CHECK-constraint violations (non-adopted type, partially-null pair), never for a duplicate-primary-key insertion. This is a real, minor, testing-coverage gap, not a persistence-architecture defect: no code path anywhere in any application service ever supplies a caller-controlled id (every `id` is generated internally via `uuid.uuid4()`), so the untested condition is currently unreachable through any adopted capture path, and the guarantee itself is enforced by the schema, not by any application-level logic that could silently regress. Recorded here for completeness (Section 24) and not treated as blocking, per the Approval Standard's own instruction that minor stylistic/coverage gaps do not block approval.

**The persistence architecture can safely be reused by remaining Domain Objects. No migration or schema concern was identified that must be addressed before further packages proceed.**

## 22. API Architecture Approval

Route conventions are uniform: `POST /<plural-resource>` (201) to capture/create, `GET /<plural-resource>/{id}` (200/404) to retrieve, no list/update/patch/delete endpoint in any of the three routers — confirmed by direct inspection of all three `router.py` files. Request/response schemas subclass the shared `CamelModel` (ADR-004) uniformly; camelCase is the wire format, with `populate_by_name=True` giving snake_case backward compatibility, confirmed exercised by a dedicated test in each of the Knowledge Reference and Judgment API suites (Case has no request body to test this against, correctly, since it captures no semantic input at all). The nested typed-reference representation (`TypedDomainObjectReferenceSchema`, required in Knowledge Reference's schema, optional in Judgment's) is reused directly from the shared DO-IMP-002 module in both packages, never re-declared. UUID and enum parsing is delegated to Pydantic uniformly, with the 422/400 asymmetry (malformed shape/unknown enum → 422 before any service; canonical-but-currently-unavailable or referentially-invalid → 400, from within the service) confirmed identical across both referential packages. Dependency wiring and error-handler registration each follow the identical `get_<x>_repository` → `get_<x>_service` → `register_<x>_error_handlers` shape, composed once in `app.py`.

**The API architecture is coherent and ready to govern later Domain Object endpoints.**

## 23. Dependency-Injection Approval

Every module's `get_<x>_repository` reuses the shared `get_decision_engine` (from `atlas.core.infrastructure.api.decision.dependencies`, the same physical `atlas.db` file every other module in this codebase already shares) and calls its own `create_<x>_table(engine)` before constructing its own `SqlAlchemy<X>Repository` — confirmed identical in shape across Case, Knowledge Reference, and Judgment. Judgment's own `get_judgment_service` additionally composes `KnowledgeReferenceRepository` via `Depends(get_knowledge_reference_repository)`, reusing Knowledge Reference's own already-wired dependency function directly rather than re-implementing repository construction — confirmed by direct inspection of `judgment/dependencies.py`, and confirmed as the correct, minimal way to satisfy a genuine cross-package collaborator dependency without duplicating wiring logic. **This pattern is approved and directly extensible**: a future package needing to verify a Knowledge Reference or Judgment target can reuse the identical `Depends(get_knowledge_reference_repository)` / a new equivalent `Depends(get_judgment_repository)` without any change to either existing module.

## 24. Test Architecture Approval

Coverage confirmed present, by direct inspection and fresh execution (this review re-ran every suite named below), for: semantic construction (all four packages); invalid construction (Knowledge Reference, Judgment — malformed subject/target types rejected; Case has no invalid-construction case, correctly, since it has no fields a caller could supply incorrectly); immutable/distinct identity (dedicated tests in Knowledge Reference and Judgment domain suites; Case's own entity docstring states the identical property but has no dedicated distinct-identity test — a minor asymmetry, not a defect, since the property follows from the same frozen-dataclass-plus-fresh-UUID mechanism verified elsewhere); persistence constraints (CHECK constraints, paired nullability, foreign-key absence — Knowledge Reference and Judgment); repository behavior (insert-only assertions — Knowledge Reference and Judgment explicitly; Case implicitly via its identical Protocol, per Section 13); application invariants, same-Case rejection, prior-acceptance rejection, and canonical-but-unavailable-type rejection (both referential packages, parametrized across every relevant `DomainObjectType` member); API serialization and parsing (all packages with a request/response body); error mapping (all four `errors.py` modules, each exercised by at least one status-code assertion per registered handler); regression protection for shared infrastructure (`DomainObjectType`'s six-member closure and `TypedDomainObjectReference`'s own behavior, explicitly re-asserted inside both the Knowledge Reference and Judgment persistence suites' own `TestExistingCoreTablesAreUnchanged`/`TestPreviouslyImplementedInfrastructureUnchanged` classes).

**One systemic, minor gap identified**: no persistence suite, in any of the three modules with a primary key, exercises an explicit duplicate-id insertion against the actual `IntegrityError` the schema's own `primary_key=True` constraint would raise (Section 21). **This does not block architecture approval** — it is a coverage gap around a condition no adopted code path can currently reach (ids are always internally generated, never caller-supplied), not evidence of a behavioral defect, and the Approval Standard explicitly excludes minor coverage gaps from blocking approval.

**No systemic testing gap was found that should block architecture approval.**

## 25. Duplication and Abstraction Analysis

Inspected directly: Knowledge Reference's `_verify_target` and Judgment's `_verify_subject` share an identical three-step shape (capture-enabled-set membership check → existence lookup via the correct repository → same-Case comparison), and both packages' dependency-wiring modules share an identical `get_<x>_repository`/`get_<x>_service` shape, and both API `errors.py` modules share an identical `NotFoundError→404, referential-errors→400, shared-errors→400` mapping shape.

**Classification: (A) acceptable explicit duplication at this stage.** Each of the three shared shapes is, in every current instance, paired with genuinely object-specific content that a shared abstraction would either have to parameterize awkwardly or would risk conflating: Knowledge Reference's own capture-enabled set, error classes, and docstrings are independently derived from OE-002 §5.2's own contract; Judgment's are independently derived from OE-002 §5.4's own, textually different contract (including the extra `MissingCharacterizationError` case Knowledge Reference has no analog for, and the extra self-repository-or-collaborator-repository dispatch Judgment's own `_verify_subject` performs that Knowledge Reference's simpler, single-target-type `_verify_target` does not need). Collapsing these into one shared validator now would either (i) smuggle a universal "Reference" abstraction into the domain layer — explicitly forbidden by the Reconciliation Plan's own Section 7 instruction and by this whole implementation series' repeated, explicit prohibition on a universal graph/reference entity — or (ii) produce a shared function so heavily parameterized by per-object callbacks that it would save no real duplication while adding an extra layer of indirection between each object's own error semantics and its own governing OE-002 subsection.

No concrete defect has resulted from this duplication in either shipped package — both are independently correct, independently tested, and independently reviewed (Sections 18–19) — so **(B) a concrete consistency risk requiring a narrow shared abstraction now** is not supported: two instances of a shape, each still faithfully object-specific, is not yet evidence of drift, only evidence of a shared *pattern* worth recognizing in prose (as this section does) without yet extracting it into code. **(C) evidence the architecture is not yet ready for additional packages** is likewise not supported — the duplication observed is exactly the ordinary, expected repetition of a young pattern with two instances, not a sign of incoherence; a third or fourth instance repeating the identical shape without any object-specific divergence would be the concrete signal that would justify extraction, and this review does not manufacture that signal in advance of it actually occurring.

**No shared abstraction is recommended.** This conclusion is reached because no current defect justifies one, not because abstraction is undesirable in principle — exactly the standard this review's own governing instructions require.

## 26. Remaining Implementation-Order Dependencies

Currently capture-enabled subject/target types: `{KNOWLEDGE_REFERENCE}` for Knowledge Reference; `{KNOWLEDGE_REFERENCE, JUDGMENT}` for Judgment. Currently unavailable: Observation, Decision, Outcome (each lacks `case_id` today — DO-REC-026/005/013, none yet implemented, confirmed directly against each of their own tables' column sets in this review's own regression pass) and Reasoning Trace (no implementation of any kind exists yet — DO-IMP-009, confirmed by repository-wide search, reused from the Judgment Implementation Design's own Section 35 finding and re-confirmed structurally unchanged in this review).

Each becomes verifiable, and thus capture-enabled, purely mechanically once its own prerequisite lands: Observation/Decision/Outcome once their own `case_id` backfill (DO-IMP-013/006/007) ships, adding same-Case (INV-004) verifiability; Reasoning Trace once DO-IMP-009 ships, adding prior-acceptance (INV-005) verifiability via a real repository. **No change to Knowledge Reference's or Judgment's own schema or API contract will be required when any of these land** — only each service's own `_CURRENTLY_CAPTURE_ENABLED_*` frozenset and its own dependency wiring need to grow to admit the newly-verifiable type, exactly as both modules' own docstrings already state.

**This implementation-order dependency is explicitly anticipated by the Reconciliation Plan**, not a surprise this review discovered: its own dependency diagram and its own DO-REC-004/DO-IMP-004 entries name DO-IMP-001/002 as Judgment's only hard prerequisites, and separately schedule DO-IMP-006/007 (Decision/Outcome) and DO-IMP-013 (Observation) as soft-dependency packages that may ship in parallel with or after Knowledge Reference/Judgment, and DO-IMP-009 (Reasoning Trace) as its own, later, independent package. **No existing package must be modified when a later repository becomes available** beyond the anticipated, additive frozenset/wiring extension described above — this review does not begin any such modification.

## 27. Architecture Risks

1. **Duplicate-primary-key insertion is untested across all three modules with a primary key** (Section 21/24). Low severity: unreachable through any adopted capture path, since every id is internally generated; mitigated by the schema's own `primary_key=True` constraint independent of any test. Not blocking.
2. **Case has no dedicated pre-commit architecture review document**, unlike Knowledge Reference and Judgment. Low severity: Case's own contract is minimal (two fields, no semantic content, no referential behavior), and its committed implementation was independently verified in this review's own Sections 8–9, 12–13 without finding any discrepancy. Not blocking, but noted as a documentation-completeness observation for the record.
3. **The `_verify_target`/`_verify_subject` shape is duplicated across two packages** (Section 25). Low severity, explicitly analyzed and classified as acceptable at the current instance count; a third repetition without object-specific divergence would raise this risk's severity and should trigger a narrow, dedicated abstraction proposal at that time, not before.
4. **Four canonical types (Observation, Decision, Outcome, Reasoning Trace) remain capture-unavailable as referential targets today** (Section 26). This is a known, explicit, anticipated, non-semantic implementation-order limitation, not an architectural defect — it does not affect the correctness of anything already shipped, and it is documented identically in both affected packages' own module docstrings.

No risk identified above rises to a level requiring correction before approval, per the Approval Standard's own explicit exclusions (minor stylistic/coverage gaps; known implementation-order limitations that are explicit and non-semantic).
