# Legacy Core Loop → Canonical Domain Architecture Reconciliation — Investigation

This document is an investigation-and-design artifact, not a normative document. It carries no Doctrine status (Draft/Final/Superseded/Historical) because those statuses apply to normative documents, and this is not one. It implements nothing, modifies no existing production file, test, or governing document. Where anything here appears to conflict with the Architecture Doctrine, OE-002 through OE-006, or the Historical Decision Record, those documents govern and this one is wrong and must be corrected.

**Audited.** This document has been independently audited following its initial draft: every consequential claim was re-verified against fresh governing-document reads and direct, line-cited live-code inspection, not merely proofread. The audit found the draft's central finding (Observation/Decision/Outcome as genuine live canonical writes) correct and independently reconfirmed it; it also found and corrected one genuine, previously-undisclosed defect (a retry-induced duplicate-legacy-object risk in the proposed M1/M2 packages, Section 15/21/23), sharpened the evidentiary basis for two open questions (reasoning_link duplicate-pair evidence, Section 10; the D4 external-caller question, Section 17/25), fixed one internal citation error (Section 17's package cross-reference), and revised the Required Final Conclusion from B to A on the audit's own re-examination of the standard for each (Section 26). Corrections are marked inline where they occur rather than silently folded in.

## 1. Executive Finding

The live legacy Core Loop and the canonical six-Domain-Object architecture are **not as separate as the Foundation Review's framing suggested.** Direct, fresh inspection of the current conversation orchestrator, decision-review orchestrator, and every composite `reasoning_link` service shows that **three of the six canonical Domain Objects — Observation, Decision, and Outcome — are already correctly, atomically, Case-scoped, written as genuine accepted canonical facts by the live product today**, not merely "bridged" in some approximate sense. This corrects and sharpens the Foundation Review's finding #6 ("Observation is currently the only genuine bridge"): Observation, Decision, and Outcome are all three genuine bridges. Only Knowledge Reference, Judgment, and Reasoning Trace remain entirely unpopulated by any live write path.

The remaining seven legacy aggregates (Question, Interpretation, Hypothesis, Evidence, Conclusion, Evaluation, Learning) and the four `reasoning_link` bridge types are, and were always intended to be, **outside OE-002's closed six-type Domain Object Set** — this was already independently and correctly established by the prior `Core-Loop-Case-Context-Reconciliation-Investigation.md` (Section 8), and this investigation's own fresh, independent re-derivation confirms it exactly: none of the seven is, or needs to become, a canonical Domain Object merely by virtue of existing. INV-002 does not apply to them, and adding `case_id` to any of them would itself be an unauthorized architectural addition.

The genuine, bounded work remaining is narrower than a wholesale migration: (1) two of the seven legacy types — **Evaluation** and, contingently, **Learning** — carry content that corresponds, with disclosed information-loss caveats, to Judgment's own ontology, and could be captured as canonical Judgments *alongside* their existing legacy capture, without removing or redesigning anything; (2) **Conclusion** supplies exactly the raw material for an optional Judgment, but forcing every Conclusion to become one is not required by any governing document and is not recommended; (3) a **Reasoning Trace** citing the Case's own already-accepted Observation(s) can be validly captured today, with zero narrative invention, at Decision-commitment time; (4) **Knowledge Reference** has no currently well-formed live acceptance point, because nothing in the live flow currently produces a reference to an *already-accepted* Domain Object as "the Case's knowledge" — Evidence's raw free text is not, and cannot become, a Knowledge Reference without first being captured as its own accepted object; (5) **Evidence's `CHALLENGES` direction is a genuine, disclosed ontology gap**: Reasoning Trace represents only support, never opposition, and no canonical type currently represents "this challenges that." This is not a migration-mechanics problem; it is an actual expressive gap requiring its own future investigation, not silently worked around here.

## 4. Current Live-Flow Architecture

Two independent, live, tested orchestrations exist:

**The First Decision Conversation** (`atlas/core/application/conversation/`) — `ConversationOrchestrator`, driven by `ConversationSession`, walks exactly `QUESTION → OBSERVATION → INTERPRETATION → HYPOTHESIS → EVIDENCE → CONCLUSION → DECISION → DECISION_RECORDED` (terminal). A `case_id` is resolved once, before the conversation starts, via `resolve_new_case`/`resolve_existing_case` (`conversation/composition.py`), both backed by the unmodified `CaseService`, and is threaded as plain, explicit data through `ConversationSession.case_id` into every request that reaches a canonical capture service. The orchestrator itself has **no** `CaseService`/`CaseRepository` dependency — Case is resolved entirely outside it, exactly per the model selected in `Core-Loop-Case-Context-Reconciliation-Investigation.md` Section 19, and — this investigation's own fresh, corrective finding — that model **has already been fully implemented**, not merely designed. The four `reasoning_link` composite services (`ObserveFromQuestionService`, `FormHypothesisFromInterpretationService`, `CaptureEvidenceFromHypothesisService`, `CommitDecisionFromConclusionService`) bridge the four edges pointing into a protected aggregate (Observation, Hypothesis, Evidence, Decision), each verifying its upstream reference exists (read-only) before delegating, unmodified, to that aggregate's own existing capture service.

**Decision Review** (`atlas/core/application/decision_review/`) — `DecisionReviewOrchestrator`, triggered by selecting an existing, already-committed Decision (read-only lookup, never writes to `DecisionRepository`), walks `OUTCOME → EVALUATION → LEARNING → REVIEW_RECORDED`. `OutcomeService.capture()` derives `case_id` directly from the referenced Decision (`case_id=decision.case_id`) — never independently investor-supplied, never a bug, confirmed by `test_core_loop_end_to_end.py` line 327's own assertion `outcome.case_id == decision.case_id`.

Both orchestrations wrap every service call in a bare `try/except Exception:` that silently re-prompts on any failure — a pre-existing, disclosed, non-blocking risk this investigation does not attempt to correct (Section 23).

## 5. Canonical Architecture Status

Confirmed by direct, fresh re-inspection of every entity, repository, application service, persistence module, and API module: all six canonical Domain Objects — Observation, Knowledge Reference, Reasoning Trace, Judgment, Decision, Outcome — plus Case are fully, correctly implemented per OE-002 through OE-006, exactly as the immediately preceding Foundation Review established. This investigation adds one correction to that review's own finding: **Decision and Outcome are not merely "correctly shaped" — they are actively, correctly written by the live product today**, via `CommitDecisionFromConclusionService` and `OutcomeService` respectively, both Case-scoped and passing every relevant invariant check. Knowledge Reference, Reasoning Trace, and Judgment remain fully implemented, fully tested, but **zero-caller** in both live orchestrations — confirmed by direct grep: neither orchestrator, nor either composition module, imports `capture_knowledge_reference`, `capture_reasoning_trace`, or `capture_judgment` anywhere.

## 6. Per-Object Legacy Analysis

For each object: current implemented meaning (from code, not name), lifecycle, current role, and canonical correspondence classification (A–E) with evidence.

### 6.1 Question
**Fields**: `id, statement, raised_at, recorded_at, note`. No `case_id`, no upstream reference — the root of the chain.
**Lifecycle**: permanent once captured, immutable, insert-only; not accepted in OE-006's sense (nothing to accept it *into* — it belongs to no invariant-bearing type).
**Role**: user input, pure elicitation trigger for Observation capture. `Statement`'s own `__post_init__` performs no semantic check that the text is actually interrogative.
**Classification: C — workflow-only structure.** A Question asserts nothing; it stages "what am I investigating" so the conversation can proceed to Observation. No governing document requires it to become, or reference, anything canonical. Evidence: no field carries information a canonical object would need beyond what is already captured directly on Observation itself (`observed_at`, `statement`, `subject`).

### 6.2 Interpretation
**Fields**: `id, observation_id (mandatory), statement, interpreted_at, recorded_at, note`. No `case_id`.
**Lifecycle**: permanent, immutable, insert-only. One Observation may have zero, one, or many Interpretations (`list_by_observation_id`, no uniqueness).
**Role**: the investor's subjective reading of "why does this fact matter" — explicitly framed by its own docstring as staging material distinct from a settled characterization, and distinct from Hypothesis (a freestanding belief that may *result* from it).
**Classification: C, with a disclosed B potential.** Interpretation does not itself assert a settled, Case-relative characterization — nothing marks it "accepted" as opposed to "merely offered," and it carries no case_id. It could, in principle, supply raw material for a future Judgment characterizing the Observation it anchors to — but nothing in its current shape or the live flow produces the "settled" moment Judgment's own ontology requires (OE-002 §5.4: "the Case's *settled*... characterization"). Forcing every Interpretation into a Judgment the instant it is captured would misrepresent an offered reading as a settled fact. Not classified as a direct (A) correspondence for this reason.

### 6.3 Hypothesis
**Fields**: `id, statement, formulated_at, recorded_at, note`. No `case_id`, no upstream reference at all — fully standalone by explicit design ("this aggregate is deliberately standalone," entity docstring).
**Lifecycle**: permanent, immutable, insert-only. "Atlas assigns no truth value, confidence, or conviction to a Hypothesis — those are explicitly out of scope" (entity docstring, own words).
**Role**: a freestanding, provisional, unconfirmed belief awaiting Evidence.
**Classification: D — distinct unresolved meaning.** Hypothesis has no subject to characterize (ruling out Judgment's referential form) and, more importantly, is *explicitly, by its own governing text, not settled* — the defining property that would let it correspond to Judgment's internal-content form either. Capturing a Hypothesis as a Judgment at formation time would assert settledness the object itself disclaims. No live event currently marks a Hypothesis "confirmed" as distinct from merely "formed." This is a genuine gap between a *provisional candidate* state and Judgment's *settled* ontology — not a naming coincidence, and not resolved by this investigation. The Historical Decision Record's own Evaluation/Learning-Event finding does not extend to Hypothesis; Hypothesis was never considered in the original OE-002 investigation at all.

### 6.4 Evidence
**Fields**: `id, statement, direction (SUPPORTS|CHALLENGES only), observed_at, recorded_at, source, note`. No `case_id`, no upstream reference — standalone by explicit design.
**Lifecycle**: permanent, immutable, insert-only.
**Role**: "a time-bound record of information the investor considered supportive of or challenging to a line of reasoning. It does not represent objective truth" (entity docstring). `Direction`'s own enum is deliberately restricted to exactly `SUPPORTS`/`CHALLENGES` — explicitly never `PROVES`/`TRUE`/`CONFIRMING` (value-object docstring).
**Classification: B for the `SUPPORTS` subset; D for the `CHALLENGES` subset.** For `SUPPORTS`: Evidence's *role* (material the investor treats as supporting a line of reasoning) is exactly the role Reasoning Trace's supports occupy — but Evidence's raw free-text statement is not itself a reference to an already-accepted, same-Case Domain Object, which is what Reasoning Trace's own ontology (OE-002 §5.3, INV-005) requires of a support. Evidence supplies the raw material; it does not itself become the support until the underlying fact is independently captured as its own canonical object (most plausibly an Observation) and *that object's reference* is what a Reasoning Trace would cite. For `CHALLENGES`: **no canonical type currently represents opposition.** Reasoning Trace's own committed Implementation Design (Section, "Required Contradiction Tests," Test 3) states directly: "Reasoning Trace, as adopted, has no 'undermine' or 'challenge' role at all... a genuine, disclosed scope boundary of the adopted type." This is not this investigation's own invention — it is independently confirmed, pre-existing, disclosed architecture. Reducing `CHALLENGES`-direction Evidence to anything canonical today would require inventing content the adopted ontology does not have. This is flagged as a genuine, disclosed ontology gap (Section 25), not silently worked around.

### 6.5 Conclusion
**Fields**: `id, evidence_id (mandatory), statement, concluded_at, recorded_at, note`. No `case_id`.
**Lifecycle**: permanent, immutable, insert-only. Anchored to *exactly one* Evidence record — its own docstring discloses this is "an explicit, documented implementation simplification... a future increment extending this to multiple Evidence records plus a direct Hypothesis reference is expected, not merely possible."
**Role**: "the output of the reasoning process: what the investor concludes after weighing Evidence." Unlike Hypothesis/Evidence, Conclusion's own docstring does **not** disclaim truth-aptness or settledness — a materially different framing. Operationally, its `statement` is copied directly, verbatim, into `Decision.investment_case` (the `reason` field) at commit time (`orchestrator.py`, `_handle_decision`, `session.conclusion_statement`) — Conclusion's content is *already* treated as settled enough to become part of an accepted Decision's own internal content.
**Classification: B — partial/composite correspondence.** Conclusion supplies exactly the content an optional Judgment could hold (`characterization=Conclusion.statement`, `subject=None` or a reference to the Observation(s) it ultimately traces to). It is not classified A, because nothing in any governing document *requires* every Conclusion to become a separately-accepted Judgment, and the live flow already has a fully legitimate, working path for Conclusion's content (direct absorption into Decision) that requires no change. Whether to *additionally* capture a Judgment from Conclusion is optional value-add (Section 14), not a migration requirement.

## 8. Canonical Acceptance-Point Analysis

**Observation** — already correctly captured, at the `ObserveFromQuestionService` step, immediately once a Question exists. Semantics match OE-002 §5.1 exactly (no truth commitment, case-owned, root-eligible in principle though not root here since Question precedes it operationally — Question is not itself a Domain Object, so this does not violate INV-012). No duplicate or premature capture found — exactly one Observation per conversation, confirmed by `test_observation_step_persists_exactly_the_session_case_id`. **It should remain the first canonical write; no change required.**

**Knowledge Reference** — no live event currently produces a well-formed acceptance point. A Knowledge Reference requires a target that is *already accepted*; the only accepted, same-Case canonical objects available at any point in the current flow are Observation (from step 2 onward) and, later, Decision/Outcome. Evidence, Hypothesis, and Conclusion do **not** supply this event, because none is itself an accepted Domain Object that could be *targeted*. Not all legacy Evidence should become Knowledge References — most Evidence today is candidate material with no existing target identity to point at. A Knowledge Reference could validly be captured **only** where the investor's own material already coincides with an existing accepted object (e.g., "I already recorded this as an Observation; I now also rely on it as knowledge") — a narrow, currently-unexercised case, not a bulk migration target.

**Reasoning Trace** — the live flow already possesses sufficient accepted, same-Case targets (at minimum, the Observation captured at step 2) to validly form a Reasoning Trace with zero narrative invention, at any point from Observation onward. The most natural operational point is **at Decision commitment**, citing the Case's own already-accepted Observation(s) as supports — mirroring exactly how Knowledge Reference/Judgment's own acceptance-time patterns work. `reasoning_link`'s bridges are **not** sufficient input on their own (their non-canonical endpoints cannot be cited), but this does not block Reasoning Trace: the *canonical* endpoints (Observation, and later Decision/Outcome) remain independently citable regardless of whether a bridge link happens to exist alongside them.

**Judgment** — no live event currently produces one. The two closest candidates are Conclusion (pre-Decision) and Evaluation (post-Decision review). Conclusion's content reads more like a settled assessment than Hypothesis's or Evidence's explicitly-disclaimed provisional material, but whether it constitutes "a proposition, a characterization, or both" is genuinely unresolved by any governing text — disclosed as an open question (Section 25), not forced. Evaluation is the cleaner fit (Section 9). The Judgment subject, where used, would be `None` (internal content) for a Conclusion-derived Judgment, or a reference to the Outcome for an Evaluation-derived Judgment.

**Decision** — already correctly written via `CommitDecisionFromConclusionService`, Case-scoped, correct. Current capture is internal-content-only (`subject`+`investment_case` as plain text); no reference to Conclusion or Judgment is held on Decision itself. See Section 19 for the referential-form conclusion.

**Outcome** — already correctly written via `OutcomeService`, Case-scoped (derived from Decision), correct. Evaluation/Learning do not substitute for it — Outcome is genuinely captured as its own canonical object, and Evaluation/Learning are downstream of it, not replacements for it. The event establishing "realized matter" is the investor's own free-text statement at the decision-review Outcome step — already exactly OE-002's internal-content form. See Section 20 for the referential-form conclusion.

## 9. Evaluation and Learning Disposition

Investigated directly, not assumed from the prior Reconciliation Plan's own citation.

**Evaluation** — fields `id, outcome_id (mandatory), statement, evaluated_at, recorded_at, note`; no `case_id`. It characterizes one specific, identified, already-accepted, same-Case object (the Outcome) — this is exactly Judgment's own definition (OE-002 §5.4: "the Case's settled, Case-relative characterization of an identified subject"), in the referential form, with `subject = the Outcome`. It is not truth-apt in an objective sense, but neither is Judgment (OE-002 explicitly: "without asserting that the characterization is objectively true") — this is not a mismatch, it is the same kind of claim. It is not a temporary analysis output; it is captured once, permanently, insert-only, identically to every other legacy aggregate. One Evaluation naturally produces **exactly one** Judgment — its single free-text `statement` gives no basis for splitting into multiple characterizations.

**Disposition selected: partial reduction to Judgment plus non-Core data.** `statement` → `characterization`; `outcome_id` → `subject` (referential, `TypedDomainObjectReference` to the Outcome); acceptance time → `recorded_at`. **`evaluated_at` has no corresponding Judgment field and would be lost if reduced verbatim** — Judgment carries only `recorded_at` (system-clock acceptance time), no separate investor-supplied timestamp. This mirrors exactly the already-disclosed, already-accepted precedent for Decision's own `user_id`/`decision_type`/`confidence`/`source` (DO-REC-008): non-constitutive metadata that may be retained *outside* the canonical Judgment as compatibility context, not silently fabricated a home for inside it. This choice — retain `evaluated_at` as non-Core metadata vs. accept its loss — is an explicit, bounded design decision requiring human sign-off (Section 21, Decision D1), not resolved here.

**Learning** — fields `id, evaluation_id (mandatory), statement, learned_at, recorded_at, note`; no `case_id`. Superficially parallel to Evaluation (anchored, single-statement, timestamped) — **but its content is materially different**: Learning is explicitly a *distilled, generalized, transferable* lesson ("weigh capex guidance more heavily than headline revenue growth" — the actual fixture text used throughout its own test suite), not a characterization of one specific identified same-Case object. Its nominal anchor, `evaluation_id`, points at Evaluation — which is not itself a canonical Domain Object today, so Learning cannot use it as a Judgment `subject` reference *unless* Evaluation is reduced to a Judgment first (a genuine, disclosed sequencing dependency: Learning's own reduction is contingent on Evaluation's).

**Disposition selected: remain as a non-Core workflow/analysis structure, primarily** — with a disclosed, secondary, contingent alternative. Learning's whole purpose is a general, portable heuristic, not a Case-relative characterization of one identified thing; forcing it into Judgment's "characterization of an identified subject" shape stretches that ontology to cover something it was not built for, which this investigation declines to do without a genuine forcing function (none was found). The secondary alternative — a Judgment referencing the Judgment Evaluation became (`subject = that Judgment`, `characterization = Learning.statement`) — is architecturally *valid* (nothing in OE-002 §5.4 forbids a Judgment's subject from being another Judgment) and remains available if a future decision favors making Learning a permanent, referenceable Case fact instead of ephemeral Lab/analytics data. **This choice is itself an open, bounded design decision (Section 21, Decision D2), not forced by this investigation either way** — same pattern would not automatically apply the same disposition; Evaluation and Learning genuinely differ despite their structural similarity, exactly the caution this task's own instructions required.

## 10. `reasoning_link` Disposition

All four bridge types (`QuestionObservationLink`, `InterpretationHypothesisLink`, `HypothesisEvidenceLink`, `ConclusionDecisionLink`) share one exact shape: `(link_id, source_id, target_id, linked_at)` — no content field, no ordering/sequence field beyond the timestamp itself, strictly append-only (no update/delete anywhere), and record *support/derivation only in the loosest structural sense* — they record that one step's output fed the next step's input, not epistemic support in Reasoning Trace's own technical sense. `linked_at` is not semantic ordering; it is simply when the bridge was recorded. **Corrected by this audit — precision on "duplicates permitted":** `tests/unit/infrastructure/persistence/reasoning_link/test_sqlalchemy_repository.py`'s `test_all_four_tables_have_no_unique_constraint` confirms, at the schema level, that no column on any of the four tables is marked unique — this is genuine, verified evidence of permissiveness. However, no test in that suite inserts the literal identical `(source_id, target_id)` pair twice; the existing multi-link tests (`test_multiple_links_for_the_same_question_are_all_returned` and its analogs) vary the *other* endpoint per call, demonstrating fan-out from one shared endpoint, not a same-pair duplicate insert. The original draft's "explicitly permitted and tested" therefore overstated the test evidence: duplicate permission is established by the *absence* of a uniqueness constraint (a real, confirmed fact), not by a test that exercises inserting one identical pair twice.

None of the four is reducible to a Reasoning Trace support set directly: Reasoning Trace requires each support to already be an accepted, same-Case canonical Domain Object, and three of the four links' non-canonical endpoint (Interpretation, Hypothesis, Evidence, Conclusion) fails that requirement. The one link whose *target* is canonical (`ConclusionDecisionLink` → Decision) still does not need to become a Reasoning Trace itself — a Reasoning Trace citing the Case's own accepted Observation(s) can be captured entirely independently of whether this link exists, using the canonical objects directly (Section 8). No single link, and no combination of links, "jointly forms" a Reasoning Trace under current ontology, because a Reasoning Trace's *own* construction depends only on which already-accepted objects are cited as supports — not on any bridge-table row existing at all.

**Classification for all four: C — temporary migration input at most, permanent non-Core workflow structure in the meantime.** None is obsolete today (all four remain actively used, tested, and load-bearing for their own stated bridging purpose); each becomes a candidate for retirement only if and when the legacy type on its non-canonical side is itself given a canonical disposition — a decision this investigation explicitly does not make (consistent with `Reasoning-Trace-Implementation-Design.md`'s own disclosed deferral of `reasoning_link`'s ultimate disposition, DO-REC-019). This is **not** simply renaming `reasoning_link` to Reasoning Trace — the two remain structurally and semantically distinct: `reasoning_link` records step-to-step derivation with no content of its own; Reasoning Trace records a positive, accepted, same-Case support relation for an already-permanent record.

## 11. Complete Live-Flow Trace

Traced directly, by reading every file in the chain (not by test inspection alone).

1. **Question** — `QuestionService.capture()`. Writes `Question` (no case_id). No Case check. Not accepted in OE-006's sense (no invariant governs it).
2. **Observation** — `ObserveFromQuestionService.observe()`. Verifies Question exists (read-only). Delegates to unmodified `CaptureObservationService.capture(case_id=session.case_id, ...)`. Writes canonical `Observation` (case-owned, INV-002/004/005/007/008/009/015 all satisfiable and satisfied). Also writes `QuestionObservationLink` (no case_id; pure bridge). **Canonical write: yes.**
3. **Interpretation** — `InterpretationService.capture()`. Verifies Observation exists (read-only, raises local `ObservationNotFoundError`). Writes `Interpretation` (no case_id). No canonical write.
4. **Hypothesis** — `FormHypothesisFromInterpretationService.form()`. Verifies Interpretation exists. Delegates to unmodified `HypothesisService.capture()`. Writes standalone `Hypothesis` (no case_id, no upstream reference at all). Writes `InterpretationHypothesisLink`. No canonical write.
5. **Evidence** — `CaptureEvidenceFromHypothesisService.capture()`. Verifies Hypothesis exists. Delegates to unmodified `EvidenceService.capture()`. Writes standalone `Evidence` (no case_id). Writes `HypothesisEvidenceLink`. No canonical write.
6. **Conclusion** — `ConclusionService.capture()`. Verifies Evidence exists (reuses `EvidenceNotFoundError`). Writes `Conclusion` (no case_id, anchored to exactly one Evidence). No canonical write; but its `statement` is captured in `session.conclusion_statement` for reuse at step 7.
7. **Decision** — `CommitDecisionFromConclusionService.commit()`. Verifies Conclusion exists. Delegates to unmodified `CaptureDecisionService.capture(case_id=session.case_id, subject=session.observation_subject, reason=session.conclusion_statement, ...)`. Writes canonical `Decision` (case-owned, every relevant invariant satisfied). Writes `ConclusionDecisionLink`. **Canonical write: yes.** Conversation terminates here (`DECISION_RECORDED`).
8. **Outcome** (separate flow, `decision_review`, triggered by selecting an existing Decision) — `OutcomeService.capture()`. Verifies Decision exists (read-only). Derives `case_id = decision.case_id`. Writes canonical `Outcome`. **Canonical write: yes.**
9. **Evaluation** — `EvaluationService.capture()`. Verifies Outcome exists. Writes `Evaluation` (no case_id, anchored to Outcome). No canonical write today.
10. **Learning** — `LearningService.capture()`. Verifies Evaluation exists. Writes `Learning` (no case_id, anchored to Evaluation; terminal node — nothing consumes it further except read-only `decision_timeline`). No canonical write today.

Every "verify exists" check across all ten steps is a **pure, read-only lookup** performed *before* any write; every composite service is proven, by its own dedicated negative test, to write nothing to either repository when the upstream check fails (`TestNegativeCasesNothingIsWrittenOnFailure`, ten cases, one per step). No step mutates a previously-written object. No Case is available at all for steps 1, 3–6, 9–10; Case is available and correctly propagated at steps 2, 7, 8.

## 13. Candidate Migration Strategies

**Candidate 1 — Dual write.** Legacy flow remains fully operational; canonical writes (Reasoning Trace at Decision commitment; Judgment from Evaluation, and optionally from Conclusion) are added *alongside* it, in the same request/response cycle, using already-accepted data with no narrative invention. *Safety*: high — nothing existing is removed or altered; every current test remains valid unchanged. *Consistency risk*: low — the new writes derive their content entirely from data the legacy writes already produced and verified exists (an accepted Outcome, an accepted Observation); there is no independent source of truth to diverge from. *Transactional boundaries*: the new writes are simple additive calls, following the exact same "verify read-only, then write" pattern already used throughout; they can share the same request without requiring new cross-service transaction machinery. *Duplicate authority*: none — the canonical write does not compete with the legacy write, since neither is authoritative over the same fact; the legacy write is authoritative for "the conversational step occurred as recorded," the canonical write is authoritative for "this specific characterization/support is now a permanent, Case-owned Domain Object." *Rollback*: trivial — deleting the new call sites removes the canonical write path entirely, leaving the legacy flow exactly as it is today. *Divergence*: none possible, since the canonical write is a pure function of already-accepted legacy data at the moment of capture, not an independently-maintained copy. *Migration duration*: unbounded — can run indefinitely with no forcing deadline. *Testability*: high — every new write is independently, narrowly testable exactly like every existing composite service.

**Candidate 2 — Canonical write with legacy projection.** Canonical objects become authoritative; legacy objects (Conclusion, Evaluation, etc.) are generated or derived *from* the canonical write, rather than the reverse. *Safety*: lower — this **inverts** an operational dependency that currently runs the other way (Decision's own `reason` field is populated *from* Conclusion today; making Conclusion a projection of a canonical Judgment would require restructuring the orchestrator's own data flow, not merely adding a call). *Consistency risk*: higher — a projection must be kept in lockstep with its canonical source by construction; any drift in the projection logic silently produces a legacy record that misrepresents the canonical fact. *Transactional boundaries*: would require the canonical write to happen *first*, which is not how the current flow is sequenced (Conclusion happens before Decision, not after a Judgment). *Duplicate authority*: avoided by design (canonical is sole authority) — the one genuine advantage of this candidate. *Rollback*: harder — reversing would mean un-inverting the data-flow direction across multiple orchestrator methods. *Divergence*: low if implemented correctly, but the implementation itself is materially riskier than Candidate 1. *Migration duration*: requires a coordinated cutover of the orchestrator's own internal sequencing. *Testability*: lower — requires rewriting, not merely extending, the existing, currently-green test suite for the affected steps. **Rejected as the primary strategy**: disproportionate risk and required restructuring relative to Candidate 1, for the same eventual benefit, given no live external consumer currently depends on the legacy shape being authoritative.

**Candidate 3 — Direct replacement.** Legacy capture (Conclusion, Evaluation, Learning, and the four bridges) is removed; orchestrators write directly to Judgment/Reasoning Trace/Knowledge Reference. *Safety*: lowest of the three — removes Conclusion's own load-bearing role feeding `Decision.investment_case` without a replacement mechanism already built (Decision's own referential form is not implemented — Section 19), and removes Learning's role entirely without first resolving its disclosed, still-open disposition (Section 9). *Consistency risk*: N/A (single representation) but only after the disposition of every affected legacy type is actually settled — which several are not (Hypothesis, Evidence-CHALLENGES, Learning). *Rollback*: none — this is destructive; reverting means re-implementing removed code from history. *Migration duration*: requires all open decisions (Section 21) resolved *before* any code is written, since there is no fallback once legacy capture is removed. *Testability*: requires a full rewrite of the conversation and decision-review test suites, not an addition. **Rejected**: several of the four Section 21 design decisions are not yet resolved, and OE-002's own Doctrine-level minimality discipline counsels against removing a still-working, still-tested mechanism before its replacement is proven — disproportionate risk for no compensating benefit at this stage.

## 14. Selected Strategy

**Candidate 1 — Dual write, narrowly scoped.** Not a wholesale duplication of the entire flow (most legacy types have no canonical counterpart to dual-write into at all — Question, Interpretation, Hypothesis, Evidence remain exactly as they are, Classification C/D, no change proposed). Scoped to exactly two additive write points: (a) a Reasoning Trace citing the Case's own accepted Observation(s), captured alongside Decision commitment; (b) a Judgment derived from Evaluation (and, optionally, from Conclusion), captured alongside the existing legacy Evaluation/Conclusion capture. Both are pure additions requiring no change to any existing entity, table, or test.

## 15. System-of-Record Model by Phase

**Phase 0 (current state)**: Legacy objects are sole authority for the fact "this conversational/review step occurred and produced this content." Observation, Decision, Outcome are already canonical-authoritative for their own facts (no legacy shadow exists for these three — they are written once, directly, as canonical objects; there is no separate "legacy Observation" competing with them). No dual authority exists anywhere today, because nothing yet writes both a legacy and a canonical representation of the same fact.

**Phase 1 (after the recommended dual-write packages, Section 21 — corrected by this audit; the original draft misattributed this to Section 17, which is API Lifecycle, not the packages)**: For Reasoning Trace and Judgment specifically, **two representations of related-but-distinct facts** begin to coexist: the legacy Conclusion/Evaluation record remains authoritative for "the investor's own reasoning/assessment text, verbatim, as originally captured" (this never changes); the new canonical Judgment/Reasoning Trace becomes authoritative for "this is now a permanent, Case-owned, independently-referenceable accepted fact." Neither is *advisory* (a non-binding hint) and neither is a *shadow* of the other (a passive mirror kept only for comparison) — each is **co-authoritative, but over a different, non-overlapping fact**: the legacy write is the sole authority for conversational/review content as originally entered; the canonical write is the sole authority for whether a canonical Domain Object exists for that content. Neither can supersede the other because neither asserts the other's fact.

**Corrected by this audit — precise failure model, required for any implementer, not previously stated with this precision.** The legacy write always happens first and is never made conditional on the canonical write's success (Section 21's packages both add the canonical write strictly after the legacy step has already completed). This has one consequence the original draft did not surface: **if the canonical write is placed inside the same `try`/`except` block as the legacy write** — as a literal reading of "add a call after the existing commit succeeds" could permit — **a canonical-write failure re-enters the existing bare `except Exception:` handler and reprompts the investor at the same conversational step**, exactly as the orchestrator already does for the legacy write's own failures (Section 23's prior finding). Because the legacy write already succeeded before the canonical write was attempted, and the reprompt does not advance `session`/`session`-equivalent state, a subsequent answer **re-invokes the legacy write a second time**, producing a **second, permanent, duplicate legacy object** (a second Decision for M1, a second Evaluation for M2) — not a duplicate canonical object. This is a genuine, previously-undisclosed risk this audit identified by direct inspection of `orchestrator.py`'s `_handle_decision` and `decision_review/orchestrator.py`'s `_handle_evaluation`, both of which transition session state (`session.pending.clear()`/`session.decision_id=...`/`session.current_step=...` for M1; `session.evaluation_id=...`/`session.current_step=...` for M2) only after their own try block, with nothing currently following that transition.

**Required implementation discipline, stated here so no future implementer has to rediscover it**: the canonical write MUST be placed strictly *after* the legacy step's own terminal state transition, in its **own**, separate `try`/`except` that does not reprompt on failure — it logs and the turn still reports success to the investor. Under this discipline, the canonical write is never retried by construction (there is no code path that re-attempts it), so **no duplicate canonical object can ever arise** — the canonical write is inherently **at-most-once**, not **at-least-once**. The direct consequence, stated plainly rather than left implicit: a canonical-write failure is **not automatically detected or repaired by the running system** — it produces a permanent, silent gap between "a legacy record exists" and "no canonical record exists for it," discoverable only by an out-of-band audit (e.g., a script comparing legacy Decision/Evaluation counts against canonical Reasoning Trace/Judgment counts for the same Case), never by the application itself. This is an accepted, disclosed cost of the narrow dual-write strategy (Section 14), not a defect to silently work around — no idempotency key or retry mechanism is introduced, because none is needed once the canonical write is never retried.

No shared database transaction is required across the legacy and canonical writes (Section 13's own "transactional boundaries" analysis) — a failure of the canonical write after a successful legacy write leaves the legacy record intact and simply omits the (additive, non-blocking) canonical fact, exactly the soft-fail behavior above, logged, not silently ignored.

**Phase 2 (a future, separately-authorized decision, not made here)**: whether legacy Conclusion/Evaluation capture is ever removed in favor of canonical-only capture is Candidate 3's own territory (Section 13) and remains explicitly out of scope for this investigation's own recommended next step.

Read paths: today, every read path (decision_timeline, decision_review's own lookup) consumes **legacy** data exclusively. After Phase 1, canonical Judgment/Reasoning Trace data becomes available for reading but nothing in the existing read paths is required to consume it — new read paths (e.g., a future Reasoning Trace or Judgment listing) would be additive, not a replacement of existing ones. No existing read path is retargeted by this investigation.

## 17. API Lifecycle

Current side-by-side exposure (`app.py`): mounted legacy routers — `hypothesis`, `evidence`; mounted canonical routers — `case`, `decision`, `decision_context`, `observation`, `knowledge_reference`, `judgment`, `reasoning_trace`. No router exists for Question, Interpretation, Conclusion, Evaluation, or Learning (none of these five is API-exposed at all — only Hypothesis and Evidence, of the seven legacy types, have REST endpoints, both narrow — capture/list/get, no update/delete/patch). No canonical Outcome API exists (already disclosed, deliberate, per the Foundation Review).

Which legacy endpoints are used by the product: `hypothesis`/`evidence` are the two legacy types exposed at all, but the *live product flow itself* (both orchestrators) never calls these HTTP endpoints — it constructs the underlying application services directly, in-process. **Strengthened by this audit's own repository-wide search**: a search across the entire repository — every `scripts/*.sh`, every `README`/`docs/*.md` outside this architecture track, and every Python module outside the `hypothesis`/`evidence` modules' own files and their own tests — found zero references to `/hypotheses` or `/evidence` as endpoints a caller invokes; the only textual matches were prose documentation (`docs/HypothesisCaptureAPI004.md`, `docs/EvidenceCaptureAPI005.md`) and one unrelated code comment listing domain-table names, not an endpoint call. This is materially stronger evidence than "no evidence was found" — it is a completed, systematic search with a negative result. It still cannot rule out a caller entirely outside this repository (a separate deployed client, an external integration never checked into this codebase), which no repository search can ever settle; that residual uncertainty is why D4 (Section 25) remains open rather than closed by this finding, not because the repository-internal question itself remains unresolved. Canonical endpoints (`/knowledge-references`, `/judgments`, `/reasoning-traces`) are currently used by nothing — not the product, not (as far as repository evidence shows) any external caller — they exist purely as a tested, correct, unconsumed surface.

A caller **can** currently mistake a legacy object for a canonically accepted fact: `POST /hypotheses` and `POST /evidence` return 201-with-object responses structurally similar in shape to the canonical endpoints' own responses (an id, a statement, timestamps), with nothing in the response body itself marking the object as outside OE-002's closed six-type set.

**Proposed endpoint lifecycle** (a proposal, not an action taken by this investigation): `/hypotheses`, `/evidence` → **mark internal / candidate for deprecation notice**, since neither is currently consumed by the live product's own orchestration and both represent types this investigation classifies D (Hypothesis) or B/D (Evidence); `/knowledge-references`, `/judgments`, `/reasoning-traces` → **retain, and treat as the intended long-term product surface** once the dual-write packages (**corrected by this audit — the packages are in Section 21, "Exact Migration Packages," not Section 22, which covers sequencing only**) begin populating them; `/observations`, `/decisions`, `/cases` → **retain unchanged**, already correctly the canonical, live surface. No route is removed by this investigation.

## 23. Risks and Rollback Boundaries

**Sharpened by this audit — the single most consequential risk in this document.** Both orchestrators' uniform bare `try/except Exception:` per step (already disclosed by the prior Case-Context investigation) does not merely risk masking a canonical-write defect as a silent re-prompt — if the canonical write is placed inside the *same* `try` block as the already-succeeded legacy write, a canonical-write failure re-enters that handler and invites a retry that **re-invokes the legacy write itself**, producing a duplicate, permanent legacy Domain Object (a second Decision, a second Evaluation) that INV-009's permanence then makes impossible to undo. This is not a hypothetical: it follows directly from `_handle_decision`'s and `_handle_evaluation`'s own current structure (Section 15), where session-state advancement happens only after the try block succeeds, with nothing currently positioned after it. Section 15 and Section 21 both now state the required fix precisely — the canonical write lives in its own, separate, non-reprompting `try`/`except`, strictly after the legacy step's terminal state transition — and this must be treated as a mandatory implementation constraint for M1 and M2, not an optional refinement. Under that discipline, the remaining, accepted risk is narrower and already disclosed: a logged, non-retried canonical-write failure produces a permanent legacy-only record with no canonical counterpart, detectable only by out-of-band audit (Section 15). Every package's rollback boundary remains a single new call site or additive field, matching the smallest-safe-package discipline already established and proven by every prior canonical Domain Object package in this codebase's own history.
