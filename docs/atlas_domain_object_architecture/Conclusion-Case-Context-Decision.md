# Conclusion Case Context — Decision (Bounded Decision D3)

This document is an investigation-and-design artifact, not a normative document. It carries no Doctrine status (Draft/Final/Superseded/Historical) because those statuses apply to normative documents, and this is not one. It implements nothing, modifies no existing production file, test, or governing document. Where anything here appears to conflict with the Architecture Doctrine, OE-002 through OE-006, or the Historical Decision Record, those documents govern and this one is wrong and must be corrected.

## 1. Executive Finding

**Conclusion does not require `case_id`, and Package M3 (Conclusion Case propagation) should be retired, not implemented.** Conclusion is not, and under OE-002 §4's closed Domain Object Set can never become, a canonical Domain Object — this was already established by the Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md and independently reconfirmed here at the field, runtime, and test-evidence level. Case is already correctly and completely available at the one place it is actually needed — Decision commitment — via `ConversationSession.case_id`, threaded directly into `CommitDecisionFromConclusionRequest.case_id`, entirely independent of Conclusion. No downstream consumer of Conclusion reads or needs Case. No invariant requires it (INV-002 does not apply to non-Domain-Objects). No remaining canonical migration package requires it — a hypothetical future Judgment-from-Conclusion package would derive Case exactly the way Package M2 derived it for Judgment-from-Evaluation: from an already-Case-owned canonical object in Conclusion's own vicinity, never from Conclusion itself.

A genuine, concrete cross-Case mismatch **is** constructible — `CommitDecisionFromConclusionService.commit()` performs zero validation connecting its supplied `case_id` to the Conclusion it commits, a fact directly proven by an existing, currently-passing test that deliberately supplies an unrelated, freshly-generated `case_id` and asserts success. But this mismatch is **not reachable through the live product's own public interface** — `ConversationSession.case_id` is set exactly once, at session construction, and is never reassigned anywhere in the orchestrator; `session.conclusion_id` is set exactly once, from a Conclusion captured within that same session's own linear chain. Reaching the mismatch requires bypassing the orchestrator and calling the application service directly — the same "vulnerability" every unvalidated composite service in this codebase already has, not something specific to Conclusion.

Adding `case_id` to Conclusion would not change its ontological status (OE-002 §4's set is closed; Conclusion would still not be a Domain Object) — it would only add a column that falsely signals canonical Case ownership where none exists, and would be motivated by symmetry with Observation/Decision/Outcome/Judgment, not by any demonstrated invariant, consumer need, or migration requirement.

**Required conclusion: B — Keep Conclusion unchanged and retire M3.**

## 2. Scope

This document resolves bounded decision D3: whether legacy Conclusion requires explicit Case context. It does not implement `case_id` on Conclusion or any change to Conclusion, Decision, Reasoning Trace, or Observation. It does not implement Knowledge Reference or historical backfill. It does not begin D4. It creates exactly one new file: this document.

## 4. Current Conclusion Meaning

`atlas/core/domain/conclusion/entity.py`: **"Conclusion is the output of the reasoning process: what the investor concludes after weighing Evidence."** Its own docstring discloses, verbatim: "for ATLAS-001, it is anchored to a single Evidence record (`evidence_id`) as an explicit, documented implementation simplification... A future increment extending this to multiple Evidence records plus a direct Hypothesis reference is expected, not merely possible." Conclusion is immutable, insert-only, and references Evidence only by id, read-only.

**Selected candidate: A — a provisional synthesis.** Conclusion is a workflow-produced synthesis that supports later Decision commitment but is not itself an accepted canonical fact. Evidence for this selection: (1) its own content is copied verbatim into `Decision.investment_case` at commit time (`orchestrator.py`, `_handle_decision`, `reason=session.conclusion_statement`) — Conclusion supplies raw material absorbed into Decision's own internal content, not a separately-referenced accepted fact; (2) nothing in the live product ever reads a Conclusion again after Decision commits — it has no read path, no API, no downstream consumer beyond the one composite service that consumes it once; (3) it is never cited by Reasoning Trace (M1) or Judgment (M2), both of which draw exclusively from the closed `DomainObjectType` enum, which has no member for Conclusion at all.

**Candidate B (an accepted proposition that should itself be Case-owned)** is rejected: nothing treats Conclusion as a standing, independently-referenceable fact of record; it is consumed once and never revisited.
**Candidate C (a Decision draft)** is rejected as too narrow: Conclusion's content becomes part of Decision, but Conclusion itself remains a permanent, immutable row with its own independent identity and timestamps — it is not discarded or superseded the way a "draft" concept implies.
**Candidate D (a workflow checkpoint with no independent proposition semantics)** is rejected: Conclusion does carry genuine semantic content (a complete natural-language statement, independently readable), not merely a stage-completion flag.
**Candidate E (a reasoning result corresponding to Reasoning Trace plus another canonical object)** is rejected: Reasoning Trace's own adopted ontology has no opposition or narrative-support role beyond citing already-accepted Domain Objects by type, and Conclusion is categorically ineligible as such a citation (Section 12). Whether Conclusion's content could ever separately seed an *optional* Judgment is a distinct question already addressed, and left open, by the Legacy Core Loop investigation's own D3-adjacent sibling questions — not resolved or reopened here.

**Direct answers to every central semantic question this audit requires, verified fresh rather than assumed:**

1. **What exact fact does a Conclusion record?** The investor's own free-text answer to "Given everything so far, what's your takeaway?" — captured verbatim, no interpretation applied.
2. **Is its statement generated, user-authored, or derived?** User-authored — `Statement(request.statement)` wraps the investor's own raw text; nothing in `ConclusionService.capture()` or `Conclusion.capture()` generates or transforms content beyond `.strip()`.
3. **Is it presented to the user as final?** No explicit confirmation step exists — the orchestrator moves directly from the Conclusion answer to `DECISION_TYPE_PROMPT` with no "is this your final takeaway?" checkpoint. Finality is implicit in the workflow's own forward-only structure (below), not asserted to the user.
4. **Is it accepted under OE-002?** No — OE-006's acceptance model applies only to Domain Objects (Section 3); Conclusion is not one, so "acceptance" in that technical sense does not apply to it at all, only ordinary, permanent storage.
5. **Is it independently truth-apt?** Genuinely ambiguous, and **not previously disclosed in this document** — corrected here. Unlike Hypothesis's own docstring ("Atlas assigns no truth value, confidence, or conviction to a Hypothesis") and Evidence's own docstring ("does not represent objective truth"), Conclusion's own docstring contains **no comparable truth-disclaiming language**. This is a real, disclosed asymmetry among the three standalone legacy types — but it bears on Conclusion's own *content classification* (Candidate A vs. B, above), not on Case ownership: even a Conclusion read as a more settled, truth-apt statement is not thereby a member of OE-002 §4's closed Domain Object Set, and set membership, not surface tone, is what governs Case ownership (Section 18). This nuance does not change the selected Candidate A, since nothing in the live product treats Conclusion as a standing, re-referenceable fact regardless of its tone (Section 15).
6. **Is it mutable?** No — frozen dataclass, insert-only repository, confirmed directly (Section 6).
7. **Can it be replaced before Decision commitment, within the same conversation?** No — `_HANDLERS` is a fixed dictionary keyed by `current_step`; once `_handle_conclusion` succeeds and advances `session.current_step` to `DECISION`, no code path returns to the `CONCLUSION` step for that session. A different conclusion requires an entirely new conversation (and hence a new Conclusion row), never an in-place revision of the existing one.
8. **Does its persistence imply acceptance?** No, per answer 4 — persistence here means only "permanently stored, insert-only," identical to Question/Interpretation/Hypothesis/Evidence/Evaluation/Learning, none of which is OE-006-accepted either.
9. **Does Decision copy its content directly?** Yes — verbatim, confirmed in Section 7.
10. **Does the committed Decision preserve all Conclusion meaning?** **No — corrected here, not previously stated explicitly.** Only `statement` is copied into `Decision.investment_case`. Conclusion's own `id`, `recorded_at`, and `concluded_at` are not preserved anywhere on Decision (Decision has its own, independently supplied `decided_at`, sourced from a separate `_now()` call at the Decision step, not from Conclusion's own `concluded_at`); `note`, though unused in the live flow, would also not transfer if ever populated. The Conclusion row remains the sole permanent record of its own exact timing and identity.
11. **Does any consumer treat Conclusion as a permanent authoritative proposition?** No — confirmed by the downstream-consumer search (Section 15): nothing reads Conclusion again after Decision commits.
12. **Does Conclusion have a stable meaning outside the workflow that created it?** Its text is independently readable as a complete natural-language statement, but its *institutional* role — what makes it exist at all — is entirely tied to feeding one specific Decision commitment; it has no standing, referenceable identity apart from that role (consistent with the Candidate A selection above).

## 6. Current Runtime Lifecycle

Conclusion is captured exactly once per conversation, by `ConclusionService.capture()` (`atlas/core/application/conclusion/capture_conclusion.py`), invoked from `ConversationOrchestrator._handle_conclusion`. It is never updated, never deleted, and — confirmed directly — never re-read by any component other than `CommitDecisionFromConclusionService`, which reads it exactly once (to verify existence) before constructing Decision. It is immutable from the moment of capture (frozen dataclass; insert-only repository). It is not "provisional" in the sense of being later revised in place — a changed mind produces an entirely new conversation, never a mutation of the existing row (identical to every other legacy Core Loop aggregate in this codebase). It has exactly one Evidence upstream (mandatory `evidence_id`) and, in the live orchestrator, exactly one Decision downstream (the single `ConclusionDecisionLink` written by `CommitDecisionFromConclusionService.commit()` in the same call that commits the Decision) — though the `ConclusionDecisionLinkRepository` Protocol itself imposes no uniqueness constraint, so nothing at the schema level forbids a second, independent composite call from linking the same Conclusion to a second Decision; the live orchestrator simply never does this, since a conversation reaches its terminal `DECISION_RECORDED` state after exactly one such call.

## 7. Decision Commitment Trace

Traced directly from `atlas/core/application/conversation/orchestrator.py` and `atlas/core/application/reasoning_link/commit_decision_from_conclusion.py`.

1. **Conclusion creation** (`_handle_conclusion`) — `ConclusionService.capture(CaptureConclusionRequest(evidence_id=session.evidence_id, statement=answer, concluded_at=_now()))`. Case is **not** passed and not needed — Conclusion has no field for it.
2. **Conclusion ID storage** — `session.conclusion_id = conclusion.id.value`; `session.conclusion_statement = answer` is also cached, in-memory only, for reuse at step 4.
3. **Decision input** — the investor supplies `decision_type` and `confidence` at the `DECISION` step; `session.observation_subject` and `session.conclusion_statement`, both cached earlier, default `subject`/`reason` without re-asking.
4. **`CommitDecisionFromConclusionService.commit()`** — receives `CommitDecisionFromConclusionRequest(case_id=session.case_id, conclusion_id=session.conclusion_id, user_id=..., decision_type=..., subject=session.observation_subject, reason=session.conclusion_statement, confidence=..., decided_at=_now())`. Verifies the Conclusion exists (read-only). **Both `case_id` and `conclusion_id` are read from the same `ConversationSession` instance, independently of each other** — `case_id` is never derived from, or checked against, the Conclusion.
5. **Canonical Decision capture** — delegates, unmodified, to `CaptureDecisionService.capture(CaptureDecisionRequest(case_id=request.case_id, ..., reason=request.reason, ...))`. Decision's `investment_case` field receives Conclusion's own `statement` text **verbatim, by direct copy** — not generated, not combined with any other input beyond the plain string assignment.
6. **`ConclusionDecisionLink`** is captured in the same call (`link = ConclusionDecisionLink.capture(conclusion_id=conclusion_id, decision_id=decision.id)`), a pure `(link_id, conclusion_id, decision_id, linked_at)` bridge record with no `case_id` of its own.
7. **Terminal state** — `session.current_step = ConversationStep.DECISION_RECORDED`.
8. **M1 Reasoning Trace capture** — occurs strictly after the terminal transition, citing only `session.observation_id` (Section 12) — Conclusion plays no role in this step whatsoever.

**Decision content is copied from Conclusion, verbatim, not generated or combined with other input.** Conclusion Case context would change **no** Decision invariant: Decision already receives its own `case_id` independently, from the same session field Conclusion's own commit request also reads — adding `case_id` to Conclusion would be redundant with, not corrective of, this existing path.

## 8. Current Case Availability

Case is fully, correctly available at the only point it is needed (step 4 above) via `session.case_id` — confirmed directly: `ConversationSession.case_id` is a required, no-default field, set exactly once at `ConversationOrchestrator.start()` (`ConversationSession(case_id=self._case_id)`), and a repository-wide search (`grep -n "session.case_id\s*="`) confirms it is **never reassigned anywhere** in the orchestrator. No consumer of Conclusion currently needs direct Case access — the one and only consumer (`CommitDecisionFromConclusionService`) already receives Case from an independent, authoritative source (the session), not from Conclusion.

**Three distinct claims, stated separately per this audit's own requirement, not collapsed into one:** (a) **Repository fact** — the field exists, is required, has no default, and is never reassigned anywhere in `orchestrator.py`'s own source (a static, code-level fact, independent of any particular run). (b) **Public-flow guarantee** — for every conversation driven through the orchestrator's own `start()`/`respond()` interface (the only way the live CLI or any ordinary caller drives it), the same session object supplies both `case_id` and `conclusion_id` together, so they are always coherent by construction — this is a guarantee about the *product's own intended interface*, not about the underlying service. (c) **Internal-service limitation** — `CommitDecisionFromConclusionService.commit()` itself performs no check connecting the two values; the guarantee in (b) holds only because of how the orchestrator happens to call it, not because the service enforces anything (Section 10 develops this precisely). `ConversationSession` is **in-memory only, never persisted, never externally supplied except as a plain constructor call, and never validated against any canonical object** — it is trusted application-boundary state, exactly as `session.py`'s own docstring discloses ("deliberately NOT a domain aggregate... not persisted"). Decision commitment (step 4) and Conclusion capture (step 1) both read `case_id` from this same object; M1's Reasoning Trace capture (Section 12) reads `session.case_id` and `session.observation_id` from the identical object, after the terminal transition — the same single Case value is used throughout one successful flow, confirmed end-to-end, not merely at one isolated point.

## 9. Pre-Decision Case Requirements

Inspected: validation, retries, reprompts, persistence, audit logging, cross-conversation queries, cleanup, authorization, multi-tenant isolation, analytics, failure recovery — none of these currently reads or requires Conclusion's Case before Decision commitment. `_handle_conclusion`'s own retry/reprompt boundary (a bare `try/except Exception:` that re-asks `CONCLUSION_PROMPT` on failure) never touches Case at all; Conclusion capture succeeds or fails purely on Evidence existence and statement non-emptiness.

**Can a Conclusion from one conversation accidentally be committed into another Case?** Structurally, at the application-service layer, yes — nothing in `CommitDecisionFromConclusionService.commit()` checks that the supplied `case_id` relates to the supplied `conclusion_id` in any way. **What currently prevents that?** Only the orchestrator's own single-session discipline (Section 8): both values are read from the same `ConversationSession` object, and nothing in the orchestrator's own public interface (`start()`, `respond()`) allows swapping one without the other. **Does `CommitDecisionFromConclusionService` receive both Conclusion and Case independently?** Yes — confirmed directly in Section 7, step 4: `case_id` and `conclusion_id` are two independent constructor arguments on the same request object, sourced from the same session field, but never cross-validated against each other by the service itself. **Does it validate that Conclusion belongs to that Case?** No. **Is there currently any persisted fact capable of proving such belonging?** Not directly — Conclusion carries no Case reference of its own; a *derived* proof is possible only via the multi-hop join chain described in Section 11, Model 3, which is not attempted anywhere in this codebase today. **Is the lack of proof a real invariant gap or an accepted legacy-workflow limitation?** The latter — Conclusion is not a Domain Object (Section 3), so INV-002 (single Case ownership) does not apply to it at all; there is no invariant for this to be "missing" against. This is the same accepted limitation that already applies, identically, to Question, Interpretation, Hypothesis, and Evidence, none of which carry Case either.

## 10. Cross-Conversation Contamination Analysis

Six scenarios tested:

1. **Conclusion created in conversation A, committed with Case B, via the live orchestrator.** **Impossible by API/type structure** — the orchestrator's `_handle_decision` always reads both `case_id` and `conclusion_id` from the same `session` argument passed to `respond()`; there is no orchestrator-level operation that accepts a foreign `conclusion_id` or a replacement `case_id` mid-session.
2. **Session object reconstructed with mismatched Conclusion and Case.** **Possible only through internal misuse** — `ConversationSession` is a plain, mutable dataclass (deliberately not a domain aggregate); nothing prevents a caller who imports it directly from constructing `ConversationSession(case_id=X, conclusion_id=Y)` with unrelated values and passing it to `orchestrator.respond()`. This requires writing Python code that manually assembles session state — not reachable through the CLI's own `input()`/`print()` loop, which only ever holds the one session object `orchestrator.start()` returned.
3. **Conclusion ID manually supplied to a composite from another conversation.** **Possible only through internal misuse** — directly demonstrated by the existing test `test_propagates_exactly_the_requests_case_id_unchanged` (`tests/unit/application/reasoning_link/test_commit_decision_from_conclusion.py`), which constructs `CommitDecisionFromConclusionRequest` with a freshly-generated, unrelated `case_id` and an `existing_conclusion` fixture, and asserts the commit succeeds — this is the service's own test suite treating this as **correct, intended behavior**, not a bug being guarded against.
4. **Repository row reused after process restart.** **Impossible by current usage** — Conclusion rows are never looked up except by the exact id the same session already holds in memory; a restarted process has no session at all, hence no `conclusion_id` to reuse.
5. **Duplicate or stale session state.** **Currently untested**, but structurally equivalent to scenario 2 — would require the same manual session construction.
6. **Direct application-service invocation bypassing orchestrator assumptions.** **Possible only through internal misuse**, identical in kind to scenario 3, and identical in kind to how every other composite service in this codebase (`ObserveFromQuestionService`, `CaptureEvidenceFromHypothesisService`, `FormHypothesisFromInterpretationService`) could equally be called with internally inconsistent arguments — this is not a Conclusion-specific weakness, it is the uniform trust model this entire application layer already uses: the caller (in production, always the orchestrator) is trusted to supply a coherent Case, and no composite service independently re-derives or cross-checks it against upstream legacy chain elements anywhere in this codebase.

**Determination: explicit Conclusion Case ownership is not the narrowest correct prevention mechanism**, because the risk is not reachable through public application behavior, and the identical trust model already governs every other composite service in the conversation flow. Per this task's own instruction, no design is proposed for arbitrary repository corruption (scenario 4/5 in the more extreme "corrupted database" sense).

## 11. Case Ownership Models

**Model 1 — Explicit `case_id` on Conclusion.** Semantically incorrect: Conclusion is not a Domain Object, so adding `case_id` would not confer canonical Case ownership in OE-002's sense — it would only add a column that reads as if it did, which is actively misleading (Section 18). No normalization issue exists (the value would simply mirror `session.case_id`, always). Duplication: yes — the value would exactly duplicate what the session already carries and already correctly threads to Decision. Same-Case enforcement: could be checked at capture time against nothing authoritative, since Conclusion has no upstream Case source of its own to validate against — the value would have to be trusted exactly as much as it already is today, just stored redundantly. Migration requirement: real (Section 13). Downstream utility: none identified (Section 15). Risk of conflicting Case sources: this model would introduce a **second** Case source (Conclusion's own column) alongside the session's, creating exactly the kind of "conflicting Case sources" risk that does not exist today, where there is only ever one. Implies canonical status: yes, falsely.

**Model 2 — Case through Decision.** Once a Decision commits, `ConclusionDecisionLink` provides `decision_id`, and Decision itself already carries `case_id` — so Case becomes available for a *committed* Conclusion via one join. Pre-Decision consumers needing Case: none exist (Section 9). Post-Decision traceability: sufficient for any conceivable future audit, since the link is permanent and unique per live-flow commit. Reverse lookup: `ConclusionDecisionLinkRepository.list_by_conclusion_id` already exists and supports this today, with no new code. One-to-one assumption: reliable in live-flow practice (Section 6), not schema-enforced.

**Model 3 — Case through Observation/session.** A full backward join chain exists using **only already-existing repository methods**: `Conclusion.evidence_id` → `HypothesisEvidenceLinkRepository.list_by_evidence_id(evidence_id)` → `hypothesis_id` → `InterpretationHypothesisLinkRepository.list_by_hypothesis_id(hypothesis_id)` → `interpretation_id` → `InterpretationRepository.get(interpretation_id).observation_id` → `ObservationRepository.get(observation_id).case_id`. This is real and requires no new method, but (a) it spans four separate repository calls across three intermediate legacy types, (b) neither bridge table carries a uniqueness constraint, so the chain's determinism (exactly one path) is a live-flow-behavior fact, not a schema-enforced guarantee, and (c) the in-memory `session.case_id` — available throughout the live conversation — is simpler and already used for exactly this purpose; it does not survive process restart, but nothing in this codebase's design ever expects a `ConversationSession` to survive one (Section 6, `session.py`'s own docstring: a First Decision Conversation is a single sitting).

**Model 4 — No Case relation required.** Consistent with current behavior (Section 8) and with the existing, already-approved Case-Context propagation model (Core-Loop-Case-Context-Reconciliation-Investigation.md, Section 19), which threads `case_id` only through the two genuine Domain-Object touchpoints (Observation, Decision) and explicitly does not extend it to any of the seven legacy types.

**Model 5 — Case derivation through another existing persisted relation.** Model 3 already is this; no further alternative was found in repository reality.

**Selected: Model 4**, with Models 2 and 3 noted as available, low-cost, no-new-code fallbacks should a genuine future need arise (Section 22, Candidate 4/Open Questions).

## 12. Reasoning Trace Interaction

M1's Reasoning Trace is captured citing exclusively `session.observation_id`, typed `DomainObjectType.OBSERVATION` (Section 7 of this document; confirmed directly in `orchestrator.py`'s own `_handle_decision`). `DomainObjectType` (`atlas/core/domain/shared/domain_object_type.py`) is a closed enum with exactly six members — `OBSERVATION, KNOWLEDGE_REFERENCE, REASONING_TRACE, JUDGMENT, DECISION, OUTCOME` — **there is no `CONCLUSION` member, and adding `case_id` to Conclusion would not create one.** Reasoning Trace's own `_verify_support`/`JudgmentService._verify_subject`-style dispatch logic is written entirely in terms of this closed enum; a Conclusion, however Case-scoped, remains categorically ineligible as a Reasoning Trace support or a Judgment subject, because eligibility is governed by Domain Object Set membership (OE-002 §4), not by whether a `case_id` column happens to exist. Conclusion Case propagation is therefore **not required** to add Conclusion as support, relate it to Reasoning Trace, validate same-Case support, enrich reasoning history, or enable any future migration through this path — none of these is possible for Conclusion regardless of Case propagation, and none becomes possible because of it.

## 13. Persistence and Migration Blast Radius

If Model 1 (explicit `case_id`) were ever selected, the complete blast radius is not small: `atlas/core/domain/conclusion/entity.py` (new field, constructor, `__post_init__`); `atlas/core/application/conclusion/capture_conclusion.py` (`CaptureConclusionRequest` gains `case_id`, `ConclusionService.capture()` passes it through); `atlas/core/domain/conclusion/repository.py` (Protocol unchanged in shape but semantically now Case-bearing); `atlas/core/infrastructure/persistence/conclusion/table.py` (new column, plus a decision on nullability); `atlas/core/infrastructure/persistence/conclusion/sqlalchemy_repository.py` (`_to_row`/`_to_conclusion` both updated); `atlas/core/application/reasoning_link/commit_decision_from_conclusion.py` and `atlas/core/application/conversation/orchestrator.py`'s `_handle_conclusion` (now must also pass `case_id=session.case_id` at Conclusion-capture time, not just at Decision-commit time); every existing Conclusion test in `tests/unit/domain/conclusion/`, `tests/unit/application/conclusion/`, `tests/unit/infrastructure/persistence/conclusion/`, plus `tests/unit/application/reasoning_link/test_commit_decision_from_conclusion.py`'s and `test_core_loop_end_to_end.py`'s own fixtures, all of which construct `Conclusion`/`CaptureConclusionRequest` without `case_id` today. This is not a "small, additive, one-field" change of the kind M1/M2 were — those added a wholly new, independent capture step; this would retrofit an existing, already-shipping, frequently-exercised legacy aggregate's own shape.

**Nullability**: the column would need to be nullable during any transition (existing rows have no Case), unless a backfill runs first — but see Section 14, backfill is not lossless for all rows. **Historical Case derivation**: via Model 2/3's own join chains, where a Decision or full upstream chain exists; **impossible without invention for rows with no committed Decision** (an abandoned conversation's own orphaned Conclusion has no link to walk at all beyond the Evidence→Hypothesis→Interpretation→Observation chain, which itself requires every intermediate legacy row to still exist and be uniquely resolvable). **Orphaned Conclusions**: possible today — nothing prevents a conversation from stopping after Conclusion but before Decision (the same class of interruption already disclosed for Decision Review's own Outcome/Evaluation/Learning chain). **Uniqueness assumptions**: not safe at the schema level (Section 11, Model 3) — only safe as an empirical fact about how the live orchestrator happens to behave.

## 14. Historical-Data Analysis

For every stored historical Conclusion: **Conclusions with a committed Decision** — Case is conditionally reconstructable via `ConclusionDecisionLink` → `Decision.case_id` (Model 2), a single, reliable join, since `ConclusionDecisionLinkRepository` has no duplicate-permitting ambiguity in the live-flow-produced data (exactly one link per Conclusion in practice). **Conclusions without a committed Decision** (abandoned conversations) — Case is reconstructable only via the longer Model 3 chain, and only if every intermediate legacy row (Evidence, Hypothesis, Interpretation) and every bridge link still exists and resolves to exactly one path; where any link is missing (e.g., the conversation stopped even earlier than Conclusion), Case is **impossible to establish without invention**. **Duplicate or repeated Conclusion attempts** — not currently producible by the live orchestrator (each conversation reaches Conclusion exactly once per session), so this case is theoretical, not evidenced.

**Classification: conditionally reconstructable, not lossless, and not unnecessary-to-consider** — a straightforward "backfill every row" script cannot be written without an explicit, disclosed policy decision for the rows with no committed Decision, exactly the same category of data-policy question already disclosed and deferred for other legacy backfills in this document series (Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md, Section 16's own D5). This is not a reason to add `case_id` prospectively — it is a reason **not** to, since the resulting column would necessarily be nullable and incompletely populated for a real subset of existing rows, for no identified consuming purpose (Section 15).

## 15. Downstream-Consumer Analysis

The only consumers of `ConclusionRepository`/`ConclusionService`/`Conclusion` outside its own module are: `atlas/core/application/reasoning_link/commit_decision_from_conclusion.py` (reads Conclusion once, to verify existence, and to obtain nothing but its `id` for the link — never reads `statement` from the entity itself, since `session.conclusion_statement` is cached separately in-memory); `atlas/core/application/conversation/{cli,composition,orchestrator}.py` (construct and wire the service; the CLI never displays Conclusion's own fields, only the prompts); `atlas/core/domain/reasoning_link/entity.py`/`repository.py` (the `ConclusionDecisionLink` bridge, which needs only `conclusion_id`, never Case). No reflection, review, timeline, coaching, strategy, pattern-recognition, or analytics module was found to consume Conclusion at all (`decision_timeline` reads Decision/Outcome/Evaluation/Learning, never Conclusion — confirmed by direct inspection of `atlas/core/application/decision_timeline/{query,timeline}.py`, neither of which imports anything from `atlas.core.domain.conclusion`). None of these consumers needs Conclusion's Case, a conversation session reference, or a reasoning-link traversal beyond the one existing `conclusion_id`→`decision_id` link. Direct `case_id` on Conclusion would simplify no real query, remove no existing join (none exists), prevent no incorrect behavior evidenced anywhere, enable no authorization (Section 21), enable no analytics currently implemented, and would remain **unused** by every actual current consumer.

## 16. API and Boundary Analysis

Conclusion is exposed only through the standalone conversation CLI (`atlas/core/application/conversation/cli.py`) and, for tests, through direct application-service composition — confirmed by the absence of any `atlas/core/infrastructure/api/conclusion/` directory and by `app.py` mounting no such router. No public or internal HTTP API exists. The CLI caller never independently supplies Case for the Conclusion step at all — Case is resolved once, before the conversation begins (`_resolve_case_id`), and used only where the orchestrator itself needs it (Decision commitment, Observation capture) — the CLI has no opportunity to "mix" Conclusion and Case, since it never solicits Conclusion-specific Case input in the first place. Direct application-service invocation (test-only composition) can, as shown in Section 10, supply an arbitrary, unvalidated `case_id` — but this is a property of the test/internal-caller boundary, not of any exposed product boundary. Explicit `case_id` would not alter any existing contract, since none currently accepts or exposes Case for Conclusion specifically.

## 18. Symmetry Audit

| Legacy/canonical object | Carries `case_id`? | Why |
|---|---|---|
| Question | No | Not a Domain Object (OE-002 §4 closed set) |
| Interpretation | No | Same |
| Hypothesis | No | Same |
| Evidence | No | Same |
| **Conclusion** | **No** | **Same** |
| Evaluation | No | Same |
| Learning | No | Same |
| Observation | Yes | OE-002 §4 Domain Object; INV-002 applies |
| Decision | Yes | Same |
| Outcome | Yes | Same |
| Judgment | Yes | Same |

The dividing line is exactly, and only, OE-002 §4's closed six-type Domain Object Set membership — not richness of content, not permanence, not importance to the workflow, not length of the object's own lifecycle. Conclusion shares every one of its relevant properties (permanent, immutable, insert-only, meaningful natural-language content) with its six non-Domain-Object siblings, none of which carries Case, and none of which should. Governing architecture requires this distinction to be drawn by Domain Object Set membership (OE-002 §2: "Architecture MUST NOT begin with, and MUST NOT be justified by... existing code... naming familiarity... workflow convenience"). **Rejected explicitly**: "Conclusion is important/long-lived/rich in content, therefore it should carry Case" — this is exactly the aesthetic-consistency argument Doctrine §3 and OE-002 §2 forbid as a basis for adding an architectural property.

## 19. Invariant Analysis

Conclusion remains subject to no Case-related invariant today, because INV-002 through INV-005 (Case ownership, event-Case correspondence, same-Case reference, prior acceptance) apply only to Domain Objects and Domain Events, and Conclusion is neither. This is not a gap — it is the same, already-correct exclusion that applies to Question, Interpretation, Hypothesis, and Evidence. If `case_id` were added, the only candidate new invariant with any real content would be "Conclusion and its eventually-committed Decision must share Case" — but this invariant **cannot be enforced through current persisted data** at Conclusion-capture time (Decision does not yet exist), and at Decision-commitment time it would be redundant with the existing, correct, single-session-sourced `case_id` already used to construct both Conclusion's (hypothetical) column and Decision's real one — the invariant would hold trivially, by construction, in the live flow, and would not hold, and could not be checked, for any Conclusion supplied out-of-band (Section 10). Such an invariant, if introduced, would be **application-only**, never canonical (Conclusion remains outside OE-002 §4 regardless), and would add no protection beyond what the existing session-sourced trust model already provides.

## 20. Failure and Retry Implications

Case propagation on Conclusion would have **no effect** on: Conclusion capture's own retry/reprompt boundary (governed by Evidence existence and statement non-emptiness only); Decision commitment's own retry/reprompt boundary (governed by Conclusion existence only; Case is already independently supplied); M1's Reasoning Trace failure boundary (cites Observation only, Section 12); terminal workflow state (`DECISION_RECORDED` already has no `_HANDLERS` entry, independent of Conclusion's own shape); duplicate prevention (governed by the same terminal-state guard already proven for M1/M2, unrelated to Conclusion's fields); session reconstruction (Conclusion's own Case-bearing or not does not change whether `ConversationSession` survives a restart — it does not, either way, per `session.py`'s own docstring); error recovery (no recovery mechanism exists for any legacy step today, and Case propagation would not introduce one). **No effect exists; M3 must not be justified as a retry-safety improvement**, and this document does not so justify it.

## 21. Security and Authorization Relevance

Case is not used anywhere in this codebase for tenant separation, access control, authorization, row filtering, deletion boundaries, or privacy isolation — confirmed by the absence of any authorization middleware, row-level security check, or access-control decorator referencing `case_id` anywhere in `atlas/core/infrastructure/api/` or `atlas/core/application/`. Case is purely an ownership/grouping boundary in the ontological sense OE-002 §3.1 defines it, not a security boundary in this implementation. Conclusion's lack of Case therefore creates **no security issue** — there is no security property Case currently provides anywhere in this codebase that Conclusion's absence of it could be said to be missing.

## 22. Candidate D3 Resolutions

**Candidate 1 — Implement explicit Conclusion `case_id`.** Semantic fidelity: poor — falsely implies canonical status (Section 11, Model 1; Section 18). Operational correctness: neutral, would work, but redundantly. Contamination prevention: does not actually prevent the identified scenario unless additionally cross-validated at every write site, which nothing currently does for any sibling legacy type either. Migration cost: real and non-trivial (Section 13). Historical-data feasibility: incomplete for a real subset of rows (Section 14). Downstream value: none identified (Section 15). Canonical migration relevance: none (Section 17). Risk: introduces a second, potentially-divergent Case source where only one exists today. Reversibility: the column itself is droppable, but every call site touched to populate it would need to be reverted too. **Rejected.**

**Candidate 2 — Keep Conclusion unchanged; remove M3 from the canonical migration roadmap.** Semantic fidelity: exact — matches Conclusion's own correctly-established non-Domain-Object status. Operational correctness: unchanged, already correct (Section 7). Contamination prevention: the underlying scenario (Section 10) is unaffected either way, since it is not Conclusion-specific and not reachable through public behavior. Migration cost: zero. Historical-data feasibility: not needed. Downstream value: preserved as-is (nothing currently needs it). Canonical migration relevance: confirmed none (Section 17). Risk: none identified. Reversibility: trivially reversible in the sense that nothing is done. **Selected.**

**Candidate 3 — Add application-level validation without changing Conclusion's shape** (e.g., validate Case through the `ConclusionDecisionLink`/Decision chain at commitment time). Would require deriving Conclusion's own Case via a chain that does not exist until *after* the Decision it would be validating already commits — circular for the one place Case is actually used (Section 7). For the theoretical "wrong Conclusion supplied to the composite" scenario (Section 10), this would add a cross-check present nowhere else in this codebase's identically-shaped composite services, an asymmetric, unforced addition. **Rejected** — no genuine, publicly-reachable contamination risk was found to justify it (Section 10), and the one authoritative relation available (Model 2/3) either postdates the moment validation would need to occur or is not otherwise used for this purpose anywhere in this codebase.

**Candidate 4 — Defer until a concrete consumer requires Case.** Considered, but rejected as *the* selected outcome (though its underlying reasoning is preserved as an open question, Section 28): the evidence gathered here — no invariant, no consumer, no migration need, no reachable contamination, no security role, exact symmetry with six untouched siblings — is sufficient to settle the question now, not merely to postpone it. Retaining D3 as "still open" would misstate how decisively the evidence resolves it.

**Candidate 5 — Another bounded solution.** None was found in repository reality beyond Candidates 1–4.

**Remaining axes, addressed explicitly for each candidate per this audit's own checklist**: **public-flow correctness** (the guarantee available through the orchestrator's own interface, Section 8) is identical — already correct — under Candidates 1, 2, and 4, since none of them changes what the orchestrator itself does; only Candidate 3 would add a check the public flow does not need. **Internal-API correctness** (whether `CommitDecisionFromConclusionService.commit()` itself, called directly, behaves safely) is unchanged and still permissive under Candidates 1, 2, and 4 (a stored-but-uncross-checked `case_id` on Conclusion would not, by itself, cause the service to validate anything new); only Candidate 3 changes this axis, and only Candidate 3 was found to have no genuine trigger for doing so today (Section 10). **Security relevance**: none for any candidate (Section 21) — Case carries no security role for any of them to protect or expose. **Future exposure risk**: Candidates 2 and 4 carry no exposure risk of their own; Candidate 1 would, if the composite were ever exposed publicly, still require the same Candidate-3-style validation to be meaningful, so it does not preempt that future need, only adds an unused column ahead of it; Candidate 3, if adopted prematurely, would itself become dead validation code until such exposure occurred.

**Selected: Candidate 2.**

## 23. Selected Resolution

**Candidate 2 — Keep Conclusion unchanged; retire Package M3.** Conclusion remains exactly as implemented: `id, evidence_id, statement, concluded_at, recorded_at, note`, no `case_id`. Case continues to reach Decision the way it already, correctly does — via `ConversationSession.case_id`, threaded directly into `CommitDecisionFromConclusionRequest`, independent of Conclusion. Model 2 (Case through the existing `ConclusionDecisionLink`→Decision join) and Model 3 (Case through the existing reasoning-link chain to Observation) remain available, at zero implementation cost, should any future, concretely-demonstrated consumer ever need to recover a committed Conclusion's Case after the fact.

## 24. M3 Retirement

Package M3 (Conclusion Case propagation), as described in the Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md, Section 21, is retired. No implementation package is specified, because none is justified: Conclusion requires no new field, no new validation, no new repository method, no persistence change, no API change, no test change, and no historical migration. The reasoning_link bridge disposition (Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md, Section 10) is unaffected and unchanged. Any future package wishing to derive a committed Conclusion's Case may do so directly via `ConclusionDecisionLinkRepository.list_by_conclusion_id` → `DecisionRepository.get(...).case_id` (Model 2) without any change to Conclusion itself.

**Exact, explicit reopening criteria** — any one of the following, if it ever becomes true, is sufficient grounds to reopen D3; none is true today, and none is anticipated by this document:

1. **`CommitDecisionFromConclusionService` (or an equivalent composite) is ever exposed through a public or internal HTTP API, a background worker, or any boundary an untrusted or independent caller can reach directly**, rather than exclusively through the single-session-disciplined conversation orchestrator. Today, no such exposure exists (Section 16); if it were ever added, the internal-service limitation disclosed in Section 8/10 would become a public-flow risk, not merely a theoretical one, and Candidate 3 (bounded application-level validation) would need to be re-evaluated as the likely resolution — not necessarily Candidate 1 (`case_id` on Conclusion itself), since the validating relation could still be Model 2/3 rather than a new field.
2. **`ConversationSession` is ever persisted, serialized, or made recoverable across a process restart or across independent requests**, rather than remaining the in-memory-only, single-sitting object it is today (Section 8, `session.py`'s own docstring). If sessions could be reconstructed from external storage, the "coherent by construction" public-flow guarantee (Section 8) would depend on that persistence layer's own correctness, not on the orchestrator's own linear code path, and would need independent re-verification.
3. **Any authorization, tenancy, or access-control mechanism is ever introduced that uses Case as a security or isolation boundary**, rather than Case remaining the purely ontological ownership/grouping concept it is today (Section 21). If Case ever gained this role, every object touching Case-sensitive data — including, potentially, Conclusion, if it were ever positioned to leak cross-Case information — would need independent security review, not merely an ontology review.

No internal validation hardening task is proposed as a companion to this retirement: Section 22, Candidate 3's own rejection applies precisely because none of the three conditions above currently holds. Should any one of them arise, this document's own Section 10 and Section 22 provide the starting analysis for that future reconsideration, so a future investigator does not need to re-derive it.
