# Core Loop Case Context Reconciliation — Investigation

This document is an investigation-and-design artifact, not a normative document. It carries no Doctrine status because those statuses apply to normative documents, and this is not one. It implements nothing and modifies no existing file, test, or document. Where anything here appears to conflict with the Architecture Doctrine, OE-002 through OE-006, or the Historical Decision Record, those documents govern and this one is wrong and must be corrected.

## 2. Executive Finding

The legacy Core Loop (`Question → Observation → Interpretation → Hypothesis → Evidence → Conclusion → Decision → Outcome → Evaluation → Learning`, orchestrated by `ConversationOrchestrator`) touches exactly **three** OE-002 §4 adopted Domain Objects — Observation, Decision, Outcome — and **seven** non-Domain-Object legacy aggregates (Question, Interpretation, Hypothesis, Evidence, Conclusion, Evaluation, Learning) plus four `reasoning_link` bridge records, none of which are, or ever need to be, Case-owned, because OE-002 §4's Domain Object Set is closed and none of the seven names appears in it. INV-002 ("every Domain Object MUST belong to exactly one Case") therefore does not apply to them at all — this is not an oversight to correct, it is the architecture working as designed.

Of the three genuine Domain-Object touchpoints: **Observation** already has its case_id correctly implemented (DO-IMP-006, committed `d1fb901`) but the legacy composite service that feeds it, `ObserveFromQuestionService`, has no source of a genuine `CaseId` and cannot construct `CaptureObservationRequest` — this is the live, currently-failing integration gap (22 failed / 4 errors). **Decision** and **Outcome** each already have an approved, committed Implementation Design (`Decision-Implementation-Design.md`, `Outcome-Implementation-Design.md`) requiring `case_id`, but neither design has been implemented in code yet — their legacy entities remain case_id-less today, so this is a known, already-anticipated, not-yet-triggered future instance of the identical gap (it will break the moment either design is implemented, since `CommitDecisionFromConclusionService` feeds Decision through the same case_id-blind orchestrator).

No canonical source defines how a genuine `CaseId` reaches the conversation-orchestration layer that constructs these two composite-service requests. This is not a gap in Case's own ontology (OE-002 §3.1 is complete and sufficient) — it is a missing **application-layer propagation decision**: who creates or selects the Case for a conversation, and how does that Case's id get threaded into `ObserveFromQuestionRequest` and (eventually) `CommitDecisionFromConclusionRequest`. That decision is not settled by any existing document and must be made before an Observation-Implementation-Design-style implementation design can be written for the integration fix.

## 3. Selected Outcome

**Outcome 2 — a bounded Case-context architecture decision is required before implementation design.** Not Outcome 1: the propagation mechanism is genuinely undecided among several live candidates, not merely undocumented. Not Outcome 3: no contradiction was found that invalidates the Core Loop's own step sequence or `ObserveFromQuestionService`'s responsibility — the gap is a narrow, mechanical wiring question at exactly two points, not a structural defect. Not Outcome 4: Case's own ontology (what a Case is, INV-002/003/004) is not in question and blocks nothing; what is missing is one layer up, at the conversation/orchestration boundary that OE-002 through OE-006 never addressed because they are silent on any application layer by design (OE-002 §8, OE-004 §15 both explicitly exclude "implementation structures of any kind").

## 4. Scope and Method

This investigation determines the Case boundary, creation authority, and propagation requirements for the legacy Core Loop, without modifying any production code, test, or existing document, and without beginning implementation of any package. It does not reopen Case's own ontology (OE-002 §3.1), does not reopen the already-approved Observation implementation (commit `d1fb901`), and does not resolve the Decision/Outcome open questions already recorded in their own Implementation Designs (committed-to-matter/realized-matter form coexistence, `decision_type`/`confidence`/`source` status) — those are cited by reference, not re-litigated. Method: extract explicit canonical claims, test each candidate Case-boundary model against them, reject by contradiction or absence of authority only, and select the smallest model that supplies a genuine CaseId at the two live/imminent integration points without inventing a new concept or reusing an unrelated one.

This is recorded as a historical inconsistency (Section 40), not fabricated or worked around here.

## 6. Case Ontology Finding

OE-002 §3.1, in full: "A Case is the normative ownership boundary within which Domain Objects exist and relate to one another. Every Domain Object belongs to exactly one Case. This document defines only the role of Case as the ownership boundary of the Domain Object Model. It does not define the complete semantics, lifecycle, or implementation of Case beyond what is required by this model." This is complete and settled for what it claims to define — nothing more is owed by OE-002, and nothing here reopens it. `Case`'s own implementation (`atlas/core/domain/case/entity.py`) mirrors this exactly: `id`, `recorded_at`, a `create()` factory that captures no investor-supplied content, deliberately named `create` not `capture` since "there is nothing to capture, only an ownership boundary to establish." **What OE-002 does not define, and never claimed to**: what real-world event triggers a new Case, whether a Case has any lifecycle stage beyond existing, or how an application layer (a CLI conversation, a future UI) decides which Case a given user action belongs to. That silence is not a defect in OE-002 — Section 8 there explicitly excludes "implementation structures of any kind" — but it does mean the conversation-orchestration question this investigation was tasked with cannot be answered by re-reading OE-002 more carefully; it requires an application-layer decision that has never yet been made for any part of this codebase.

## 7. Case Lifecycle and Creation-Authority Finding

Creation authority is already fully settled and singular: only `CaseService.create()` (`atlas/core/application/case/create_case.py`) constructs a Case, calling `Case.create()`, backed by `CaseRepository.add()`. No other path exists anywhere in the codebase. This investigation changes nothing about that — the open question is exclusively **who calls `CaseService.create()` (or `.get()`) and when**, for the legacy conversation flow, not whether a new creation path should exist. Lifecycle: a Case, once created, has no defined end, no status, no closure operation — `CaseRepository` intentionally has no `list_all()` ("nothing within DO-IMP-001's approved scope needs to enumerate every Case yet"). This absence is itself a finding: any candidate model requiring an investor to browse or select among existing Cases (Section 17, Candidates F/G) requires `CaseRepository` to gain an enumeration capability that does not exist today — a small, real, disclosed implementation gap, not a blocker (Section 39).

## 8. The Closed Domain Object Set and Its Consequence for the Legacy Core Loop

OE-002 §4 states: "The Domain Object Set consists of exactly the following six Domain Objects: 1. Observation 2. Knowledge Reference 3. Reasoning Trace 4. Judgment 5. Decision 6. Outcome. No other Domain Object is part of this model." Section 2 reinforces: "The Domain Object Set stated in Section 4 is closed." This is the single most decisive finding of this investigation. It means **Question, Interpretation, Hypothesis, Evidence, Conclusion, Evaluation, and Learning are not Domain Objects under any reading of current architecture, and INV-002 does not apply to them.** This is independently confirmed by the already-committed `Outcome-Implementation-Design.md` (Section 20): "Learning is not an adopted Domain Object... not a member of OE-002 §4's closed six-type set... exactly identical to the already-confirmed non-adoption of Reasoning Act." The task's own instruction not to assume Question/Interpretation/reasoning_link "already belong to a Case unless governing architecture establishes it" is answered decisively in the negative for all seven, plus the four `reasoning_link` bridges — governing architecture establishes the opposite: they are excluded by a closed, exhaustive list, not merely unaddressed. Adding `case_id` to any of them would itself be an unauthorized architectural addition, exactly as forbidden as inventing a new "Investigation" Domain Object (Section 17, Candidate C) — it would require reopening OE-002 §4 under a genuine forcing function (Doctrine §8), and none exists.

## 9. Current Core Loop Map — Question Through Learning

`Question` (root, no upstream dependency, `id`/`statement`/`raised_at`/`recorded_at`/`note`) → `ObserveFromQuestionService.observe()` verifies the Question exists, then calls the unmodified `CaptureObservationService.capture()` to construct `Observation` (`id`/`case_id`/`subject`/`statement`/`observed_at`/`recorded_at`/`source`/`note` — Domain Object, case-owned since DO-IMP-006), then records a `QuestionObservationLink`. → `InterpretationService` reads the Observation by id (read-only) and constructs `Interpretation` (`id`/`observation_id`/`statement`/`interpreted_at`/`recorded_at`/`note` — not a Domain Object). → `FormHypothesisFromInterpretationService` verifies the Interpretation exists, calls unmodified `HypothesisService.capture()` to construct standalone `Hypothesis` (`id`/`statement`/`formulated_at`/`recorded_at`/`note` — not a Domain Object, no references at all), records an `InterpretationHypothesisLink`. → `CaptureEvidenceFromHypothesisService` verifies the Hypothesis exists, calls unmodified `EvidenceService.capture()` to construct standalone `Evidence` (`id`/`statement`/`direction`/`observed_at`/`recorded_at`/`source`/`note` — not a Domain Object), records a `HypothesisEvidenceLink`. → `ConclusionService` reads Evidence by id and constructs `Conclusion` (`id`/`evidence_id`/`statement`/`concluded_at`/`recorded_at`/`note` — not a Domain Object). → `CommitDecisionFromConclusionService` verifies the Conclusion exists, calls unmodified `CaptureDecisionService.capture()` to construct `Decision` (`id`/`user_id`/`decision_type`/`subject`/`investment_case`/`confidence`/`decided_at`/`recorded_at`/`source` — **Domain Object, OE-002 §5.5, currently case_id-less**), records a `ConclusionDecisionLink`. Beyond Decision, three further legacy steps exist but are **not wired into `ConversationOrchestrator` at all** (`composition.py`'s own docstring: "Does not construct OutcomeService, EvaluationService, or LearningService — those belong to a future review phase"): `Outcome` (`id`/`decision_id`/`statement`/`occurred_at`/`recorded_at`/`note` — **Domain Object, OE-002 §5.6, currently case_id-less**), `Evaluation` (`id`/`outcome_id`/`statement`/`evaluated_at`/`recorded_at`/`note` — not a Domain Object), `Learning` (`id`/`evaluation_id`/`statement`/`learned_at`/`recorded_at`/`note` — not a Domain Object).

## 10. Current Core Loop Map — reasoning_link Bridges

`QuestionObservationLink`, `InterpretationHypothesisLink`, `HypothesisEvidenceLink`, `ConclusionDecisionLink` — four thin, immutable bridge records (`link_id`, two foreign ids, `linked_at`), explicitly self-documented as "PROVISIONAL STATUS... a temporary orchestration mechanism, not a permanent addition to the ubiquitous language," introduced solely to bridge edges pointing into aggregates that must not gain a new field. None is named in OE-002 §4's closed set; none carries or needs `case_id`; the already-committed Reasoning-Trace-Implementation-Design.md independently confirms these are "not an existing implementation of Reasoning Trace... carry no independent content, no Case concept, and are explicitly disclosed as provisional," useful at most as future migration seed data, never as something requiring Case-ownership correction today.

## 11. Current Identifier Map

`CaseId` — exists (`atlas/core/domain/case/value_objects.py`), used today only by Case, Knowledge Reference, Judgment, Observation. `UserId` — exists (`atlas/core/domain/decision/value_objects.py`), a distinct user-identity concept; Decision's `user_id` was already found, independently, in the approved Decision Implementation Design to have "no future semantic role" beyond compatibility metadata and is explicitly disclaimed from ever substituting for Case ownership ("does not require an Agent," §18). `investor_id` — resolved once per process via `resolve_investor_identity(engine)`, held by `ConversationOrchestrator` and used only at the Decision step (`user_id=self._investor_id.value`); confirms, by direct code inspection, the same separation the Observation blocker-resolution document already established: identity of the person is never Case ownership. `session_id` — `ConversationSession.session_id: uuid.UUID`, generated in-memory, never persisted, explicitly documented as belonging "to a different layer entirely: the application boundary, not the domain model," exempt from the immutability convention every domain aggregate follows. No `CaseId`-equivalent identifier exists anywhere upstream of `ObserveFromQuestionService`'s construction of `CaptureObservationRequest`, confirming the already-committed blocker-resolution document's finding remains correct after this investigation's own, independent, fresh inspection.

## 13. ObserveFromQuestionService Analysis

`ObserveFromQuestionService.observe()` (`atlas/core/application/reasoning_link/observe_from_question.py`) constructs `CaptureObservationRequest(subject=..., statement=..., observed_at=..., source=..., note=...)` — no `case_id` argument anywhere. Since DO-IMP-006 made `case_id` a required, no-default field of `CaptureObservationRequest`, this call now raises `TypeError: __init__() missing 1 required positional argument: 'case_id'` on every invocation. `ConversationOrchestrator._handle_observation` wraps this call in a bare `try/except Exception:` that silently re-prompts on any failure, which is why the manifestation in the full suite is 22 assertion failures/timeouts in conversation-level tests rather than a visible crash. `ObserveFromQuestionRequest` itself (the composite service's own request object) also has no `case_id` field to relay one even if the service were fixed internally — the gap exists at two levels: the composite service's own request shape, and the orchestrator's own construction of that request. `ObserveFromQuestionService`'s responsibility (verify Question exists, delegate to `CaptureObservationService`, record the link) remains entirely valid and requires no redesign — only a new, additional required input, exactly the same shape of change DO-IMP-006 itself already made to `CaptureObservationRequest`.

## 14. CommitDecisionFromConclusionService Analysis

`CommitDecisionFromConclusionService.commit()` (`atlas/core/application/reasoning_link/commit_decision_from_conclusion.py`) constructs `CaptureDecisionRequest(user_id=..., decision_type=..., subject=..., reason=..., confidence=..., decided_at=..., source=...)` — no `case_id`. Today this raises no error, because `Decision`'s entity and `CaptureDecisionRequest` have not yet been changed to require it — the approved `Decision-Implementation-Design.md` specifies `case_id` as a required minimal field, but "no new file was created for implementation, and none was modified" per that document's own Section 38. This is therefore a **known, disclosed, not-yet-triggered instance of the identical integration gap**: the moment a DO-IMP package implements Decision per its approved design, `CommitDecisionFromConclusionService` will fail exactly as `ObserveFromQuestionService` does today, for the identical reason and via the identical mechanism (the orchestrator's bare exception handling). Any Case-context model selected for `ObserveFromQuestionService` should be verified to generalize to this second touchpoint without a separate redesign — Section 19 confirms it does.

## 15. ConversationSession Analysis

`ConversationSession` (`atlas/core/application/conversation/session.py`) is explicitly, by its own module docstring, "NOT a domain aggregate" — never persisted, mutable by design, exempt from the immutability convention because "it belongs to a different layer entirely: the application boundary, not the domain model." It carries `session_id: uuid.UUID` (in-memory correlation only) and a `ConversationStep` enum covering exactly Question through Decision (Outcome/Evaluation/Learning are absent from the enum by design, matching Section 9's finding that they are unwired). Nothing about `ConversationSession`'s own definition forbids it from *additionally* holding a resolved `case_id` value once one is obtained — doing so would not promote `session_id` to `CaseId` (binding fact from the original blocker document, reaffirmed here), it would simply add one more piece of ordinary, in-memory, per-conversation application state alongside the existing `session_id`, `current_step`, and captured-object fields it already carries. This also does not make `ConversationSession` itself a Case, a Domain Object, or Case-owned in any sense — it remains exactly what this section's opening establishes: a non-domain, unpersisted, application-boundary construct that merely carries a Case's id as one more piece of correlation data, the same relationship it already has with every other identifier it holds.

## 16. ConversationOrchestrator Analysis

`ConversationOrchestrator` (`atlas/core/application/conversation/orchestrator.py`) is constructed with exactly seven step services plus `investor_id: UserId` — no `CaseService`, no `CaseRepository`, anywhere in its constructor or in `build_conversation_orchestrator(engine)` (`composition.py`). Every one of its seven `_handle_*` methods wraps its underlying service call in a bare `try/except Exception:`, which is the reason `ObserveFromQuestionService`'s `TypeError` manifests as an infinite re-prompt in conversation-level tests rather than a propagated, visibly-labeled error — a pre-existing, unrelated error-handling breadth issue this investigation does not attempt to correct (Section 41). `investor_id` is used exactly once, at `_handle_decision` (`user_id=self._investor_id.value`), independently confirming, by direct fresh inspection, that this codebase already keeps user identity and Case ownership strictly separate in practice, not merely in principle.

## 17. Candidate Case Boundaries — Evaluation

**A — one Case per conversation session.** Orchestrator creates a fresh Case at conversation start, holds its id in `ConversationSession` alongside (never instead of) `session_id`. Satisfies exactly-one-Case, user-visible meaning, lifecycle correctness for a single sitting. Fails: no continuation across conversations — an investor returning "the next day" to add Evidence to the same Hypothesis gets a new, disconnected Case every time, even though it is evidently the same line of reasoning; this is a real weakness, not merely a stylistic one, since ATLAS-002 conversations can already be interrupted (the existing `decision_review` module exists precisely because conversations are not always completed in one sitting).

**B — one Case per user-submitted Question.** Extensionally identical to A today (one conversation asks exactly one Question), diverges only if the Core Loop is ever extended to multiple Questions per sitting. Would require adding `case_id`-creation responsibility to `QuestionService` itself, even though Question is not a Domain Object and gains nothing ontologically from it — this conflates "what triggers a new investigation" with "what Question happens to be asked," which are not shown to be the same fact anywhere in canon. Not selected; subsumed by G below without needing Question's own involvement.

**C — one Case per investigation/analysis initiated through the Core Loop.** Rejected for lack of authority: no such concept ("Investigation," "Analysis") exists anywhere in `atlas/core` as a class or documented concept (confirmed by repository-wide grep); inventing one now to serve as the Case boundary would itself be an unauthorized new architectural concept, and if it existed it would simply collapse into Case's own already-defined ownership-boundary role (Doctrine §5, Distinctness and Reducibility) rather than being genuinely distinct from it.

**D — one Case per intended Decision.** Rejected: creates a temporal contradiction. Observation is captured (and, per binding fact #1/#2, must already have a real `case_id`) several steps before any Decision exists in the sequence; a rule that creates the Case only at/around Decision time cannot supply Observation's required Case at the point Observation is actually captured.

**E — one Case per portfolio/security/company/investment subject.** Already rejected in the committed blocker-resolution document as fragmenting Case's own purpose; reconfirmed here: "subject" is unstructured, investor-supplied free text on Observation and Decision individually, not an identified aggregate anywhere in the codebase, and Case's own entity (`id`, `recorded_at` only) has no field to match against such text — adopting E would require adding an unauthorized field to Case itself, directly forbidden by this task's own instruction.

**F — a conversation may attach to an existing Case selected by the investor.** Requires `CaseRepository` to gain an enumeration/lookup-by-selection capability it does not have today (Section 7) — a real, disclosed, small implementation gap, not a blocker.

**G — a conversation may create a new Case or continue an existing Case, via an explicit request contract.** Satisfies every property F does, generalizes A's "new" branch and F's "continue" branch under one explicit, investor-visible choice made once per conversation rather than inferred. Satisfies binding fact "no hidden Case creation" directly, since the choice is explicit. Solves A's continuation weakness: a second conversation can explicitly continue the first conversation's Case.

**H — Case exists above the conversation layer, supplied to the orchestrator.** A propagation-direction description (who hands the resolved case_id to the orchestrator), not a competing policy — compatible with, and adopted as the mechanism for, G.

**I — Case created inside the orchestrator at an explicit lifecycle boundary.** A strict subset of G (the "always create new" branch only); rejected as the sole rule for the same continuation reason as A, but its "explicit lifecycle boundary" framing is retained as exactly where G's "new" branch fires.

**J — the legacy Core Loop is not a legitimate Case-producing flow, requires retirement/restructuring.** Rejected: no contradiction was found between Case and the Core Loop's own shape (Section 32); the gap is a narrow, two-touchpoint wiring omission precisely analogous to what DO-IMP-006 already fixed for Observation, not evidence the whole flow is invalid.

**K — any other repository-supported candidate.** None found: `atlas/shared/entities.py` and `atlas/adapters/portfolio.py` define a `Portfolio`/`Watchlist`/`ResearchNote` legacy Alpha subsystem, confirmed by grep to have zero cross-imports with `atlas/core` — a wholly disconnected, non-candidate system, not a Case-boundary concept.

## 18. Candidate Rejection Analysis

Rejected outright, by direct contradiction with existing binding facts or canon: C (no authority for a new concept), D (temporal contradiction with Observation's own required case_id timing), E (requires an unauthorized new Case field), J (no contradiction found to justify it), K (no candidate exists). Rejected as insufficiently general but not contradictory: A and I (fail multi-conversation continuation), B (conflates Question with investigation boundary, offers no advantage over G). Retained and combined: G (policy) with H (propagation direction) as the selected model.

## 19. Selected Case-Context Model

**A conversation may create a new Case or continue an existing Case, decided explicitly, once, at conversation start, never inferred from `session_id` or `investor_id`.** The resolved `CaseId` is held by `ConversationSession` as ordinary, additional, in-memory application state (never replacing or being derived from `session_id`), and is threaded explicitly as a plain data field into every composite-service request that ultimately reaches a Domain-Object-owning capture service — exactly the same pattern already proven correct by DO-IMP-006 for `CaptureObservationRequest.case_id`. This model generalizes cleanly to both live/imminent touchpoints identified in Sections 13–14: `ObserveFromQuestionRequest` gains a `case_id` field relayed straight through to `CaptureObservationRequest`, and, whenever Decision's approved design is implemented, `CommitDecisionFromConclusionRequest` gains the identical field relayed to `CaptureDecisionRequest` — no separate model is needed for the second touchpoint.

## 20. Case Creation Authority Under the Selected Model

Unchanged from DO-IMP-001: only `CaseService.create()`/`.get()` may create or retrieve a Case. The **caller** of that authority, under this model, is the conversation-composition layer (`build_conversation_orchestrator`, or a new bootstrap step immediately preceding it) — never `CaptureObservationService`, never `CaptureDecisionService`, never any capture-service, satisfying binding facts 6 and 7 directly (`CaptureObservationService` must not fabricate or repair-via-`CaseRepository` a missing Case). No field is added to `Case` itself; no new creation path is introduced.

## 21. Exact Case-Origin Analysis

Under the selected model, a genuine `CaseId` originates at exactly one point: an explicit, investor-visible choice made once, before or at the start of a `ConversationOrchestrator` run — "start a new investigation" (→ `CaseService.create()`) or "continue investigation X" (→ `CaseService.get(existing_id)`, requiring the enumeration/selection capability flagged in Section 7 and Section 17-F). It never originates from `session_id`, `investor_id`, a default, a sentinel, or an inferred value, satisfying binding facts 3, 4, 5, and 9 directly.

## 22. Propagation Analysis

Once resolved, `case_id` propagates as a plain, explicit constructor/request argument, never as a repository dependency injected into a capture-service and never inferred downstream: `ConversationSession` holds it → each `_handle_*` orchestrator method reads it from the session → each composite-service request object (`ObserveFromQuestionRequest`, and later `CommitDecisionFromConclusionRequest`) gains a `case_id` field → each composite service relays it unchanged into the underlying `CaptureObservationRequest`/`CaptureDecisionRequest` it already constructs. This is a pure data-threading change at each of these four points — no new repository dependency, no new cross-service coupling, no change to any Domain Object's own already-approved shape.

## 23. Per-Domain-Object Propagation Requirement

**Observation** (live): `ObserveFromQuestionRequest` gains `case_id: uuid.UUID`; `ObserveFromQuestionService.observe()` relays it into `CaptureObservationRequest(case_id=request.case_id, ...)`; `ConversationOrchestrator._handle_observation` supplies it from `ConversationSession`. **Decision** (imminent, once implemented per its approved design): `CommitDecisionFromConclusionRequest` gains `case_id: uuid.UUID`; `CommitDecisionFromConclusionService.commit()` relays it into `CaptureDecisionRequest`; `_handle_decision` supplies it identically. **Outcome**: no current integration exists to fix (Section 9) — this requirement is dormant until a future package wires `OutcomeService` into any orchestrator. **Knowledge Reference, Judgment, Reasoning Trace**: no Core Loop integration exists or is implied by anything in this investigation; unaffected.

## 24. API Implications

No REST API change is required by this investigation's own selected model at the two touchpoints themselves — `ObserveFromQuestionService` and `CommitDecisionFromConclusionService` are conversation-layer composite services with no dedicated router of their own today. A future implementation package would need to expose the "new Case or continue existing Case" choice through whatever entry point drives a conversation (currently a CLI, `atlas/core/application/conversation/cli.py`) — a CLI/UX design question, not an API schema question, since no HTTP surface currently fronts the conversation flow.

## 25. Application-Layer Implications

`ConversationSession` gains one new field (`case_id: uuid.UUID | None`, resolved before the first step or at the Question step). `ConversationOrchestrator` gains no new constructor dependency under this model (it does not need `CaseService` injected into it if the composition layer resolves the Case before constructing the orchestrator for a given run) — this is a deliberate minimality choice: prefer resolving Case once, outside the orchestrator, over adding a `CaseService` dependency the orchestrator would otherwise need to carry for its entire lifetime.

## 26. Domain-Model Implications

None to `Case` itself (Section 20). `Observation` is already correctly shaped (DO-IMP-006). `Decision` and `Outcome` already have approved designs specifying `case_id`; this investigation does not alter either design, and confirms no further domain-model change is implied beyond what those two documents already specify.

## 27. Persistence Implications

None beyond what DO-IMP-006 already committed for `observations`, and what the already-approved Decision/Outcome designs already specify for their own future `decisions_v2`/outcome persistence work. No new table is required for Case-propagation itself — it is pure request/session data, never persisted independently of the Domain Objects it eventually reaches.

## 28. Dependency-Injection/Composition Implications

`build_conversation_orchestrator(engine)` (or a new, small wrapping function) gains responsibility for resolving a `CaseId` (via a `CaseService` it constructs locally, exactly as it already constructs every other per-run service) before or during `ConversationSession` construction — a mechanical, additive change to `composition.py`, not a redesign of it.

## 29. Test Implications

New tests would be required, at the future implementation stage (not here): `ObserveFromQuestionService`/`ObserveFromQuestionRequest` unit tests confirming `case_id` is required and relayed unchanged; `ConversationOrchestrator` tests confirming a resolved `case_id` is read from the session and passed through at the observation step; a "new versus continue" selection test at whatever composition/CLI layer implements the explicit choice.
