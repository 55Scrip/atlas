# Hypothesis / Evidence API Lifecycle Decision (D4)

This document is an investigation-and-lifecycle-design artifact, not a normative document. It carries no Doctrine status (Draft/Final/Superseded/Historical) because those statuses apply to normative documents, and this is not one. It implements nothing, modifies no production file, no test, and no existing document. Where anything here appears to conflict with the Architecture Doctrine, OE-002 through OE-006, the Historical Decision Record, or `Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md`, those documents govern and this one is wrong and must be corrected.

## 1. Executive Finding

D4 — "Does any external caller currently depend on the `/hypotheses` or `/evidence` REST schemas?" (`Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md`, Section 25) — is resolved on its repository-internal half exactly as that investigation already found, independently reconfirmed here by a fresh, repository-wide search: **zero internal callers** of either endpoint exist anywhere in this codebase outside the two modules' own files and their own tests. The residual, externally-facing half of the question (a caller entirely outside this repository) cannot be settled by repository inspection and remains genuinely open — but, as this document shows in Section 28, that residual uncertainty does not block the specific action this document selects, because the selected action changes no runtime behavior for any caller, known or unknown.

Both Hypothesis and Evidence are, independently and for structurally identical reasons, **classified for retention as explicit legacy workflow APIs, not canonical Atlas Core APIs** (Required Conclusion B). Both aggregates are standalone by their own design (no `case_id`, no relationship to any other aggregate), both are mounted as genuine public HTTP routes with no authentication or authorization anywhere in the application, both have exactly one internal consumer (the live conversation orchestrator, which never calls the HTTP layer — it constructs the application services directly, in-process), and neither has a canonical Domain Object that can replace it today without semantic distortion or loss. This document recommends exactly one immediate, additive, zero-behavior-change package — documentation/tag-level legacy classification on both routers, operationalizing Package M4 as already proposed by `Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md`, Section 21 — and defers restriction or removal pending forcing functions that do not yet exist.

## 4. Definition of API Surface

For this document, an "API surface" is any interface a caller outside the object's own module can invoke without modifying source code: (a) an HTTP route mounted into the production `FastAPI` app (`atlas.core.infrastructure.api.app.create_app`); (b) a CLI command; (c) an application-service class (e.g. `HypothesisService`), callable by any composition root within the codebase; (d) a repository `Protocol`, callable by any application service. This document's primary concern is (a) and (b) — the surfaces a genuinely external caller could reach. Surfaces (c) and (d) are addressed only to establish whether the live product's own dependency on them is affected by any candidate lifecycle action; none of this document's candidates touches them.

## 6. Current Hypothesis Meaning

Tested against all four stated candidates plus the entity's own governing text (`atlas/core/domain/hypothesis/entity.py:1-9,48-55`; independently reconfirmed by `Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md`, Section 6.3, Classification D).

- **H-A — Provisional explanatory candidate.** Matches directly: the entity docstring states Hypothesis "is the investor's provisional belief about what something may mean," and "Atlas assigns no truth value, confidence, or conviction to a Hypothesis — those are explicitly out of scope" (own words, `entity.py:48-54`).
- **H-B — Workflow state.** Rejected as the primary characterization: Hypothesis is not merely a step marker: it carries genuine, permanent, semantically rich content (`Statement`) that outlives the conversational turn that produced it, unlike a pure state-transition record.
- **H-C — Analytical proposition with value outside the workflow.** Not supported: nothing in Hypothesis's own definition, or in any consumer found in Section 10, treats it as reusable analytical material; it has exactly one consumer (`FormHypothesisFromInterpretationService`), and that consumer only ever writes it, never re-reads it for analysis.
- **H-D — Proto-Observation or proto-Reasoning object.** Rejected: Observation's own definition (OE-002 §5.1) requires no commitment about settledness one way or the other, but Hypothesis is *explicitly, by its own governing text, not settled* — it is a candidate explanation awaiting Evidence, a different pragmatic role than "something noticed." Reasoning Trace (OE-002 §5.3) requires its supports to be *already-accepted* Domain Objects (INV-005); Hypothesis is neither accepted into any Case (it has no `case_id` at all) nor itself a canonical Domain Object. Casting Hypothesis directly as either would assert a settledness or acceptance status the object itself disclaims.

**Selected: H-A.** The current REST API (create/list/get, no `case_id`, no update) is consistent with this meaning: it captures a freestanding provisional belief and preserves it verbatim, with no mechanism that would falsely suggest settlement (no "confirm" or "accept" endpoint exists). This is the same conclusion the governing investigation reached (Classification D — "distinct unresolved meaning"), independently re-derived here for the API-lifecycle question specifically rather than assumed from that prior finding.

## 8. Current Evidence Meaning

Tested against all seven stated candidates plus the entity's own governing text (`atlas/core/domain/evidence/entity.py:1-16,53-62`; `value_objects.py:43-54`).

- **E-A — Unresolved workflow material, no support claim.** Rejected as stated: Evidence's own `direction: Direction` field *does* record an explicit support/challenge stance — it is not merely undifferentiated material.
- **E-B — Accepted support/challenge assertion.** Closest match, with one necessary precision: "accepted" must be read as *the investor's own declared stance within their own reasoning*, never as OE-006 Case-acceptance — Evidence carries no `case_id` and is never accepted into any Case. With that reading, E-B matches directly: the `Direction` enum's own docstring states "Evidence influences reasoning; it does not determine truth — there is no PROVES, DISPROVES, TRUE, FALSE... here or anywhere else in this aggregate" (`value_objects.py:44-51`), and the entity docstring states Atlas "preserves that the investor regarded this information as evidence, not that the information proves or disproves anything" (`entity.py:4-6`).
- **E-C — Container for source material.** Partially present (the optional `source` field) but not primary: `source` is optional context, not Evidence's defining role: the `direction` field, not `source`, is what every test and every consumer treats as load-bearing.
- **E-D — Legacy reasoning node connecting Hypothesis and Conclusion.** Rejected as Evidence's *own* meaning: the connective role is carried entirely by `HypothesisEvidenceLink`, a separate bridge entity with no `direction` field of its own (confirmed `reasoning_link/entity.py:137-165`) — conflating the two would misattribute a bridging responsibility to the standalone aggregate itself, exactly the confusion this investigation's own instructions warn against.
- **E-E — Proto-Knowledge Reference.** Rejected: Knowledge Reference (OE-002 §5.2) requires its target to be *already accepted* as a Domain Object; Evidence's raw statement is inline content, not a reference to anything, and Evidence itself is not an accepted Domain Object.
- **E-F — Proto-Reasoning Trace support.** Rejected as a direct equivalence for the same INV-005 reason given for Hypothesis in Section 6, and doubly rejected for the `CHALLENGES` direction, since Reasoning Trace has no opposition/undermine role at all (`Reasoning-Trace-Implementation-Design.md`, quoted directly in `Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md` Section 6.4: "Reasoning Trace, as adopted, has no 'undermine' or 'challenge' role at all").
- **E-G.** Not required; E-B, read with the precision above, is sufficient.

**Selected: E-B** (with the "investor-declared, not Case-accepted" precision stated above). This corrects the prior Reconciliation Investigation's own framing only in emphasis, not substance: that document reached the same substantive conclusion by splitting Evidence's classification by direction (B for `SUPPORTS`, D for `CHALLENGES`) at the *canonical-correspondence* level; this document's E-B selection concerns Evidence's *own intrinsic meaning* (which is uniform across both directions — a declared support-or-challenge stance, full stop) and defers the direction-specific canonical-correspondence asymmetry to Section 13, where it belongs. The `SUPPORTS`/`CHALLENGES` value itself is not a separate reasoning-link direction or relation — confirmed directly: `HypothesisEvidenceLink` (`reasoning_link/entity.py:137-165`) has no `direction` field; `SUPPORTS`/`CHALLENGES` exist exclusively as (a) `Evidence.direction`'s two enum values (`value_objects.py:53-54`) and (b) free-text keyword targets in `conversation/prompts.py:59-71`'s `parse_direction`, which only ever feeds the same `Evidence.direction` field via the in-process orchestrator.

## 11. Public versus Internal Classification

"Public" is established here by direct trace of `atlas/core/infrastructure/api/app.py:53-73`: `create_app()` calls `app.include_router(hypothesis_router)` (line 59) and `app.include_router(evidence_router)` (line 60) unconditionally, with no feature flag, no environment gate, and no dependency override in production code — both are mounted into the exact same `FastAPI` instance as every canonical router (`case`, `decision`, `observation`, `knowledge_reference`, `judgment`, `reasoning_trace`). A repository-wide search for authentication/authorization code (`APIKeyHeader`, `OAuth`, `HTTPBearer`, `authenticate`, `current_user`, `get_current`, etc.) across `atlas/core/` returned **zero matches** — there is no meaningful authorization layer anywhere in Atlas Core today, for any router, canonical or legacy. Both `/hypotheses` and `/evidence` are therefore genuinely **public HTTP surfaces**, reachable by any client that can reach the process, structurally indistinguishable in shape (id + statement + timestamps, 201-with-object) from the canonical endpoints' own responses — confirmed directly by comparing `HypothesisResponse`/`EvidenceResponse` against `ObservationResponse`. Both are exercised in their own tests via `fastapi.testclient.TestClient` hitting the real, fully-assembled `create_app()`, not a stub — this is integration-level, not merely internal-application-service, test coverage. No CLI command invokes either HTTP route (the CLI drives the orchestrator's in-process services, never HTTP); neither router is imported by any other package outside its own module, its own tests, and `app.py`'s own mounting.

## 14. API Safety Audit

Tested directly, including attempts to construct concrete invalid states through the actual test client and the actual application services (see also the existing tests cited below, which already exercise several of these paths).

- **Case ownership**: not applicable in the failure sense — neither object has a `case_id` concept to violate. But this is itself the safety-relevant fact: **every direct-API-created Hypothesis or Evidence is structurally an orphan**, with no way for any reader of the API response to tell it apart from a Hypothesis/Evidence that arose from a real, in-progress conversation. Confirmed reachable through mounted HTTP: **yes** (`POST /hypotheses`, `POST /evidence`, no precondition).
- **Prior-object validation**: the direct API performs **none** — `CreateHypothesisRequest`/`CreateEvidenceRequest` (`schemas.py` for each) take no `interpretation_id`/`hypothesis_id` at all, unlike the internal composites (`FormHypothesisFromInterpretationService`, `CaptureEvidenceFromHypothesisService`), which each verify their one upstream reference exists before delegating. The public API bypasses this validation entirely because it calls `HypothesisService`/`EvidenceService` directly, never the composite. Classification: **reachable through mounted HTTP**, and it is the *defining* behavior of this surface, not an edge case.
- **Cross-Case contamination**: not constructible in the traditional sense (no Case field exists to contaminate) — but the practical analog, "an orphan record indistinguishable from a real conversational one," is always constructible, as above.
- **Orphan creation**: **always possible, and is literally the API's only capability** — confirmed by inspection: no code path from the direct HTTP layer ever creates the accompanying `InterpretationHypothesisLink`/`HypothesisEvidenceLink`. Classification: **possible and reachable through mounted HTTP; semantically it is exactly what this surface does, not a misuse of it.**
- **Arbitrary ID mixing**: not applicable — neither create endpoint accepts any upstream ID at all.
- **Duplicate behavior**: unrestricted — no uniqueness constraint on either table (matches the rest of this codebase's convention); repeated identical requests each create a new, distinct row, exactly as intended for an insert-only aggregate.
- **Permanence**: consistent with the rest of the system — insert-only, no update/delete path anywhere.
- **Authentication / authorization**: **none exists anywhere in the application** (Section 11) — this is a repository-wide characteristic, not something specific to Hypothesis/Evidence.
- **Enumeration/list exposure**: `GET /hypotheses` and `GET /evidence` return *every* row ever recorded, across every conversation, with no pagination and no scoping — confirmed directly (`router.py`'s `list_hypotheses`/`list_evidence` call `service.list_all()` unconditionally). **This is not unique to Hypothesis/Evidence**: `GET /observations` exhibits the identical pattern (`observation/router.py:51-55`, `repository.list_all()` with no Case filter) — this is a systemic, repository-wide characteristic of the current (near-total absence of an) authorization model, not a defect specific to the legacy objects under investigation here, and this document does not overstate it as such.
- **Transaction boundaries**: each create is one repository `add()` call, consistent with every other aggregate in this codebase; no partial-write state is possible.

**Distinguishing structural fact, not shared with Observation**: `CreateObservationRequest` *requires* `case_id` as an explicit field (`observation/router.py:41`, `payload.case_id`) even though the router does not verify that Case's existence before writing — Observation's public API is at least structurally anchored to a Case identifier. Hypothesis's and Evidence's public APIs require no structural anchor of any kind, because neither object's domain model has one to require. This makes Hypothesis/Evidence orphan creation a strictly *lower-friction* action than Observation orphan creation, though neither is prevented today.

**Overall classification**: no *confirmed current security defect* exists — there is no authorization model anywhere in this application for the direct API to violate, and no live data (conversational or canonical) is corrupted, overwritten, or exposed across a boundary that exists elsewhere in the system but not here. The genuine, disclosed concern is narrower and different in kind: **legacy-workflow-API integrity** — a caller of the public API can produce records that look, in shape, identical to ones produced by a real conversation, with nothing in the response distinguishing the two. This is classified as **a reason for legacy classification/disclosure (Section 19–21), not a reason for restriction, and not a confirmed security defect requiring separate urgent security work.**

## 15. SUPPORTS and CHALLENGES Audit

Confirmed directly by a repository-wide search (`grep -rn "SUPPORTS\|CHALLENGES"`): the two terms exist **exclusively** as (a) the two literal values of the `Direction` enum on the Evidence entity itself (`atlas/core/domain/evidence/value_objects.py:43-54`), and (b) free-text keyword targets in `atlas/core/application/conversation/prompts.py:59-71`'s `parse_direction`, which maps investor words ("support"/"yes"/"challenge"/"no"/etc.) onto the same two string values before they are ever passed to `EvidenceService`. There is **no separate link type, no separate endpoint, and no reasoning-link field** carrying direction — confirmed directly by reading `HypothesisEvidenceLink` (`reasoning_link/entity.py:137-165`), which has exactly four fields (`link_id, hypothesis_id, evidence_id, linked_at`) and no direction field of any kind. `SUPPORTS`/`CHALLENGES` therefore is not an independent surface requiring its own bounded decision separate from Evidence's own lifecycle — it is entirely and exclusively Evidence's own `direction` field, fully addressed by whatever this document decides for Evidence as a whole (Section 21).

Direction is not Case-bound (Evidence has no `case_id`), is not an accepted claim in the OE-006 sense, and is purely workflow mechanics in the sense that it records the investor's own declared stance, nothing more. It does not overlap with Reasoning Trace's support semantics (Section 13 — Reasoning Trace requires already-accepted same-Case targets; Evidence's direction is asserted on unaccepted, standalone content) and does not overlap with Judgment (Judgment characterizes an identified subject; Evidence's direction characterizes a relationship to "a line of reasoning" in the abstract, not an identified Domain Object). No live consumer reads `direction` back out for any downstream decision — `decision_timeline` and every other read-side consumer checked in Section 12 does not reference Evidence at all. Direct API creation with an arbitrary direction string is safe in the narrow sense that `Direction.coerce()` rejects any value outside `{SUPPORTS, CHALLENGES}` — confirmed by the existing, passing test `test_invalid_direction_is_rejected` (`test_router.py:70-72`, expects 400 for `"PROVES"`).

## 16. API Contract and Compatibility Audit

A repository-wide search found: **no API versioning scheme** (no `/v1/`, no `api_version` field, no matches for either); **no OpenAPI `deprecated=True` flag anywhere** in `atlas/core/`; **no CHANGELOG file** at the repository root; **no OpenAPI export or SDK-generation mechanism** anywhere (`grep` for `openapi.json`, `generate_openapi`, `sdk` — zero matches outside this document's own search). Atlas Core has never released an external version, has no confirmed production users of its REST layer, and has no generated SDK or persisted external integration — confirmed by the same negative evidence the governing investigation already established for D4 and independently reconfirmed here.

Atlas **does** have an established, working deprecation practice — but it is CLI-local, not REST-local: `atlas/cli/deprecations.py` defines a `DeprecatedCommand` dataclass (`command`, `message`, `replacement_command`, `consolidation_direction`, `legacy_module`, `removal_criteria`) and a `_RETIRED_REGISTRY` for fully-removed commands, documented in parallel at `docs/DeprecatedCommands.md`. That module's own docstring states explicitly: "it is CLI-local and must stay that way" — it cannot be directly reused for a FastAPI router without creating a new, analogous module; no such REST-level equivalent exists today. This precedent is cited here as evidence that Atlas has organizational vocabulary and practice for staged retirement (a message, a stated replacement or consolidation direction, and explicit removal criteria), which a future REST-level mechanism could mirror in spirit, not as something this document's own recommended package (Section 22) needs or uses directly.

## 24. Canonical Authority Model

- **Hypothesis** remains authoritative for: the investor's own provisional, unsettled explanatory belief, verbatim, exactly as captured — nothing else asserts or preserves this fact.
- **Evidence** remains authoritative for: the investor's own declared support-or-challenge stance toward a line of reasoning, verbatim — nothing else asserts or preserves this fact.
- **Observation** is authoritative for: informational content preserved without a truth commitment, Case-owned, root-eligible.
- **Reasoning Trace** is authoritative for: which already-accepted, same-Case Domain Objects provide epistemic support for itself.
- **Knowledge Reference** is authoritative for: that the Case relies on one already-accepted Domain Object as knowledge.
- **Canonical APIs**: `/cases`, `/decisions`, `/decisions/{id}/context`, `/observations`, `/knowledge-references`, `/judgments`, `/reasoning-traces`.
- **Legacy APIs** (this document's own classification): `/hypotheses`, `/evidence`.
- **Workflow-internal, no API surface at all**: `InterpretationHypothesisLink`, `HypothesisEvidenceLink` (and the other two `reasoning_link` bridges), addressed only by application-service callers, never by any router.
- **No semantic dual authority remains or is created by this decision**: Hypothesis and Evidence do not compete with any canonical object over the same fact (Section 13 — no canonical object asserts what either preserves). "Legacy" here means *non-canonical for Atlas Core's own closed Domain Object Set*, not incorrect or inferior — each remains fully authoritative for its own workflow role, exactly as the Doctrine's own terminology discipline requires (Section 14 of the Doctrine: status terms must not be read beyond their stated scope).
