# Observation Implementation Design

## 1. Title

Atlas Core — Observation Implementation Design (design-only; no implementation performed).

## 2. Design Status

Engineering implementation-design artifact. Not a normative document; carries no Doctrine status. ## 3. Executive Finding

**Outcome 1 — Implementation design approved and ready for implementation.** Observation already exists in this repository as a partially-correct, pre-Domain-Object-Architecture implementation (`atlas/core/domain/observation/` and its four sibling layers, from the legacy API-003 increment) that already, correctly satisfies OE-002 §5.1's truth-independence and content-preservation contract but lacks `case_id` (the one binding correction identified by the committed review, `Observation-Architecture-Review.md` §32, Correction 2). This design specifies the exact, complete, minimal extension of the existing implementation to add `case_id` throughout every layer, adopts the corrected ontology statement (Correction 1) as this design's own governing formulation, retains every other existing field (`subject`, `observed_at`, `source`, `note`) unchanged and unremoved (no authority exists in this package to alter them), and finds no blocking question, no contradiction with the Implementation Architecture Approval, and no unsafe or speculative design choice. One genuine, disclosed, non-blocking operational matter is identified and correctly separated from architecture: whether any existing local `observations` rows need a data-level `case_id` backfill is a deployment/data-policy question outside this design's own scope, exactly as already established for every other `case_id`-added correction in this series.

## 10. Exact Domain Model

**Module**: `atlas/core/domain/observation/entity.py` (existing path, modified).
**Class**: `Observation`, `@dataclass(frozen=True)` (unchanged mechanism, unchanged name).
**Field order** (dataclass-valid: no-default fields precede default fields): `id: ObservationId`, `case_id: CaseId` (new — imported from `atlas.core.domain.case.value_objects`, reused directly, not reinvented, exactly as Knowledge Reference and Judgment already import it), `subject: Subject`, `statement: Statement`, `observed_at: datetime`, `recorded_at: datetime`, `source: str | None = None`, `note: str | None = None`. `case_id` is placed immediately after `id`, matching the identical field-ordering convention already used by Knowledge Reference (`id, case_id, target, recorded_at`) and Judgment (`id, case_id, characterization, recorded_at, subject=None`) — ownership immediately follows identity.
**Constructor/factory**: `Observation.capture(*, case_id: CaseId, subject: Subject, statement: Statement, observed_at: datetime, source: str | None = None, note: str | None = None, clock: _Clock = _utc_now) -> Observation` — the existing classmethod, extended with one new required keyword-only parameter (`case_id`), positioned first among the keyword arguments to mirror the entity's own field order; `id` and `recorded_at` continue to be generated internally, never accepted as parameters (unchanged).
**Immutability mechanism**: unchanged — `@dataclass(frozen=True)`.
**Nullability**: `case_id` is non-nullable (no default), matching `id`, `subject`, `statement`, `observed_at`, `recorded_at`; `source`/`note` remain nullable/optional (unchanged).
**Equality/hashing**: unchanged — default, field-by-field dataclass equality (no custom `__eq__`/`__hash__`), which already, correctly gives content-identical-but-distinct Observations an unequal comparison because `id` is always fresh per `capture()` call and participates in the comparison.
**Serialization responsibility**: unchanged — the domain entity itself performs none; `ObservationResponse.from_domain` (API layer) remains solely responsible.
**Validation responsibility**: unchanged split — `Subject`/`Statement`'s own `__post_init__` own their own non-emptiness checks (unchanged); `Observation.__post_init__` continues to own `observed_at`'s timezone-awareness check and `source`/`note`'s blank-normalization (unchanged); `case_id` requires no additional validation beyond being a `CaseId` instance (no `CaseRepository` existence check — Section 14).

## 12. Atomic-Content Representation

`statement`'s implementation meaning, fixed by this design (unchanged from current code, confirmed correct against the binding ontology): **type** — `Statement`, a `@dataclass(frozen=True)` value object wrapping `value: str` (not a bare string on the entity itself, not a richer structured type). **Whitespace** — leading/trailing stripped in `__post_init__` (existing, unchanged); internal whitespace and line breaks preserved verbatim. **Empty strings** — rejected (`MissingStatementError`, existing, unchanged). **Whitespace-only strings** — rejected, identically (the `.strip()`-then-falsy check already treats these the same as empty). **Maximum size** — not enforced; none is added, since none is canonically forced and inventing one would exceed this design's authority. **Line breaks** — allowed; no restriction exists or is added. **Structured JSON** — not a distinct, parsed content type; a caller may place JSON-formatted text inside the string, but no parsing, validation, or special handling of it is added. **Binary data** — not supported; the field is `str`-typed. **Markup** — allowed as plain text; no HTML/markdown parsing, stripping, or validation is performed. **Language/encoding** — not tracked; no field is added for either. **Domain validation of semantic atomicity** — **not performed, and cannot be safely performed mechanically.** The domain enforces only structural non-emptiness (a real, mechanical, always-correctly-checkable property); whether a given `statement` value actually represents "one atomic informational item" versus an unbounded compound document (per the accepted cardinality rule) is **authoring discipline**, not something `Statement`'s own validation can or should attempt to detect — there is no general, safe algorithm for deciding how many "claims" a block of text contains, and inventing a heuristic one would itself be an unauthorized, speculative addition. **The exact boundary**: structural validation = non-empty, stripped string, unbounded length, unbounded line count; semantic atomicity = the capturer's own responsibility at the moment of choosing what to preserve as one Observation's content, exactly as already correctly established and accepted for Judgment's own free-text `characterization`. `Statement` is an **opaque preserved expression**, never an assertion interpreted by Atlas — its own class carries no truth/reliability/confidence/authority field, and no validation logic inspects its content for truthiness, ensuring the binding ontology's own truth-independence is never smuggled around at the field level.

## 13. Identity and Permanence

**`ObservationId` creation**: unchanged — `field(default_factory=uuid.uuid4)` on the existing `ObservationId` value object, assigned fresh inside `Observation.capture()`. **Caller-supplied IDs**: not permitted, matching the uniform, already-approved convention across Case, Knowledge Reference, and Judgment — no code path in this design accepts a caller-supplied id. **ID generation location**: the domain entity's own `capture()` classmethod (unchanged) — neither the service layer nor the API layer generates it. **Content update**: no — the frozen dataclass and the insert-only repository together prohibit it; no `update` method is added anywhere. **Metadata update**: no, for the identical reason. **Corrections create new Observations**: yes — matching the identical, already-established discipline for Judgment ("a revised assessment is a new, separate Judgment"), reused here by direct structural analogy since INV-009/011 apply identically to every Domain Object. **Duplicate semantic content**: permitted — no uniqueness constraint on `statement`, `subject`, or any combination thereof is added, matching the identical, twice-established precedent for Knowledge Reference and Judgment. **Duplicate IDs**: rejected by the persistence layer's own primary-key constraint (unchanged); this design does not add a duplicate-primary-key test beyond what already exists (none, across every module in this repository, per the Implementation Architecture Approval's own §21/24 finding) — adding one is a legitimate, optional future test-coverage improvement, not required by either binding correction, and not performed by this design. **Deletion**: no — insert-only, unchanged, confirmed by the unchanged repository Protocol (Section 17). **Supersession**: only in the general, non-erasing INV-011 sense already available to every Domain Object (a later Observation MAY supersede practical relevance without erasing an earlier one) — no dedicated `supersedes` field is added. **Invalidation**: no dedicated mechanism exists or is added; a later determination that an Observation's content was wrong is itself recorded as a separate, later fact (e.g., a future Judgment characterizing it), never a mutation. **The approved permanence model is applied exactly, with no Observation-specific mutation lifecycle introduced.**

## 14. Case Ownership

**Domain**: add `case_id: CaseId` to `Observation` (Section 10). **Repository protocol**: `atlas/core/domain/observation/repository.py` — **no signature change required**; `case_id` travels as part of the `Observation` object passed to `add()` and returned by `get()`/`list_all()`, exactly as it already does for Knowledge Reference and Judgment's own Protocols, which needed no method-signature change when their own `case_id` fields were added. **Application layer**: `CaptureObservationRequest` (`atlas/core/application/observation/capture_observation.py`) gains `case_id: uuid.UUID` (new, required, no default — inserted as the first field, mirroring the entity's own ordering); `CaptureObservationService.capture()` gains one new line, `case_id = CaseId(request.case_id)`, and passes it into `Observation.capture(case_id=case_id, ...)` — matching exactly the wrapping pattern already used by every other module's own service. **Persistence table**: `atlas/core/infrastructure/persistence/observation/table.py` — add `Column("case_id", String, nullable=False, index=True)`, positioned immediately after `observation_id`, matching Knowledge Reference's and Judgment's own column-ordering convention. **Persistence mapper**: `atlas/core/infrastructure/persistence/observation/sqlalchemy_repository.py` — `_to_row` gains `"case_id": str(observation.case_id)`; `_to_observation` gains `case_id=CaseId(uuid.UUID(row["case_id"]))`. **API request**: `CreateObservationRequest` (`schemas.py`) gains `case_id: uuid.UUID` (required, serializes as `caseId`). **API response**: `ObservationResponse` gains `case_id: uuid.UUID` (required, `caseId`), and `from_domain` gains `case_id=observation.case_id.value`. **Tests**: all four existing Observation test files require `case_id` added to every construction call and assertion (Section 25).

**Validation behavior, specified exactly**: **Case does not exist** — not validated, by design, matching the uniform, already-approved convention (Implementation Architecture Approval §9): no module in this codebase verifies Case existence via a `CaseRepository` call, and Observation's own correction does not introduce the first exception to that convention without a governing reason to do so (none exists — OE-002 §3.1/INV-002 require ownership, not existence-verification by the referencing module). **Case identifier malformed** — rejected by Pydantic at the API boundary (422), identical to every other module's own `case_id: uuid.UUID` field handling; no domain-level check is added. **Case exists but is not accepted** — not a representable state in the current architecture: Case carries no acceptance-status field of any kind (`id`, `recorded_at` only), and OE-006 §9 forecloses any intermediate/deferred acceptance state generally — this scenario is inapplicable, not merely unhandled. **Persistence row with a missing Case reference** — prevented for every future insert by the `NOT NULL` constraint; for rows already persisted before this correction ships, this state already, actually exists today and is addressed by the migration/compatibility plan (Section 27), not silently ignored. **Legacy Observation lacking `case_id`** — identical treatment, addressed in Section 27.

**Migration/compatibility policy required**: yes — a genuine, disclosed data question (Section 27), correctly separated from this design's own, fully-specified code-level shape.

**INV-002 validation is not deferred**: the combination of the domain's own non-nullable `case_id` field and the persistence layer's own `NOT NULL` column together structurally guarantee that no future write can omit Case ownership — enforcement is immediate and unconditional from the moment this correction's code lands, not phased in or optional.

## 15. Root Eligibility

Confirmed, unchanged from the committed review: **Observation's accepted minimum has zero outgoing Domain Object references** — `case_id` is ownership, not a semantic reference to another Domain Object, and no field among `subject`, `statement`, `observed_at`, `source`, `note` is or becomes a `TypedDomainObjectReference`. **Acceptance requires only**: valid Observation fields (non-empty `subject`/`statement`, a timezone-aware `observed_at`, `source`/`note` blank-normalization — all existing, unchanged) and an owning `case_id` value (structurally present and well-formed, per Section 14 — never independently existence-checked). **No prior accepted Domain Object of any kind is required.** No source validation beyond the existing optional/blank-normalize handling. No subject validation beyond the existing non-empty-string check. No `observed_at` validation beyond the existing timezone-aware-datetime check. No additional dependency of any kind.

**Distinctions, stated precisely**: **Case ownership validation** = "is `case_id` structurally present and well-formed" (enforced, Section 14). **Prior-Domain-Object-reference validation** = inapplicable; Observation has none to verify. **Canonical root eligibility** = unconditional yes, unchanged (OE-002 §5.1, INV-012) — structural, not form-dependent (unlike Judgment/Decision/Outcome). **Current capture availability** = becomes fully INV-002-conformant once this correction ships; **this is exactly what this package enables** — closing the one remaining gap between "Observation already works" and "Observation is a fully conformant Case member." **This package does not enable Observation as a verifiable *target* for Knowledge Reference or Judgment** — that is a distinct, future change to Knowledge Reference's and Judgment's own `_CURRENTLY_CAPTURE_ENABLED_*` frozensets, entirely outside this package's own scope, performed (if ever) by a future correction to *their* own modules, not to Observation's.

## 17. Repository Protocol

**Path**: `atlas/core/domain/observation/repository.py` (existing, **unchanged** — no method signature requires modification). **Methods, confirmed retained exactly as currently implemented**: `add(observation: Observation) -> None`; `get(observation_id: ObservationId) -> Observation | None`; `list_all() -> list[Observation]`. **Synchronous** (matches every module). **Return types**: unchanged. **Not-found behavior**: `get` returns `None` (unchanged); the API router continues to translate this into a 404 (Section 20). **Duplicate behavior**: governed by the persistence layer's own primary-key constraint, unchanged. **Accepted-object lookup**: `get` by id only, unchanged — no Case-scoped lookup method is added; none is canonically required, and adding one would be an unauthorized, speculative query method (explicitly forbidden by this task's own instruction). **List behavior**: `list_all()` is retained exactly as currently implemented (oldest `recorded_at` first) — this is a **pre-existing asymmetry** relative to Case/Knowledge Reference/Judgment's own narrower Protocols (none of which exposes a list method) that predates this whole series and is **not removed by this design**, since removing it is not required by either binding correction and would exceed this package's own authority under the identical "do not silently remove" discipline already applied to fields in Section 10. **Update/delete**: confirmed prohibited, confirmed absent, unchanged.

**Reuse**: the `add`/`get` shape is identical to Case's, Knowledge Reference's, and Judgment's own Protocols; `list_all` remains Observation-specific, reused from itself (its own pre-existing convention), not borrowed from or extended to any other module.

## 18. Application Service

**Path**: `atlas/core/application/observation/capture_observation.py` (existing, modified). **Class name**: `CaptureObservationService` — **retained unchanged**, not renamed to match the `XService` convention used by `CaseService`/`KnowledgeReferenceService`/`JudgmentService`; renaming is not required by either binding correction, and doing so "merely for symmetry" is exactly what the Implementation Architecture Approval's own §25 explicitly warns against. **Dependencies**: `ObservationRepository` only — **no second collaborator repository is added**, since Observation has no outgoing reference requiring cross-repository verification (Section 15), unlike Judgment's own, genuinely necessary dependency on `KnowledgeReferenceRepository`. **Input parameters**: `CaptureObservationRequest` gains `case_id: uuid.UUID` (Section 14); existing `subject: str, statement: str, observed_at: datetime, source: str | None = None, note: str | None = None` retained unchanged. **Generated values**: `id` and `recorded_at`, both generated inside `Observation.capture()` (domain layer), unchanged — never generated at the service layer. **Validation sequence, exact**: (1) `case_id = CaseId(request.case_id)` — structural wrapping only, no existence check; (2) `Subject(request.subject)`, `Statement(request.statement)` — existing value-object construction, triggers `MissingSubjectError`/`MissingStatementError` on blank input, unchanged; (3) `Observation.capture(case_id=case_id, subject=..., statement=..., observed_at=request.observed_at, source=request.source, note=request.note)` — triggers `InvalidObservedAtError` and blank-normalization internally, unchanged; (4) `self._repository.add(observation)`; (5) return the captured entity. **Repository calls**: exactly one, `add` — unchanged. **Case verification**: none, matching Section 14's own established precedent. **Error propagation**: unchanged — value-object/entity construction errors propagate uncaught through the service to the API's own error handler. **Transaction responsibility**: the repository's own `add()` (unchanged, `with self._engine.begin()...`). **Return value**: the captured `Observation` entity, unchanged.

**Pattern determination**: **Observation follows the Case pattern (single repository, no cross-aggregate verification), not the Knowledge Reference/Judgment pattern** — because Observation has no outgoing reference to verify, the `_verify_target`/`_verify_subject` shape is categorically inapplicable here, not merely unneeded. **This does not create a third repetition of that pattern** — a third repetition would require a third object with a genuine outgoing reference and capture-availability gating; Observation has neither. **No extraction is warranted, and none is performed.** This finding positively confirms, rather than strains, the Implementation Architecture Approval's own §25 conclusion: the `_verify_*` pattern generalizes correctly only to objects that actually need it, and Observation's own correction is direct, further evidence that the pattern's boundary is being applied correctly, not evidence that it should be forced onto every module regardless of need. No refactor is performed in this design task.

## 19. Validation Sequence

Restated as its own required section, precisely: (1) API layer — Pydantic validates request shape, `case_id`/`observedAt` types, and required-field presence (422 on failure, before any domain code runs); (2) application layer — `CaseId(request.case_id)` wraps without validating existence; (3) domain layer, value objects — `Subject`/`Statement` reject blank input; (4) domain layer, entity `__post_init__` — `observed_at` timezone-awareness checked, `source`/`note` blank-normalized; (5) domain layer, `capture()` — identity and `recorded_at` assigned; (6) application layer — `repository.add()` persists atomically. No step is skipped, reordered, or deferred relative to this sequence for any input.

## 20. Error Taxonomy

**Reused, unchanged**: `ObservationError` (base), `ObservationValidationError` (base for structural failures, →400 via the existing registered handler), `MissingSubjectError`, `MissingStatementError`, `InvalidObservedAtError` (all existing, all subclass `ObservationValidationError`, all unchanged).

**`case_id`-related failures**: malformed `case_id` → Pydantic 422 at the API boundary (no domain error, matching every other module's `case_id: uuid.UUID` handling); no Case-existence check exists, so no `CaseNotFoundError` is added (Section 14).

It is recorded here precisely as a non-blocking risk (Section 32), available for a future, separate, explicitly-scoped cleanup task, not this one.

**Duplicate Observation identifier**: persistence-layer `IntegrityError` via the primary-key constraint, unchanged, no new domain error (matches the already-acknowledged, untested-everywhere gap noted in the Implementation Architecture Approval — not worsened, not fixed, by this design). **Malformed optional timestamps**: existing `InvalidObservedAtError`, unchanged. **Malformed optional source/note**: none — both are permissively blank-normalized, never rejected; no new error is needed. **Unsupported content structure**: not applicable — `statement` has no structural type beyond non-empty string (Section 12). **Legacy row missing `case_id`**: a migration-sequencing responsibility (Section 27), not a new runtime domain error — once the `NOT NULL` constraint is live, no legacy-shaped row can be read by the corrected mapper without the migration having already run first. **Persistence conversion failure, repository failure**: infrastructure-level, unchanged, not domain errors.

**No genuinely new Observation-specific domain error is required.** The existing taxonomy, unchanged, already correctly covers every applicable failure mode once `case_id` is added.

**API mapping, unchanged**: `ObservationValidationError`→400; not-found→404 (existing raw `HTTPException`, unchanged); malformed shape or malformed `caseId`→422 (Pydantic).

## 21. Persistence Design

**Table**: `observations` (unchanged name). **Columns** (final shape): `observation_id` (PK, `String`, unchanged), `case_id` (**new**, `String`, `NOT NULL`, indexed), `subject` (`String`, `NOT NULL`, unchanged), `statement` (`String`, `NOT NULL`, unchanged), `source` (`String`, nullable, unchanged), `note` (`String`, nullable, unchanged), `observed_at` (`String`, `NOT NULL`, ISO-8601, offset preserved exactly, unchanged), `recorded_at` (`String`, `NOT NULL`, ISO-8601, always UTC, unchanged). **Primary key**: `observation_id`, unchanged. **Foreign keys**: none — matches the uniform, already-approved "no `case_id`→`cases` foreign key anywhere in this codebase" convention. **Indexes**: `case_id` gains an index, matching Knowledge Reference's and Judgment's own convention. **Uniqueness constraints**: none beyond the primary key — duplicate content and duplicate `case_id` combinations both remain permitted, unchanged. **Timestamp storage**: unchanged. **Statement storage**: unchanged, `String NOT NULL`. **Optional-field storage**: unchanged, nullable `String`. **Append-only**: unchanged. **Row mapper**: `_to_row`/`_to_observation` in `sqlalchemy_repository.py`, extended by exactly one field each (Section 14). **Repository implementation path**: unchanged file. **Initialization mechanism**: unchanged — direct schema initialization via `metadata.create_all(engine, tables=[observations_table])`, called from `create_observation_table(engine)`, invoked by the API dependency function — confirmed, again, in this design, as the repository's own uniform, actual convention; no formal migration tool exists anywhere in this repository. **No new migration framework is introduced.**

**Legacy rows, a genuine operational caveat correctly flagged**: SQLAlchemy's `metadata.create_all(...)` only creates tables that do not yet exist; it does **not** alter an already-existing table's schema. Adding a `NOT NULL` column without a default to an already-existing SQLite table that may already contain rows is **not** achievable by `create_all` alone, and SQLite's own limited `ALTER TABLE` support does not directly support adding a non-nullable column without a default value to a populated table — this requires either a hand-written table-rebuild sequence (create new table, copy+backfill data, drop old, rename) or, for a purely local/disposable development database, dropping and recreating the table. **This design specifies the target schema exactly (above) and flags this operational step precisely (Section 27, Section 28) — it does not perform it, and does not invent a production-scale migration requirement this repository provides no evidence for.**

**Unknown/unsupported stored values**: not applicable — Observation's schema has no enum-constrained column (unlike Knowledge Reference's/Judgment's own `target_type`), so no CHECK-constraint-style "unsupported value" scenario exists for it.

**No JSON representation is chosen** — the currently-adopted, already-correct scalar-text realization remains sufficient and is not speculative; **no generic metadata storage is added** — none has ontological authority (Section 11).

## 22. API Design

**Routes, unchanged**: `POST /observations` (201); `GET /observations` (200, list — pre-existing, retained, not part of the newer Case/Knowledge Reference/Judgment "no list route" convention, and not removed here, since removal is unauthorized by either binding correction); `GET /observations/{id}` (200/404). **Request schema** (`CreateObservationRequest`): gains `case_id: uuid.UUID` (required, `caseId`); retains `subject: str, statement: str, observed_at: datetime, source: str | None = None, note: str | None = None` unchanged. **Response schema** (`ObservationResponse`): gains `case_id: uuid.UUID` (`caseId`), positioned after `observation_id`/`observationId`; retains every other field unchanged.

**Field-by-field inclusion, exact rationale**: `id` — excluded from the request (server-generated, Section 13), included in the response as `observationId` (existing). `caseId` — **included in the request** (required; the capturer must specify the owning Case, matching Knowledge Reference's and Judgment's own `caseId` request field exactly) and **included in the response** (echoes the assigned ownership). `statement` — included in both (the canonical minimum's own semantic content). `recordedAt` — **excluded from the request** (technical, server-assigned acceptance time; per this task's own explicit instruction, and matching every other module's identical treatment, it must never be client-authoritative), **included in the response only**. `subject` — included in both (retained, required, unchanged). `observedAt` — included in both (retained, required, investor-supplied, unchanged). `source`, `note` — included in both, optional (retained, unchanged).

**Success status**: 201 (POST), 200 (GET), unchanged. **Error mapping**: unchanged (Section 20). **Router construction**: `router.py` unchanged in file/module identity; only the `CaptureObservationRequest(...)` construction inside `create_observation` gains `case_id=payload.case_id`. **Dependency injection**: unchanged (`get_observation_repository`/`get_capture_observation_service`, both continuing to reuse `get_decision_engine`). **Persistence dependency**: unchanged call site (`create_observation_table(engine)`); only the table definition itself changes (Section 21). **Application assembly**: **`app.py` requires no change** — Observation was already fully wired (router included, error handlers registered) when it first shipped, predating this whole series; this correction is a field-level change within already-wired modules, not a new module requiring new wiring, unlike Knowledge Reference's or Judgment's own first-time integration.

**Duplicate requests**: unsupported/non-idempotent, matching every other module — no idempotency key or deduplication mechanism exists anywhere in this codebase; two identical `POST` requests create two distinct, valid Observations, matching the already-established, twice-precedented "duplicate content permitted" principle. **No update or delete route is added.**

## 27. Migration and Compatibility Plan

**Existing rows without `case_id`**: a real, disclosed code-versus-data compatibility question. **Code-level compatibility** (this design's own responsibility) is fully specified: the corrected schema requires `case_id NOT NULL` going forward (Section 21); the corrected mapper (`_to_observation`) will unconditionally read `row["case_id"]`, so any row lacking that column becomes unreadable once the corrected code runs against it. **Operational/data-level compatibility** (explicitly outside this design's own scope, per the identical, already-accepted separation used for every other `case_id`-added correction in this series) is *not* resolved here: this repository provides no evidence of a deployed, production `observations` table with meaningful existing data — only a local, developer-owned SQLite file appears anywhere in this codebase's own tooling and tests. **This design does not invent a production data-migration requirement the repository provides no evidence for.** For a local/development database, the correct, minimal path is to treat the existing `observations` table as disposable and recreate it (matching the "additive-then-backfill, or drop-and-recreate for dev-only data" discipline already accepted in the Reconciliation Plan §15's own rollback section); for any environment where real data is later confirmed to exist, a hand-written, one-time table-rebuild script (create the corrected table, copy+backfill `case_id` per whatever policy is separately decided, drop the old table, rename) would be required — this design specifies the target shape precisely enough for that script to be written mechanically once a backfill policy is chosen, but does not choose that policy itself, since it is a data-policy decision, not an architectural one (matching the Reconciliation Plan's own already-flagged, still-open Q3).

**Existing `subject`/`observed_at`/`source`/`note`**: retained unchanged (Section 10); no compatibility action of any kind is needed for these four fields.

**Existing API clients**: the request contract gains a new required field (`caseId`) — a disclosed, intentional breaking change, exactly matching the identical, already-accepted precedent recorded in the Reconciliation Plan's own §16 API Reconciliation table for this exact correction ("Only `case_id` is added (DO-REC-026)").

**Existing fixtures**: the four existing Observation test files' own helper functions (`_new_observation`, `_request`, `_valid_payload`) must each gain a `case_id`/`caseId` default parameter (Section 25/26) — a mechanical, fully-specified change.

**Existing serialized representations**: any response body captured before this correction lacks `caseId` — an operational/documentation concern, not a code-level or architectural one, out of this design's own further scope.

**Current database initialization**: unchanged mechanism (`create_all`); see the `NOT NULL`-on-an-existing-table caveat (Section 21) — a genuine implementation-order concern (Section 28), not a design gap.

**Local development databases**: should be treated as disposable/recreatable absent evidence of real data worth preserving.

**Unsupported legacy data**: any row missing `case_id`, if the corrected code runs against a database that has not been migrated first, becomes unreadable (a `KeyError`/`TypeError` on read) — this is precisely why the migration step must run before or atomically with the corrected code's own deployment, never after (Section 28).
