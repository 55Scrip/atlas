# Evaluation-to-Judgment Reduction — Design (Package M2, Bounded Decision D1)

This document is a design-investigation artifact, not a normative document. It carries no Doctrine status (Draft/Final/Superseded/Historical) because those statuses apply to normative documents, and this is not one. It implements nothing, modifies no existing production file, test, or governing document. Where anything here appears to conflict with the Architecture Doctrine, OE-002 through OE-006, the Historical Decision Record, or the Judgment Implementation Design, those documents govern and this one is wrong and must be corrected.

**Audited.** This document has been independently audited following its initial draft: every consequential claim was re-verified against fresh governing-document reads and direct, line-cited code and test inspection, not merely proofread. The audit found the draft's central selection (Outcome as Judgment subject, verbatim `statement` as content, Disposition B for timestamps, L3 for Learning) correct and independently reconfirmed it, strengthened it with additional, previously-uncited evidence (the `Statement` value object's own docstring, the live `EVALUATION_PROMPT` text, `Statement`'s and `Characterization`'s own whitespace/non-emptiness guarantees), and disclosed one genuine complication the draft's field-level analysis alone had not surfaced: the actual, live test fixtures in this codebase's own decision-review test suite phrase the Evaluation statement as **"The decision proved correct"** — surface language naming the Decision, not the Outcome — which does not change the selected subject (Judgment's referential form does not require characterization text to grammatically name its subject) but is now explicitly disclosed rather than assumed away (Section 9). The audit also sharpened the duplicate-prevention and failure-model sections with a precise statement of exactly what is and is not guaranteed, including the explicit, disclosed fact that no retry mechanism exists for a failed Judgment capture. Required conclusion is unchanged: A. Corrections are marked inline where they occur.

## 1. Executive Finding

**Evaluation reduces to exactly one canonical Judgment per Evaluation, whose subject is the already-accepted Outcome it references, and whose characterization is Evaluation's own `statement`, copied verbatim with no invented wording.** This is not a new ontological finding — it is the same reduction the Historical Decision Record already recorded for the original, coarser-grained "Evaluation" candidate during OE-002's own founding investigation — but this document resolves it at the exact field level the earlier, coarser finding left unaddressed, and required by bounded decision D1 (Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md, Section 25, Section 21 Package M2).

Evaluation's own two decisive fields — `outcome_id` (a mandatory reference to an already-accepted, same-Case Outcome) and `statement` (a required, non-empty, free-text assessment anchored to that same Outcome) — map exactly onto Judgment's own two forced components (an optional typed subject reference, and a required characterization), with zero semantic invention required for the reference itself. This holds even though the statement's own *surface wording* may, in practice, colloquially reference "the decision" rather than "the outcome" (Section 9) — Judgment's referential form is established by the reference field, not by parsing the characterization text for a match. `evaluated_at` and `note` have no landing field in Judgment's actual, implemented shape (`id`, `case_id`, `characterization`, `subject`, `recorded_at` — no second timestamp exists) and remain permanently, honestly non-Core: they stay exactly where they already are, on the legacy Evaluation row, which this package neither deletes nor alters.

Learning does **not** reduce to Judgment in this package. Its content is a generalized, cross-Case-transferable heuristic, not a characterization of one specific identified same-Case object — forcing it into Judgment's shape would stretch that ontology past what OE-002 §5.4 was built to express, and no forcing function (Doctrine §8) requires it. Learning remains outside Core, exactly as it is today.

**Required conclusion: A — M2 is implementation-ready.** Every one of the twelve determinations this task requires resolves to exactly one answer, directly derivable from OE-002 §5.4's own text, Judgment's actual implemented field shape, and direct inspection of the live decision-review flow — none requires further human product-policy input, unlike M1's own D1 disposition question for `evaluated_at`, which this document now fully closes rather than merely restates. The one genuine complication this audit surfaced (surface phrasing that names the Decision rather than the Outcome) is a disclosed, honestly-stated nuance, not an unresolved semantic decision — the construction rule remains fully mechanical regardless of what any individual statement's surface wording happens to say.

## 2. Scope

This document determines whether, and exactly how, Package M2 (Judgment capture from the live decision-review Evaluation flow) can be specified completely enough that a later implementation task requires no further semantic decision. It does not implement Judgment capture. It does not modify Judgment's ontology, fields, persistence, or API. It does not modify any production file, test, or existing governing document. It does not resolve Learning's ultimate architectural home beyond stating that it remains outside Core for this package. It creates exactly one new file: this document.

## 4. Current Evaluation Meaning

`atlas/core/domain/evaluation/entity.py`: **"Evaluation is the investor's assessment of an Outcome: did it confirm or contradict what was expected, and why?"** Fields: `id: EvaluationId`, `outcome_id: OutcomeId` (mandatory), `statement: Statement` (required, non-empty), `evaluated_at: datetime` (required, tz-aware, preserved exactly as given — investor-supplied), `recorded_at: datetime` (Atlas's own UTC acceptance clock), `note: str | None` (optional, blank normalizes to `None`). Frozen dataclass, immutable, insert-only (`EvaluationRepository` has no update/delete method). `EvaluationService.capture()` (`atlas/core/application/evaluation/capture_evaluation.py`) verifies the referenced Outcome exists via a read-only lookup before constructing the Evaluation; never writes to `OutcomeRepository`. No `case_id` anywhere in the entity, table, or repository — Evaluation is not, and has never claimed to be, a canonical Domain Object (consistent with Legacy-Core-Loop-Canonical-Reconciliation-Investigation.md Section 1's own closed-set finding, reconfirmed here fresh). `EvaluationRepository.list_by_outcome_id` permits multiple Evaluations per Outcome — no uniqueness constraint.

**Audited directly against `atlas/core/domain/evaluation/value_objects.py`'s `Statement` value object** — its own docstring independently states: "The investor's assessment of an Outcome against what was expected," confirming the Outcome-directed framing from a second, independent source, not merely the entity's own docstring. `Statement.__post_init__` rejects `None`/whitespace-only text (`MissingStatementError`) and unconditionally `.strip()`s the surviving value before storing it — so `evaluation.statement.value`, by the time an Evaluation instance exists at all, is **already guaranteed non-empty and already whitespace-stripped**; this is a repository fact, not an assumption, load-bearing for Section 10's content-construction rule. Evaluation is "final" the instant it is captured (no draft/pending state exists in this codebase's own model), but it is not "accepted" in OE-006's own technical sense, since OE-006's acceptance model applies only to Domain Objects, and Evaluation is not one — it is simply permanent, immutable, ordinary stored data, exactly like every other legacy Core Loop aggregate.

**Audited directly against `atlas/core/application/decision_review/prompts.py`**: `OUTCOME_PROMPT = "Looking back, what actually happened?"`; `EVALUATION_PROMPT = "How did that compare to what you expected?"` — grammatically, "that" in the Evaluation prompt refers back to the Outcome just described, confirming the Outcome-directed framing a third time, from the actual live question text the investor answers, not merely from field shape or docstrings (Section 9 addresses one genuine complication this same audit uncovered in the actual test fixtures).

## 7. Judgment Semantic Capacity

Reused directly from `docs/atlas_domain_object_architecture/Judgment-Implementation-Design.md`, re-verified against the actual implemented entity (`atlas/core/domain/judgment/entity.py`): a Judgment is a permanent, Case-owned Domain Object recording the Case's settled characterization of an identified subject, without asserting objective truth (OE-002 §5.4). Its **actual, implemented** fields are exactly: `id: JudgmentId`, `case_id: CaseId`, `characterization: Characterization` (required, non-empty text), `subject: TypedDomainObjectReference | None` (optional; when present, selects the referential form — persisted as two columns, `subject_target_type`/`subject_target_id`, both null or both non-null), `recorded_at: datetime` (system acceptance clock — **the only timestamp Judgment carries**). `CaptureJudgmentRequest(case_id, characterization, subject=None)` and `JudgmentService.capture()` (`atlas/core/application/judgment/capture_judgment.py`) verify, when a subject is given, that it is same-Case (INV-004) and already accepted (INV-005) via `_verify_subject`, dispatching across all six adopted `DomainObjectType` members — Observation, Knowledge Reference, Judgment, Decision, Outcome, and Reasoning Trace are all currently capture-enabled subject types (confirmed: `_CURRENTLY_CAPTURE_ENABLED_SUBJECT_TARGET_TYPES` includes all six). No `TargetTypeUnavailableError` is reachable for any adopted type today. Judgment carries no rationale/narrative field, no status, no confidence, no source-object-id field of any kind (Section 28 of the Judgment Implementation Design) — this design does not propose adding one.

## 8. Live Review Runtime Trace

Traced directly from `atlas/core/application/decision_review/orchestrator.py`, `session.py`, and `composition.py`.

1. **Decision already exists** — selected via `DecisionReviewOrchestrator.select()`, a pure read against `DecisionRepository` (never written by this flow). `DecisionReviewSession(decision_id=...)` is constructed; it carries **no `case_id` field** — the only identifiers it carries are `decision_id`, `session_id`, `current_step`, `outcome_id`, `evaluation_id`, `learning_id`, `pending`.
2. **Outcome capture** (`_handle_outcome`) — `OutcomeService.capture(CaptureOutcomeRequest(decision_id=session.decision_id, statement=answer, occurred_at=_now()))`. Internally, `OutcomeService.capture()` fetches the Decision (read-only), derives `case_id=decision.case_id`, and writes canonical `Outcome`. On success: `session.outcome_id = outcome.id.value`; `session.current_step = EVALUATION`.
3. **Evaluation capture** (`_handle_evaluation`) — `EvaluationService.capture(CaptureEvaluationRequest(outcome_id=session.outcome_id, statement=answer, evaluated_at=_now()))`. Verifies Outcome exists (read-only). Writes legacy `Evaluation` (no `case_id`). On success: `session.evaluation_id = evaluation.id.value`; `session.current_step = LEARNING`.
4. **Learning capture** (`_handle_learning`) — `LearningService.capture(CaptureLearningRequest(evaluation_id=session.evaluation_id, statement=answer, learned_at=_now()))`. Verifies Evaluation exists. Writes legacy `Learning`. On success: `session.learning_id = learning.id.value`; `session.current_step = REVIEW_RECORDED` (terminal).
5. **Terminal review state** — `REVIEW_RECORDED` has no entry in `_HANDLERS`; `respond()` looks up `self._HANDLERS[session.current_step]`, which raises `KeyError` for this step, exactly the same structural guarantee already proven for M1's `ConversationStep.DECISION_RECORDED`.
6. **Retry/reprompt boundaries** — each of the three steps wraps its own service call in a bare `try/except Exception:` that reprompts at the **same** step on failure, without advancing `current_step` or setting the corresponding session id field. None of the three try/except blocks currently contains more than its own single service call.
7. **Repository transactions** — each of `OutcomeService.capture()`, `EvaluationService.capture()`, `LearningService.capture()` performs its own single, independent `engine.begin()` transaction (confirmed by each `SqlAlchemy*Repository.add()`); no transaction spans more than one of the three writes.

Per-step identity/Case/repeat table:

| Step | Object identity available | Case available | Accepted canonical subject available | May the step repeat for this session? | Would a later failure retry this step's own write? |
|---|---|---|---|---|---|
| Decision selection | `decision_id` | Yes, via Decision (read-only) | Decision itself | No — happens once, before any handler runs | N/A, read-only |
| Outcome | `outcome_id` | Yes, derived from Decision | Decision | No — `_HANDLERS[OUTCOME]` only reached once `current_step` is `OUTCOME`, and success advances past it | N/A under this design (Judgment is not placed here) |
| Evaluation | `evaluation_id` | Not on session; derivable via Outcome | Outcome | No — same reasoning as Outcome | N/A under this design |
| Learning | `learning_id` | Not on session; derivable via Outcome | Outcome (unchanged); Evaluation now also accepted, but not canonical | No — advances to terminal `REVIEW_RECORDED` on success | **Yes, this is where Judgment capture is placed (Section 17) — proven not to retry Learning or any earlier step** |

**Text flow diagram:**

```
[Decision]* (pre-existing, read-only) ──resolve case_id──► Outcome capture
                                                                 │
                                                                 ▼
                                                          [Outcome]* (case_id derived from Decision)
                                                                 │
                                                                 ▼
                                                            Evaluation capture (legacy, no case_id)
                                                                 │
                                                                 ▼
                                                              Learning capture (legacy, no case_id)
                                                                 │
                                                                 ▼
                                                    session.current_step = REVIEW_RECORDED (terminal,
                                                    no _HANDLERS entry — nothing can re-enter this flow)
                                                                 │
                                        ┌────────────────────────┘
                                        ▼
                          Judgment capture attempted here (Section 17):
                          subject = the already-accepted [Outcome]*,
                          characterization = Evaluation.statement,
                          case_id = Outcome.case_id (re-derived, read-only)
                          — own try/except, never retries Evaluation/Learning/Outcome.

* = canonical Domain Object.
```

## 9. Candidate Judgment Subjects

**Candidate A — Decision.** Evaluation's own mandatory reference field is `outcome_id`, never `decision_id` — there is no field anywhere on Evaluation that names or points at the Decision directly; there is no way to construct a Decision-directed reference without an extra, transitive hop through `Outcome.decision_id` that Evaluation's own fields do not themselves authorize. Evaluation's own docstring and `Statement`'s own docstring both independently frame its content as an assessment of the **Outcome** (Section 4). **Corrected by this audit — a genuine complication, not resolved by dismissal**: the actual, live test fixtures used throughout this codebase's own decision-review test suite (`tests/unit/application/decision_review/test_orchestrator.py`, `test_review_end_to_end.py`) capture the Evaluation step with the literal text **"The decision proved correct."** — surface phrasing that names "the decision," not "the outcome." This shows real Evaluation statements are not always grammatically Outcome-directed; investors may naturally phrase a retrospective assessment in terms of "the decision" even though the field structurally binds it to the Outcome. This does **not** change the rejection of Candidate A: Judgment's own referential form does not require the characterization *text* to grammatically name its *subject* — the subject is established by the reference field itself, exactly as it is for every other Judgment use elsewhere in this design (a Judgment characterizing an Observation need not say "this Observation..." in its own text either). What it does require is an explicit, disclosed acknowledgment (Section 4) that the resulting Judgment's characterization may read, in isolation, as being "about the decision" in surface language while its actual, structural subject is the Outcome — a divergence between phrasing and reference that is honest, not a contradiction, and does not by itself justify choosing Decision as the subject, since Evaluation still has no field that ever points at a Decision directly. **Rejected**, on the same structural ground as before, now with the phrasing nuance disclosed rather than assumed away.

**Candidate B — Outcome.** Evaluation's `outcome_id` is exactly a reference to an already-accepted, same-Case Outcome (Outcome carries `case_id` directly — confirmed, `atlas/core/domain/outcome/entity.py`). Evaluation's `statement` is exactly a characterization anchored to that same referenced Outcome, reinforced by three independent textual sources (Section 4: the entity docstring, the `Statement` value object's own docstring, and the live `EVALUATION_PROMPT` text), even though, as just disclosed, its surface phrasing may colloquially reference "the decision" rather than "the outcome." This is a direct, one-to-one structural match onto Judgment's own two forced components (subject reference, characterization) with zero invention required for the reference itself. **Accepted — selected as the primary model**, with the phrasing nuance above disclosed, not concealed.

**Candidate C — Reasoning Trace.** Evaluation carries no field referencing any Reasoning Trace, and the only live Reasoning Trace in this system (captured by M1, at Decision commitment) exists entirely upstream of, and causally unrelated to, the decision-review flow. No field-level evidence supports this candidate at all. **Rejected — no textual support.**

**Candidate D — Multiple Judgments.** Evaluation's entire content is one undifferentiated free-text `statement` field, with no internal structure separating "decision quality" from "outcome accuracy" from "process feedback." Splitting it into several independent characterizations of different subjects would require inventing a decomposition the field itself does not provide — natural-language inference, not extraction. **Rejected as the primary model** — Evaluation genuinely represents one accepted characterization, not several (see Section 14 for the exact cardinality conclusion).

**Candidate E — No canonical Judgment.** Given Candidate B's clean, direct, lossless field-level match, no genuine ontological obstacle forces this outcome. **Rejected as unnecessary** — a valid reduction exists.

**Selected: Candidate B.** Subject = `TypedDomainObjectReference(target_type=DomainObjectType.OUTCOME, target_id=evaluation.outcome_id.value)`.

## 10. Candidate Judgment Content Models

The characterization content is directly present in Evaluation's own `statement` field — no normalization, no wording generation, and no sentence template is required or authorized. `statement` is already a complete, independently meaningful natural-language answer to "did it confirm or contradict what was expected, and why?" — it remains meaningful outside the review UI without modification (it is not a fragment, an enum value, or a code, so no serialization-into-text step is needed). **Deterministic content-construction rule, defined exactly**: `characterization = evaluation.statement.value`, copied verbatim, no concatenation with `note`, no prefix/suffix text, no reference to `evaluated_at`. This is one proposition, not several (Section 9, Candidate D rejection). No information is lost in this specific copy (the full `statement` text transfers exactly); `note` and `evaluated_at`, as established in Section 5, are deliberately excluded from this rule, not lost by it — they remain fully intact on the unmodified legacy Evaluation row. Free-form explanation is exactly what `characterization` already is — no further explanation field is added, consistent with the Judgment Implementation Design's own rejection of a separate rationale field (Section 28 of that document).

**Exact whitespace and normalization behavior, audited directly against both value objects' own `__post_init__` implementations**: `evaluation.statement.value` is already stripped of leading/trailing whitespace at Evaluation-capture time (`atlas/core/domain/evaluation/value_objects.py`, `Statement.__post_init__`), and is guaranteed non-empty (the same constructor raises `MissingStatementError` otherwise) — so the copy this rule performs can never produce blank or untrimmed content. `Characterization.__post_init__` (`atlas/core/domain/judgment/value_objects.py`) independently re-strips and re-validates non-emptiness on construction — a second, harmless, idempotent pass over already-clean text, not a source of double-transformation risk, since stripping already-stripped text is a no-op. The content therefore always satisfies Judgment's own validation without any possibility of a `MissingCharacterizationError` at this step, given Evaluation itself already exists. No note content is required to make the copied characterization intelligible on its own (Section 9's disclosed phrasing nuance concerns surface wording, not intelligibility — "The decision proved correct." is a complete, grammatical sentence with or without any note). No direction/category encoding exists on Evaluation to serialize (unlike Evidence's `SUPPORTS`/`CHALLENGES`, Evaluation carries no such field at all).

## 11. Acceptance-Event Analysis

**Candidate: when Evaluation is first captured.** At this moment, the Outcome subject already exists and is accepted (Section 8, step 2 precedes step 3); the Evaluation's own characterization content (`statement`) is already complete and final (Evaluation is immutable from capture, INV-009-equivalent legacy discipline). Nothing about Learning's later capture could retroactively change Evaluation's own `statement` — Learning references Evaluation, never the reverse, and Evaluation is never mutated. Retries at this exact point do not create duplicates, provided the write is placed strictly after Evaluation's own step has itself terminated (Section 17). **This candidate is semantically sufficient the moment Evaluation succeeds** — the Judgment's content does not require Learning to exist.

**Candidate: when the full review flow completes (after Learning).** Also sufficient, since nothing about Learning changes what the Judgment would say; this candidate is chosen for **placement**, not because Learning's content is needed (Section 17), mirroring M1's own terminal-placement pattern for maximal consistency and provable non-retry safety.

**Candidate: after user confirmation, or after a specific review response.** No such confirmation step exists in the current flow; inventing one would add UI/workflow surface not authorized by this design. **Rejected — not required, and not present.**

**Candidate: no current event is sufficient.** Rejected — both of the first two candidates are sufficient; this is not the genuine state of affairs.

**Selected exact runtime event**: the Judgment becomes accepted immediately after `_handle_learning`'s own successful terminal state transition (`session.current_step = REVIEW_RECORDED`), in a separate, non-retrying `try`/`except` (Section 17) — chosen for placement safety and consistency with M1, not because Learning's own content contributes to the Judgment.

**Explicit semantic-versus-operational distinction, stated plainly per this audit's own requirement**: the characterization this Judgment records is already complete and true the moment Evaluation itself is captured (step 3) — that is the *semantic* acceptance moment, in the sense that nothing after it changes what the Judgment would say. The *operational* write is deliberately delayed one step further, to after Learning succeeds (step 4), purely for placement safety and consistency with M1's own established pattern — never because Learning semantically participates in, qualifies, or is required by the Judgment's own content. A future implementer must not read the operational delay as meaning "the Judgment is somehow about the review as a whole" — it remains, exactly and only, a characterization of the Outcome, timed operationally later than it is semantically settled.

## 12. Case-Source Analysis

`DecisionReviewSession` carries no `case_id` field at all (Section 8). The narrowest authoritative source is **the Outcome itself** — the exact object the Judgment is about to cite as its subject, which already carries `case_id` directly (`Outcome.case_id`, `atlas/core/domain/outcome/entity.py`). `OutcomeService` (already held by the orchestrator as `self._outcome_service`) already exposes `.get(outcome_id) -> Outcome`, raising `OutcomeNotFoundError` if absent — no new repository dependency is required merely to read `case_id`; the same lookup that will separately be re-verified inside `JudgmentService.capture()`'s own `_verify_subject` is performed here first, purely to obtain the `case_id` value the request itself requires. This avoids duplicating Case input: no Decision lookup is introduced, and no `case_id` field is added to `DecisionReviewSession`. Same-Case validation is trivially satisfiable at this point: the Outcome being cited as subject and the Judgment being constructed share the identical `case_id` by construction (the value is read directly off the same Outcome object), so INV-004 cannot fail for this specific write.

## 13. Timestamp Decision

Distinguishing the four times precisely: (a) the time the underlying evaluation occurred is not separately represented at all — Evaluation's own `evaluated_at` is the closest analog, representing when the investor performed the assessment; (b) the time the Evaluation record was captured is `Evaluation.recorded_at`; (c) the time the canonical Judgment is accepted is a new, distinct moment — whenever this package's own capture call succeeds, strictly after Learning's own terminal transition (Section 11); (d) `Judgment.recorded_at` is exactly and only (c) — Judgment's actual field shape has no field for (a) or (b).

**Selected disposition: B — `evaluated_at` remains legacy/non-Core metadata; Judgment receives its own ordinary `recorded_at` at canonical acceptance.** This is not a preference — it is the only disposition consistent with Judgment's actual, implemented field shape (Section 7), which the Judgment Implementation Design's own Section 23 already establishes was deliberately left as a **non-forced**, currently-unexercised option ("a second, investor-supplied... timestamp is permitted... but not canonically forced"). Disposition A (`evaluated_at` becomes Judgment's acceptance time) is rejected: doing so would misrepresent the actual acceptance moment of the Judgment (a later, distinct event) as though it were the same moment the investor typed their answer — falsifying acceptance chronology, directly prohibited by INV-015's own text ("MUST NOT be replaced by, or conflated with, any time represented by that Domain Object's own content"). Disposition C (`evaluated_at` encoded in content) is rejected: the time is not part of the characterization proposition itself ("did it confirm or contradict...") — encoding a timestamp into free text would not be a faithful representation of a time value and would invite exactly the kind of invented-wording problem Section 10 forecloses. Disposition D (a separate canonical representation required) is rejected: no correct semantics are blocked by omitting `evaluated_at` from the canonical record — the underlying Evaluation row, which is never deleted or altered by this package, already permanently retains it. Disposition E (Evaluation cannot reduce) is rejected: Section 9's own clean field match demonstrates a valid reduction exists independent of this timestamp question. `evaluated_at` and `note` are not silently discarded — Section 5 documents exactly why each is non-Core, and neither is ever deleted from the legacy Evaluation row by this package.

## 14. Cardinality Decision

**Selected: one Evaluation creates exactly one Judgment.** Evaluation's `statement` is a single free-text field asserting one characterization of one identified Outcome (Section 9, Candidate D rejection) — there is no field-level basis for producing a "deterministic bounded set" of more than one, and Judgment creation does not depend on which optional Evaluation fields are present (`note` and `evaluated_at` are never consulted by the construction rule, Section 10, so their presence or absence cannot change cardinality). "Evaluation cannot currently produce Judgment" is rejected by Section 9's own positive finding. Since `EvaluationRepository` permits multiple Evaluations per Outcome (no uniqueness constraint) and this package is a pure per-Evaluation reduction, multiple Evaluations of the same Outcome each independently and legitimately produce their own separate Judgment — this is not a violation of "exactly one," it is "exactly one Judgment per Evaluation instance," which is the only cardinality this design asserts.

## 15. Learning Disposition

Investigated independently, per the task's own instruction not to force Learning into Judgment merely to reduce legacy object count.

**L1 — Learning is part of the same Judgment as Evaluation.** Rejected: Evaluation is already a complete, independently meaningful characterization of the Outcome on its own (Section 10) — appending Learning's own generalized, forward-looking statement would conflate two different kinds of claims (a retrospective assessment of one specific Outcome, and a cross-Case, future-facing heuristic) within a single characterization field, which is not required and is not a faithful single proposition.

**L2 — Learning creates a later, separate Judgment.** Tested: Learning's own reference (`evaluation_id`) could, once Evaluation itself is reduced to a Judgment, be retargeted onto that Evaluation-derived Judgment as an ordinary Judgment-to-Judgment reference (permitted, no type restriction, OE-002 §5.4 Relationships). But is Learning's content actually **a characterization of that Judgment as an identified subject**? Learning's own statement ("weigh capex guidance more heavily than headline revenue growth") is not *about* the Evaluation-Judgment as a thing — it is a free-standing lesson that happens to have been prompted by reviewing it. Treating the Evaluation-Judgment as Learning's "subject" would use it as a mere causal anchor, not as what the characterization is genuinely about — the same "characterizes vs. merely follows from" distinction the Judgment Implementation Design itself draws for Reasoning Trace's own support relation (Section 14 of that design). **Rejected as the primary model**, though architecturally valid in the narrow sense that nothing forbids it if a future, separately-justified need arises.

**L3 — Learning remains outside Core.** Learning's own content is explicitly general and cross-Case-transferable, not a settled fact about one specific, identified, same-Case Domain Object — the defining property Judgment's own ontology requires (OE-002 §5.4: "characterization of an identified subject"). No forcing function (Doctrine §8) — no newly identified domain fact inexpressible by the current architecture, no unavoidable contradiction, no downstream normative task exposing a real expressive gap — requires Atlas Core to canonically represent it. `decision_timeline` (Section 20) already reads Learning directly from its own legacy repository, with no canonical dependency, and needs no change. **Selected** — Learning remains permanently outside Core for this package, as legacy/analytical data, its own future architectural home (if any, e.g., a Lab-style read-model) left for a separate, later investigation.

**L4 — Learning exposes an ontology gap requiring permanent representation for correctness.** No genuine correctness requirement was found — nothing in the live product depends on Learning being canonically queryable or referenceable today. **Rejected — no forcing function demonstrated.**

**Disposition: L3.** Learning is not touched by Package M2 in any way; the Judgment this package captures is constructed entirely from Evaluation and Outcome, never from Learning.

## 16. Knowledge Reference and Reasoning Trace Interaction

**A Knowledge Reference to the Evaluation**: categorically invalid, not merely unneeded — Evaluation is not itself a canonical Domain Object (no `case_id`, not a member of OE-002 §4's closed set), so it cannot be a valid Knowledge Reference target under INV-005/INV-001 regardless of any implementation choice. **Rejected, structurally.**

**A new Reasoning Trace**: Evaluation supplies no new support-relation information beyond what M1 already captured at Decision commitment (citing the conversation's own Observation). Adding one here would be an unforced, symmetry-only addition, explicitly excluded by this task's own instruction. **Rejected.**

**Support from the existing Decision-time Reasoning Trace**: not applicable — that Trace already exists as its own independent, complete fact; nothing about this package needs to reference or extend it.

**Selected: no additional canonical object.** Judgment directly characterizes the already-accepted Outcome — the simplest, semantically correct path.

## 17. Failure and Retry Model

Applying the M1 audit's own rule exactly: a failed additive canonical write must never cause an already-successful permanent write to repeat. At the selected acceptance event (Section 11), Evaluation is already successfully stored (step 3 precedes step 4 precedes the Judgment attempt); the selected subject (Outcome) is already accepted (step 2); Learning is already successfully stored (step 4, which precedes the Judgment attempt). The Judgment capture attempt must be placed **strictly after** `session.learning_id = learning.id.value; session.current_step = DecisionReviewStep.REVIEW_RECORDED` inside `_handle_learning`, in its **own**, separate `try`/`except`, never sharing Learning's own retry/reprompt boundary above it — mirroring exactly the placement rule established and audited for M1's `_handle_decision`. Because `REVIEW_RECORDED` has no entry in `_HANDLERS` (Section 8, step 5), no code path can re-invoke `_handle_learning`, `_handle_evaluation`, or `_handle_outcome` again for this same session once that transition has occurred — so a Judgment-capture failure at this point cannot retry Evaluation, cannot retry Learning, cannot retry Outcome, and cannot create a duplicate Evaluation, Learning, or Outcome. Failure must be surfaced explicitly, not silently ignored: the returned `ReviewTurn` uses a distinct prompt (a new `CLOSING_MESSAGE_JUDGMENT_FAILED` constant, mirroring `CLOSING_MESSAGE_REASONING_TRACE_FAILED`'s own precedent exactly) while still reporting the turn as complete, since Learning — the actual conversational deliverable of this step — did succeed. The system does not claim atomicity across Learning's own write and the Judgment's own write: these are two separate repository transactions (Section 8, step 7), and this must be stated in code comments at the integration point, exactly as it was for M1.

**Verified directly, audited against the actual entry-point surface**: no API router exists for `outcome`, `evaluation`, `learning`, or `decision_review` at all (`find atlas/core/infrastructure/api -maxdepth 1 -type d` lists no such directory; `app.py` mounts nothing for any of the three). The only entry point is `decision_review/cli.py`'s own `input()`/`print()` loop, which calls `orchestrator.respond(session, answer)` only while `not session.is_complete()` — once `REVIEW_RECORDED` is reached, that loop exits and never calls `respond()` again for this session. There is therefore no HTTP retry surface to consider for this specific flow at all (unlike a networked API, where a client might resend a request after a dropped response), and the CLI's own loop structure independently confirms, by direct inspection, that it never attempts a second `respond()` call after completion.

**Exceptions the Judgment capture attempt may itself raise**, for completeness: `EmptySupportError`/`TargetNotFoundError`/`CrossCaseTargetError` (from `JudgmentService`'s own `_verify_subject`, none of which should occur in ordinary operation given the Outcome is already accepted and same-Case by construction, Section 12) and `MissingCharacterizationError` (structurally unreachable, Section 10) — plus any transport-level failure from the underlying database call, which is the realistic failure mode this design must actually protect against.

## 18. Idempotency Model

Judgment's own ontology carries no source-Evaluation-id field, and none is proposed here (consistent with this task's own explicit prohibition and with the Judgment Implementation Design's own rejection of any such field, Section 28 of that design). At-most-once capture is guaranteed by the **terminal workflow-state guard** already proven in Section 17: `REVIEW_RECORDED` has no handler entry, so the Judgment capture call site is reached, for any one `DecisionReviewSession` instance, at most once, by direct inspection of `_HANDLERS`' own fixed dictionary — not by runtime probability, by the absence of any dispatchable path. No in-memory review-session flag, no composition-level idempotency wrapper, no deterministic pre-check, and no database uniqueness constraint is required or introduced; each would duplicate a guarantee the existing control flow already provides for free. Running an entirely **new**, separate review of the same Decision (permitted today, `TestMultipleReviewsOfTheSameDecision`) legitimately produces its own new Outcome, Evaluation, Learning, and — under this design — its own new Judgment; this is not a duplicate-prevention failure, it is the same multiplicity Outcome and Evaluation already, correctly, exhibit, extended consistently to Judgment. An interrupted review (stopping before Learning) never reaches the Judgment capture call site at all — no repair, no orphan-Judgment risk, exactly mirroring the already-accepted, disclosed behavior for an interrupted review's own orphaned Outcome (`TestInterruptedReviewIsNotRepaired`).

**Precise scope of the guarantee, stated using the exact language this audit requires**: this design guarantees **at-most-once invocation of the Judgment capture call site, and at-most-once persistence of the resulting Judgment, for any single, ordinary, in-memory `DecisionReviewSession` run to completion** — it does not, and cannot, guarantee delivery. Per-scenario verification: ordinary repeated method calls and repeated final user input are both foreclosed by the terminal-state guard (Section 17); orchestrator reuse across a *new* session is not duplication, it is legitimate independent multiplicity (above); process restart and session reconstruction cannot cause duplication, because `DecisionReviewSession` is never persisted (`session.py`'s own docstring) — a restart simply loses the in-memory session entirely, exactly like today's already-accepted interrupted-review behavior, and any subsequent review is necessarily a brand-new, independent `DecisionReviewSession`, never a resumption of the lost one; HTTP retry does not apply, since no HTTP surface exists for this flow at all (Section 17); CLI retry does not apply, since the CLI's own loop never calls `respond()` again once `is_complete()` is true (Section 17); an application exception after the Judgment's own repository `.add()` call has already committed, but before this method returns, is not distinguished from an ordinary capture failure by this design — either way, the Judgment row already exists in the database, the call site is never re-entered for this session, and the design does not attempt to detect this narrow race, since doing so would require introducing exactly the kind of new mechanism (a flag, a constraint) this section deliberately declines to add. **No retry mechanism exists for a failed Judgment capture, and none is provided by this package** — this is a disclosed, accepted limitation, not an oversight (Section 25). A failed Judgment *could* be captured later, safely, but only by a separate, future, out-of-band operation (e.g., a manual or scripted backfill targeting that one specific Evaluation, Section 19) — never by any mechanism this package itself implements, and never by re-running the review, which is already terminal.

## 19. Historical-Data Analysis

For every existing Evaluation row: subject identity (`outcome_id`) — present, always has been (mandatory since Evaluation's own inception). Case — derivable, losslessly, via the referenced Outcome's own `case_id` (Outcome's `case_id` column is `NOT NULL` in the current schema; every row satisfies it). Complete content (`statement`) — present, always required. Associated Outcome — present, directly. Associated Decision — derivable transitively via Outcome, though not needed by this design (subject is Outcome, not Decision). Sufficient status to establish finality — trivially satisfied: Evaluation has no draft/pending state; every captured row is, by construction, already final and permanent.

Acceptance timestamp for a **backfilled** Judgment deserves explicit treatment: a historical Judgment created by a future backfill script would necessarily receive `recorded_at` equal to the script's own run time, not the original Evaluation's `recorded_at` or `evaluated_at`. This is **not** dishonest or lossy — it exactly mirrors the retrospective-recording pattern OE-002 §5.6 and INV-015 already explicitly authorize for Outcome ("An Outcome's event MAY occur at any time relative to the time its own content treats the realized matter as having become actual"): the backfilled Judgment's `recorded_at` honestly represents when *that Judgment* was accepted, never claiming to represent when the underlying Evaluation was originally made.

**Classification: lossless** for the (subject, content, Case) triple that actually populates a backfilled Judgment; `evaluated_at`/`note` are not "lost" by a backfill, since they are non-Core by design (Section 5) and remain permanently on the untouched legacy Evaluation row regardless of whether backfill ever runs.

**Historical backfill is not a prerequisite for M2.** Exactly as M1 never touched historical Decision rows, M2 is specified here as a prospective, going-forward-only additive capture: only Evaluations completed *after* this package ships produce a Judgment. Whether to separately backfill existing Evaluation rows is an independent, optional, later decision, out of scope for this design and not blocking Conclusion A (Section 28).

## 20. Downstream-Consumer Analysis

A repository-wide search confirms the only consumer of `EvaluationRepository`/`LearningRepository` outside their own modules and `decision_review` itself is `atlas/core/application/decision_timeline/` (`query.py`, `timeline.py`, `composition.py`, `cli.py`). `DecisionTimelineQuery.build()` reads `Evaluation`/`Learning` directly via `list_by_outcome_id`/`list_by_evaluation_id`, assembling a pure, non-persisted, recomputed-per-request read model (`DecisionTimeline`/`DecisionReviewChain`/`EvaluationWithLearnings`) with no awareness of Judgment at all. Adding Judgment capture **changes nothing** for this consumer: it creates no dual authority (Evaluation remains sole authority for "the investor's own verbatim assessment text, as captured"; Judgment becomes co-authoritative only for "whether an accepted characterization of this Outcome now exists as a permanent Case fact" — a distinct, non-overlapping fact, exactly the same two-tier split already established and audited for M1's Decision/Reasoning Trace relationship), risks no divergent interpretation (the Judgment's content is a pure, deterministic function of the Evaluation's own already-verified content, never independently re-entered), and requires no new read path. **M2 is additive historical record with no read-path change** — the same category M1 already established for Reasoning Trace.

## 21. Candidate Reduction Designs

**Candidate 1 — One Judgment about Outcome.** Ontology fidelity: exact, direct field match (Section 9). Data loss: none for the copied fields; `evaluated_at`/`note` deliberately non-Core, not lost (Section 5, 13). Semantic invention: none — verbatim copy only (Section 10). Runtime feasibility: fully satisfiable at the selected acceptance event (Section 11), Case derivable without new session state (Section 12). Case/prior-acceptance invariants: satisfiable by construction (Section 12). Timestamp treatment: fully resolved, Disposition B (Section 13). Retry safety: proven via the terminal-state guard (Sections 17–18). Historical migration: not required, optionally lossless later (Section 19). Downstream usefulness: additive, no consumer disruption (Section 20). Complexity: minimal — mirrors M1's own already-proven pattern exactly. **Selected.**

**Candidate 2 — One Judgment about Decision.** Ontology fidelity: fails — no field-level support (Section 9, Candidate A). Rejected on the same grounds.

**Candidate 3 — Split Judgments (Decision-focused and Outcome-focused).** Ontology fidelity: fails for the same reason as Candidate 2, compounded by Section 9's Candidate D rejection (Evaluation's `statement` does not naturally decompose). Semantic invention: high — would require inventing a Decision-directed characterization Evaluation's own fields do not support. **Rejected.**

**Candidate 4 — No current reduction.** Ontology fidelity: N/A. Rejected as unnecessary given Candidate 1's own clean fit (Section 9, Candidate E rejection). Complexity: lowest, but at the cost of leaving a demonstrably reducible fact permanently uncaptured, contrary to the Historical Decision Record's own already-settled finding that Evaluation is reducible. **Rejected.**

## 22. Selected Reduction Design

**Candidate 1 — One Judgment per Evaluation, subject = the already-accepted Outcome, characterization = Evaluation's own `statement`, verbatim.** `recorded_at` is Judgment's own, freshly-generated acceptance time (Disposition B, Section 13). Learning is not consulted (Section 15, L3). No Knowledge Reference or new Reasoning Trace is created (Section 16).

## 23. Exact M2 Implementation Package

*Objective*: after Learning has been successfully captured in the live decision-review flow, capture exactly one canonical Judgment whose subject is the Evaluation's own already-accepted Outcome and whose characterization is that Evaluation's own `statement`, verbatim.

*Exact integration point*: `atlas/core/application/decision_review/orchestrator.py`, inside `_handle_learning`, strictly after `session.learning_id = learning.id.value; session.current_step = DecisionReviewStep.REVIEW_RECORDED`, in its own, separate `try`/`except`.

*Exact subject type*: `DomainObjectType.OUTCOME`.

*Exact subject ID source*: `session.outcome_id` (already retained on `DecisionReviewSession` since `_handle_outcome`; no new session field required).

*Exact Case source*: derived by calling the orchestrator's own, already-held `self._outcome_service.get(OutcomeId(session.outcome_id))` and reading `.case_id.value` off the returned `Outcome` — no new repository dependency needed for this specific read (Section 12). This is a second, independent read of the same Outcome `JudgmentService.capture()`'s own `_verify_subject` will re-verify internally; this is intentional, matching the same "verify, then let the callee re-verify" pattern already used throughout this codebase (e.g., M1's `ReasoningTraceService` re-verifying its own Observation support).

*Exact Judgment content-construction rule*: `characterization = evaluation.statement.value` — but the orchestrator does not currently hold the `Evaluation` object at the point Learning succeeds. It must retain a reference: either (a) keep the `Evaluation` instance returned by `_handle_evaluation`'s own earlier call in a new, unexported local retained on `session` for the duration of the review, or (b) re-fetch the Evaluation via `self._evaluation_service.get(EvaluationId(session.evaluation_id))` at the point of Judgment capture. **Option (b) is selected** — it requires no new session field (consistent with "introduce the smallest explicit propagation required" and this codebase's own established preference for re-fetching over threading extra state, e.g., M1 never added an extra session field beyond the pre-existing `observation_id`). `characterization = evaluation.statement.value`.

*Exact cardinality*: exactly one Judgment per successful review (Section 14).

*Exact timestamp behavior*: `Judgment.recorded_at` is generated fresh, at the moment of this capture call, via `JudgmentService`'s own existing, unmodified clock discipline; `evaluated_at`/`note` are never read by this package.

*Exact service used*: the existing, unmodified `JudgmentService` (`atlas/core/application/judgment/capture_judgment.py`), via `CaptureJudgmentRequest(case_id=outcome.case_id.value, characterization=evaluation.statement.value, subject=TypedDomainObjectReference(target_type=DomainObjectType.OUTCOME, target_id=session.outcome_id))`.

*Exact composition wiring*: `atlas/core/application/decision_review/composition.py` gains: `SqlAlchemyJudgmentRepository`, `SqlAlchemyKnowledgeReferenceRepository`, `SqlAlchemyObservationRepository`, `SqlAlchemyReasoningTraceRepository` (four new, lazily-constructed repository instances — none eagerly touches its own table, mirroring M1's own established pattern in `conversation/composition.py`); `decision_repository`/`outcome_repository` are already constructed in this module and are reused directly, unmodified, as two of `JudgmentService`'s six constructor arguments. `create_judgment_table(engine)` is added to `create_decision_review_tables`; `knowledge_references`/`observations`/`reasoning_traces` tables are **not** created here, for the identical reason M1 did not create `knowledge_references`/`judgments`/`outcomes` in `conversation/composition.py` — the subject passed by this package is always `OUTCOME`-typed, so `_verify_subject`'s dispatch never actually queries those three repositories in practice. `build_decision_review_orchestrator` constructs `JudgmentService(...)` and passes it into `DecisionReviewOrchestrator`'s new `judgment_service` constructor parameter.

*Exact workflow-state transition*: occurs after, never before, `session.current_step = DecisionReviewStep.REVIEW_RECORDED`.

*Exact failure behavior*: on any exception from the Judgment capture attempt, return `ReviewTurn(prompt=prompts.CLOSING_MESSAGE_JUDGMENT_FAILED, is_complete=True)`; on success, return the existing `ReviewTurn(prompt=prompts.CLOSING_MESSAGE, is_complete=True)`, unchanged.

*Exact duplicate-prevention mechanism*: the terminal workflow-state guard (Section 18) — no new field, flag, or constraint.

*Exact transaction boundary*: Learning's own transaction and the Judgment's own transaction are separate; no shared transaction is claimed or implemented.

*Exact system-of-record effect*: Evaluation remains sole authority for the investor's own verbatim assessment text; Judgment becomes co-authoritative, non-competing authority for the accepted-characterization fact (Section 20).

*Expected production files*: `atlas/core/application/decision_review/orchestrator.py` (new constructor parameter, new post-Learning capture block); `atlas/core/application/decision_review/composition.py` (new repository construction, new `JudgmentService` wiring, `create_judgment_table` added); `atlas/core/application/decision_review/prompts.py` (new `CLOSING_MESSAGE_JUDGMENT_FAILED` constant).

*Expected test files*: a new `tests/unit/application/decision_review/test_judgment_integration.py`, mirroring `tests/unit/application/conversation/test_reasoning_trace_integration.py`'s own structure exactly.

*Required tests*, itemized per this audit's own checklist:

- **Semantic mapping**: exactly one Judgment is created; its subject is exactly the review's own Outcome (never any other Outcome in the Case); its `characterization` equals the Evaluation's own `statement` verbatim; `note` content, when present on the Evaluation, is confirmed **not** present anywhere in the Judgment's characterization; Learning's own statement is confirmed **not** present anywhere in the Judgment's characterization; the Judgment's `case_id` equals the Outcome's own `case_id`.
- **Ordering**: the Outcome exists (is queryable) before Evaluation capture is attempted; the Evaluation exists before Learning capture is attempted; the Judgment does not exist in the database at any point before Learning's own terminal transition; no Judgment is ever written prematurely (e.g., immediately after Evaluation, before Learning).
- **Failure boundary**: simulate Judgment capture failure; prove Outcome/Evaluation/Learning capture were each invoked exactly once; prove no retry of any of the three occurred; prove the legacy Outcome/Evaluation/Learning rows remain permanently recorded regardless of the Judgment failure; prove failure is surfaced via `CLOSING_MESSAGE_JUDGMENT_FAILED`; prove no malformed or partial Judgment is persisted.
- **Duplicate behavior**: a repeated terminal interaction (calling `respond()` again after `REVIEW_RECORDED`) does not create another Judgment (and raises `KeyError`, proving the call site is unreachable); a reprompt before Evaluation succeeds (e.g., a transient Evaluation-capture failure) creates no Judgment; a reprompt before Learning succeeds creates no Judgment; the absence of any database-level uniqueness constraint is explicitly disclosed in the test's own docstring as an accepted, workflow-level-only guarantee (Section 18), not a database-level one.
- **Composition**: real composition supplies a genuine `JudgmentService` instance (`isinstance` check); the `judgments` table is created by `create_decision_review_tables`; imports remain acyclic (direct import of the modified modules succeeds); isolated tests use only an in-memory SQLite engine, never the real on-disk database file.
- **Regression**: existing Outcome, Evaluation, Learning, Judgment, and `decision_review` orchestrator/end-to-end tests remain green, unmodified; `decision_timeline` tests remain green, unmodified, since Judgment introduces no change to that consumer (Section 20).

*Rollback boundary*: remove the one new call site and its composition wiring — identical, trivial rollback shape to M1.

*Independently releasable*: yes — fully independent of M1 (already shipped), M3, and M4.

## 25. Risks and Rollback

The single most consequential risk, per the M1 audit's own finding, is a naive placement of the Judgment capture call inside the *same* `try`/`except` as Learning's own capture, which would let a Judgment-capture failure re-enter that handler and retry Learning, producing a duplicate Learning row. Section 17/23 states the required fix precisely (own, separate, non-reprompting `try`/`except`, strictly after Learning's own terminal transition) and this must be treated as a mandatory implementation constraint, not an optional refinement, exactly as it was for M1. The remaining, accepted risk is narrower: a logged, non-retried Judgment-capture failure produces a permanent Evaluation with no canonical Judgment counterpart, detectable only by out-of-band audit — an accepted cost of the narrow additive strategy, not a defect. Rollback for the whole package is a single new call site plus its composition wiring.

## 26. Explicit Exclusions

This design does not: implement Judgment capture from Evaluation; modify Judgment's ontology, fields, persistence, or API; modify Evaluation, Learning, Outcome, Decision, or Reasoning Trace in any way; reduce Learning to Judgment; add a source-Evaluation-id field to Judgment; add a second timestamp field to Judgment; add a Knowledge Reference or a new Reasoning Trace; change any existing read path; propose historical backfill as a requirement; modify any test; modify any other governing document; stage, commit, tag, or push anything.

Neither question requires resolution before M2 can be implemented as specified in Section 23.
