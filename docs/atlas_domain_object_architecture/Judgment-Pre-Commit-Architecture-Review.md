## 6. Implemented Judgment Contract

As built: `Judgment(id: JudgmentId, case_id: CaseId, characterization: Characterization, recorded_at: datetime, subject: TypedDomainObjectReference | None = None)`, constructed only via `Judgment.capture(case_id, characterization, subject=None, clock)`. `JudgmentService.capture()` (`atlas/core/application/judgment/capture_judgment.py`) requires `characterization` unconditionally; when `subject` is supplied, it verifies `subject.target_type` is in `_CURRENTLY_CAPTURE_ENABLED_SUBJECT_TARGET_TYPES = frozenset({KNOWLEDGE_REFERENCE, JUDGMENT})`, then checks prior acceptance and same-Case membership against the corresponding repository; all four other canonical types are rejected with `TargetTypeUnavailableError`. Persistence is one table, `judgments`, with a CHECK constraint generated from `DomainObjectType`'s own six values and a second CHECK constraint enforcing paired nullability of `subject_target_type`/`subject_target_id`.

## 7. Exact Semantic Content Analysis

**(A1)** One accepted Judgment records exactly OE-002 §5.4's Definition clause: "the Case's settled, Case-relative characterization of an identified subject, without asserting that the characterization is objectively true." **(A2)** "Characterization" is not an implementation label for another concept — it is OE-002 §5.4's own term, verbatim ("records the Case's settled... characterization of an identified subject"); the implementation's field name directly names the canonical semantic content itself. **(A3)** Yes, always present: OE-002 §5.4's Definition clause names two components (a characterization and a subject); if the characterization were dropped, leaving only a subject reference, the result would be structurally and semantically identical to Knowledge Reference (OE-002 §5.2: a bare reference asserting reliance without further content) — and the Historical Decision Record's own "Decision History: OE-002" section confirms Judgment ("characterization") and Knowledge Reference ("reference to knowledge") were each independently justified as *distinct* semantic operations. This is a logically-derived requirement (not itself one of OE-004's fifteen numbered invariants) that follows necessarily from that settled distinctness finding — exactly the argument the Judgment Implementation Design states in its own Section 11, and one this review independently re-derives from OE-002/the Historical Decision Record rather than accepting on the Design's authority alone. **(A4)** Free text is the correct minimal representation: OE-002 §5.4's Responsibility clause explicitly states Judgment "does not assign a mandatory discrete status vocabulary," making free text the least-inventive, most directly conformant realization — not asserted as the only possible one, but correctly adopted as the minimal default. **(A5)** OE-002 imposes no constraint on characterization's form, language, grammar, interpretation, or truth-aptness; it explicitly rejects any mandatory discrete vocabulary. **(A6)** No — explicitly disclaimed by OE-002 §5.4 itself. **(A7)** No — no canonical text in §5.4 mentions confidence, probability, reliability, authority, correctness, or justification, and none is implemented. **(A8)** Only in the referential form is Judgment "about" an architecturally separate subject; in the internal-content form, the subject is embedded within the characterization's own text, not a distinct entity. **(A9)** Yes — OE-002 §5.4 Ownership boundary states both forms are "independently valid." **(A10)** Whatever the characterization's own text names or describes — the subject is content held internally, per OE-002's own phrase. **(A11)** A complete canonical form, not an incomplete one — OE-002's own text states both forms are independently valid with no qualification. **(A12)** Yes: the entity carries exactly `id`, `case_id`, `characterization`, `recorded_at`, and an optional `subject` — the Design's Section 27 six named facts, with the two subject-reference columns unified into one atomic optional field (Section 11 below) — nothing more.

**Classification: correct as written.**

## 9. Internal-Content Form Analysis

`subject is None`; `characterization` alone carries the settled assessment. OE-002 §5.4 Ownership boundary states this form is independently valid and, per INV-012, unconditionally root-eligible ("MAY be the first Domain Object accepted into a Case"). The implementation requires no pre-existing target for this path: `JudgmentService.capture()` only invokes `_verify_subject` `if request.subject is not None`; when absent, capture proceeds directly from `case_id` and `characterization` alone. Confirmed by `TestInternalContentFormRootEligibility.test_captures_the_first_ever_domain_object_in_an_empty_case` (`tests/unit/application/judgment/test_capture_judgment.py`), which captures successfully against a genuinely empty store with no seeding of any kind — the one meaningful behavioral difference from Knowledge Reference, whose every capture structurally requires a pre-existing target.

## 10. Referential Form Analysis

`subject` populated with exactly one `TypedDomainObjectReference`; `characterization` remains required alongside it (Section 7, A3) — the referential form does not relax the characterization requirement, it only adds a subject. INV-004 (same-Case) and INV-005 (prior acceptance) apply to this reference exactly as OE-004 §8 states for Judgment's referential form ("Where Judgment... use a referential form, INV-004 and INV-005 apply to that reference in the same manner"). Per INV-012 and the derivation in Section 17 below, this form can never be root-eligible. Confirmed structurally sound in both the domain layer (`Judgment.__post_init__`'s `_validated_subject` rejects any non-`TypedDomainObjectReference`, non-`None` value) and the application layer (`_verify_subject` fully verifies before construction).

## 11. One-Type-versus-Two-Forms Analysis

**(B1)** Yes — OE-002 §5.4 Ownership boundary explicitly states both forms are independently valid. **(B2)** Yes — one Domain Object type (Judgment), with two alternative realizations of its single "ownership boundary," exactly the same pattern OE-002 states for Decision and Outcome. **(B3)** No semantic priority is stated in the text; both are "independently valid" with equal standing. **(B4)** Yes — only the internal-content form is root-eligible (§5.4, INV-012). **(B5)** Yes — necessarily non-root, derived directly from INV-005 requiring the referenced target to already be accepted, which entails a prior Domain Object in that Case (Section 17). **(B6)** Preserves one coherent Judgment concept — OE-002 defines Judgment as a single type; the optional subject is one alternative realization of its ownership boundary, not a second Domain Object smuggled into one nullable schema. **(B7)** Sufficient at the persistence layer (the CHECK constraint `ck_judgments_subject_reference_paired`), but the domain and API layers use a *strictly stronger* guarantee than mere paired-nullability: **(B8)** the entity's `subject` field is one atomic `TypedDomainObjectReference | None`, not two independently nullable primitives — it is not even representable, at the Python or Pydantic type level, to construct a mismatched pair. The persistence-layer CHECK constraint exists only as a backstop against direct SQL manipulation bypassing the domain layer entirely, consistent with the Design's own Section 31 recommendation; this is a compliant strengthening, not a deviation from it. **(B9)** Yes — persistence stores two nullable columns with the paired CHECK constraint, and `sqlalchemy_repository.py`'s `_to_row`/`_to_judgment` correctly serialize/deserialize the single atomic field to/from that pair (confirmed by `TestSchemaAndConstraints` and `TestEqualsOriginal` in the persistence test module). **(B10)** Yes — `CreateJudgmentRequest.subject`/`JudgmentResponse.subject` are both `TypedDomainObjectReferenceSchema | None`, a nested optional object, never flat `subjectTargetType`/`subjectTargetId` fields. **(B11)** No third form is representable: every layer admits only "subject is `None`" or "subject is a fully-formed typed reference." **(B12)** No — a malformed or partially-populated `subject` object cannot reach the domain layer: Pydantic's nested `TypedDomainObjectReferenceSchema` requires both `targetType` and `targetId`; an incomplete nested object fails validation with 422 before the router calls `.to_domain()` (confirmed by `test_rejects_malformed_subject_target_id` and the general Pydantic contract — no test submits a one-sided nested object, since Pydantic's own schema makes this structurally unreachable, not merely untested).

**Classification: correct as written.**

## 12. Canonical Subject Eligibility

**(D1–D2)** Yes, canonically unrestricted: OE-002 §5.4 Relationships clause states "Where Judgment's subject is a reference, it MUST be to another same-Case Domain Object; no specific Domain Object type is required." **(D3–D8)** All six adopted types — Observation, Knowledge Reference, Reasoning Trace, Judgment, Decision, Outcome — are each canonically eligible Judgment subjects, without exception; the four currently rejected by the service are rejected on present-capture-availability grounds (Section 13), never on canonical-eligibility grounds. **(D9)** Yes — the distinction is correct and is the same one already established and corrected for Knowledge Reference (Outcome 2): canonical eligibility (OE-002 §5.4, permanent, unconditioned) is categorically distinct from current capture availability (an application-layer, present-state fact about which invariants can currently be positively established). **(D10)** Yes — the Judgment Implementation Design's Section 15 ("no specific type restriction") and Section 30 ("Reference Semantics... no type restriction") explicitly authorize this target model, directly reflecting OE-002's own text. **(D11)** No invariant restricts which type may occupy the subject role beyond the generic INV-004/INV-005 that OE-004 §8 states apply to any referential form. **(D12)** `subject_target_type` only identifies what is characterized (a routing/dereferencing fact, per the Design's own field table, Section 27: "Technical (routing)"); it carries no independent semantic weight — the characterization itself is the sole bearer of Judgment's semantic content.

**Classification: all six canonical types are eligible.**

§9 recognizes no "accepted with a deferred invariant" status. **(E3–E4)** Both Knowledge Reference and Judgment currently expose a `case_id` column and a working `.get()` repository method, so both INV-005 (via existence check) and INV-004 (via `case_id` comparison) are currently, fully verifiable for either type — confirmed directly against `atlas/core/infrastructure/persistence/knowledge_reference/table.py` and `atlas/core/infrastructure/persistence/judgment/table.py`, both read in this review. **(E5–E7)** Confirmed directly: `observations_table` columns are `{observation_id, subject, statement, source, note, observed_at, recorded_at}`; no instance of that type has ever been accepted, so INV-005 is determinately violated for any claimed Reasoning Trace target, not merely unverifiable. **(E9)** Yes, presently required — OE-006 §5/§9/§16 read with OE-005 §15's determinacy distinction (implementation inability to evaluate a complete subject is a defect, never a license to proceed as if the invariant holds) directly force rejection of all four currently-unverifiable types; ## 14. Judgment-as-Subject Analysis

**(F1)** Yes — canonically valid: Judgment is itself one of the six Domain Object types, and OE-002 §5.4 places no type restriction on the subject role. **(F9)** A Judgment characterizing another Judgment asserts nothing about the prior Judgment's truth — OE-002 §5.4's own truth disclaimer governs only the *new* Judgment's own characterization; the definition never raises the referenced object's truth as a question its referencer must answer, unlike Knowledge Reference's explicit non-vouching language (which has no analog needed here, since Judgment never vouches for anything about its target in the first place). **(F10)** Yes — multiple Judgments may characterize the same subject; no uniqueness constraint exists on `(subject_target_type, subject_target_id)` in `judgments_table`, confirmed by `test_duplicate_subject_references_across_separate_records_are_permitted`. **(F11)** Yes — contradictory Judgments about the same subject may coexist, per Design Section 25 ("Permitted, without qualification") and confirmed directly by the domain test `TestContradictoryJudgmentsPermitted`. **(F12)** No uniqueness, replacement, supersession, or contradiction-resolution mechanism is imposed; a revised assessment is simply a new, separately-captured Judgment (Design Section 24); no `supersedes` field exists (correctly deferred, Section 28/36 Q3 — no canonical basis exists, and none is invented).

Self-reference and cycles are analyzed separately in Sections 15–16, per this review's own instruction not to conflate them with the six distinct concerns above. All six — duplicate object identity, duplicate semantic content, multiple Judgments about one subject, contradictory Judgments, direct self-reference, indirect cycles — are handled separately and correctly: duplicate identity is impossible by construction (a fresh `JudgmentId` per capture); duplicate content is permitted (no constraint on `characterization`); multiple Judgments about one subject is permitted (no constraint on `subject`); contradictory Judgments is permitted (Section 25 of the Design); self-reference and cycles are structurally impossible (Sections 15–16 below) — none of these six is conflated with another anywhere in the implementation or its 85 tests.

## 15. Self-Reference Analysis

**(F2)** No — direct self-reference is structurally impossible: `JudgmentId()` is generated only inside `Judgment.capture()`, which `JudgmentService.capture()` invokes only *after* `_verify_subject()` has already completed in full. A caller cannot supply, as `subject.target_id`, the identity of the very Judgment under construction, because that identity does not exist at request-construction time. This is the identical argument already established and applied for Knowledge Reference and Reasoning Trace, correctly reapplied here — verified directly against `capture_judgment.py`'s own control flow (`case_id = CaseId(...)` → `if request.subject is not None: self._verify_subject(...)` → `Judgment.capture(...)`), not merely asserted from precedent. **(F7–F8)** No explicit self-reference validation is required or was implemented, correctly, since the impossibility is structural rather than a runtime condition to be checked.

## 16. Cycle Analysis

**(F3)** No — two Judgments cannot target each other: whichever of the two is captured first must, by INV-005, target an *already*-accepted object, but the second Judgment does not yet exist at that moment. **(F4)** No — a longer cycle of any length is excluded by the identical argument: INV-005 forces every reference to point only to a strictly-earlier-accepted object, and INV-009/INV-011 (permanence, no update) preclude any later, retroactive insertion of a reference that could close a cycle after the fact. **(F5–F6)** Yes — INV-005 (prior acceptance) combined with permanence together impose a strict DAG on the reference graph; acceptance ordering alone would not suffice without permanence, since a mutable object could in principle acquire a new reference later, but no such operation exists anywhere in this codebase's convention or in this implementation (`JudgmentRepository` exposes only `add`/`get`). **(F7)** No explicit cycle-detection code exists or is required — confirmed by direct inspection of `capture_judgment.py`: no graph traversal, no visited-set, no recursive lookup of any kind appears anywhere in `_verify_subject` or elsewhere in the module.

## 17. Root-Eligibility Analysis

**(G1)** Root eligibility (OE-002 §6, INV-012) means whether a Domain Object type or form MAY be the first accepted Domain Object in a Case — i.e., accepted while no other Domain Object yet exists in that Case. **(G2–G3)** Judgment is conditionally root-eligible: only the internal-content form (`subject` absent) MAY be first; the referential form (`subject` present) MUST NOT be first — stated directly by OE-002 §5.4 Ownership boundary and by INV-012's own text ("Judgment, Decision, and Outcome MAY be the first accepted Domain Object in a Case only when their respective subject... is internal content rather than a reference"). **(G4–G5)** Root eligibility is not stored on the object — no such field appears in the Design's Section 27 minimal field list or in the implemented `Judgment` entity; it is a derived structural possibility, a fact about Case state at acceptance time and about which form is used, never object metadata. **(G6)** Yes — subject absence unconditionally permits the internal-content form to be a Case's first accepted Domain Object; confirmed directly: `JudgmentService.capture()` invokes `_verify_subject` only `if request.subject is not None`, so a subjectless capture request performs zero referential checks and cannot fail on any prior-existence ground, and `TestInternalContentFormRootEligibility.test_captures_the_first_ever_domain_object_in_an_empty_case` exercises exactly this against a genuinely empty store. **(G7)** Yes — subject presence necessarily requires a prior accepted object, via `_verify_subject`'s own `TargetNotFoundError` check, which trivially entails the referential form can never be a Case's first Domain Object. **(G8)** No explicit validation is missing: the permissive branch requires no check (an unconditional "MAY" imposes no obligation to verify anything), and the restrictive branch is already, automatically enforced as a byproduct of the pre-existing INV-005 check — no separate, additional root-eligibility validator is needed on top of it. **(G9)** Yes — the API permits a subjectless `CreateJudgmentRequest` (`subject: TypedDomainObjectReferenceSchema | None = None`), confirmed by `TestCreateJudgmentInternalContentForm.test_returns_201_with_no_subject`. **(G10)** Yes — persistence correctly preserves a subjectless Judgment (both subject-reference columns `NULL`), confirmed by the round-trip test `test_persists_the_internal_content_form_with_no_subject`.

**Classification: correct as written.**

## 18. Case-Ownership Analysis

**(I1)** Yes — every Judgment carries exactly one non-nullable `case_id: CaseId`, matching INV-002. **(I2)** The owning Case's own existence is not independently verified against a `CaseRepository` — `JudgmentService.__init__` depends only on `JudgmentRepository` and `KnowledgeReferenceRepository`. This is not a gap introduced by this package: it is the identical, already-established convention followed uniformly by every other implemented module in this codebase (Knowledge Reference, Decision, Observation, Outcome each accept `case_id` as given, with no independent Case-existence check), and no governing source (OE-002 §3.1, OE-004 INV-002) requires such a check — Case's role as ownership boundary is stated without any corresponding validation obligation on referencing modules. **(I3)** Yes — Case is the ownership boundary (OE-002 §3.1), explicitly not a member of the six-type Domain Object Set (§4), a fact already settled by the Domain Object Type Set Discrepancy Investigation (Outcome 1) and correctly reflected throughout this implementation.

## 19. Same-Case Validation Analysis

**(I4)** No — Case cannot be a Judgment subject: `DomainObjectType` has exactly six members (confirmed by direct inspection of `atlas/core/domain/shared/domain_object_type.py`), none named `CASE`; a request naming `"Case"` as `targetType` is rejected by Pydantic's own enum validation at 422, confirmed by `TestUnknownTargetTypeRejection.test_rejects_case_as_an_unknown_target_type_distinctly`. **(I5)** Yes — INV-004 requires every referential subject to belong to the same Case as its referencing Judgment. **(I6)** Yes — correctly applied for Knowledge Reference subjects: `_verify_subject` compares `existing.case_id != case_id` and raises `CrossCaseTargetError`, confirmed by `test_rejects_a_cross_case_knowledge_reference_target` at both the application and API layers. **(I7)** Yes — correctly applied identically for Judgment subjects, confirmed by `test_rejects_a_cross_case_judgment_target` at both layers. **(I8)** Yes — subjectless capture is fully compatible with Case ownership: `case_id = CaseId(request.case_id)` executes unconditionally, before the subject-conditional branch, so `case_id` is always required and recorded regardless of whether a subject is present. **(I9)** Yes — persistence stores `case_id` as an indexed, non-nullable `String` column, matching every other module's convention. **(I10)** No missing check beyond established convention — no module in this codebase enforces a `case_id`→`cases` foreign key or an independent Case-existence check; Judgment's omission is consistent with, not a deviation from, that uniform practice. **(I11)** Yes — the implementation cleanly preserves the distinction: `case_id` establishes ownership (INV-002, always present, never itself validated against a target), while `subject` establishes an optional semantic relationship (INV-004/005, validated only when present) — these remain two structurally and validationally separate concerns throughout `entity.py`, `capture_judgment.py`, and `table.py`.

**Classification (Case ownership and same-Case validation together): correct as written.**

## 20. Prior-Acceptance Validation Analysis

Already addressed in full in Section 13 (E3–E4, E8–E9) — restated here for structural completeness per the required document outline.
