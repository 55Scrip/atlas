# Knowledge Reference Pre-Commit Architecture Review

## 1. Title

Atlas Core — Knowledge Reference (DO-IMP-003) Pre-Commit Architecture Review.

## 2. Status

Engineering review artifact. Not a normative document; carries no Doctrine status. Where anything here conflicts with the Architecture Doctrine, OE-002 through OE-006, or the Historical Decision Record, those documents govern and this review is wrong and must be corrected. This document does not amend architecture; it applies already-adopted architecture to a specific, uncommitted implementation and states whether that implementation is canonically correct.

Limited to the three named questions: (A) whether Knowledge Reference targeting another Knowledge Reference, self-reference, and cycles are handled correctly; (B) whether the current partial referential-validation behavior (accepting Observation/Decision/Outcome targets while rejecting Reasoning Trace/Judgment targets) is canonically correct; (C) whether the implementation's acceptance semantics are correctly represented. Does not reopen any other settled question from this series, and does not perform any correction.

## 6. Implemented Knowledge Reference Contract

As built: `KnowledgeReference(id: KnowledgeReferenceId, case_id: CaseId, target: TypedDomainObjectReference, recorded_at: datetime)`, constructed only via `KnowledgeReference.capture(case_id, target, clock)`. `KnowledgeReferenceService.capture()` (`atlas/core/application/knowledge_reference/capture_knowledge_reference.py`) dispatches on `target.target_type`: Observation/Decision/Outcome targets are checked for existence via their own repositories and accepted if found (same-Case membership is not checked); Knowledge Reference targets are checked for existence and same-Case membership; Reasoning Trace/Judgment targets are rejected with `UnsupportedTargetTypeError`, since no repository exists for either.

## 7. Knowledge-Reference-as-Target Analysis

OE-002 §5.2 Relationships: *"Knowledge Reference MAY reference any other Domain Object defined in this document that belongs to the same Case. No specific Domain Object type is required as its target; the target's type is unrestricted by this document."* Knowledge Reference is itself one of the Domain Objects "defined in this document" (§5.2 is its own definition). This text places no exception on Knowledge Reference referencing another Knowledge Reference — the disclaimer is unconditional ("No specific Domain Object type is required," "unrestricted"). **Knowledge Reference targeting another Knowledge Reference is canonically permitted**, directly, without needing to be inferred.

## 8. Self-Reference Analysis

OE-002 §3's general reference rule uses "another Domain Object" / "that other Domain Object" throughout — language that presupposes two distinct objects, not one object referencing itself. This is reinforced structurally, not merely lexically: INV-005 (OE-004) — *"A Domain Object MUST NOT reference another Domain Object that has not already been accepted"* — combined with INV-008's atomicity (acceptance and event occurrence are the same architectural moment, with no intermediate state) means a candidate Knowledge Reference, at the moment its own target is validated, does not yet exist as an accepted object; it cannot simultaneously be the thing referenced and the thing not-yet-accepted. Self-reference is therefore **structurally forced to be impossible**, not merely unaddressed — this is the identical argument already applied, and already settled, for every other type in this series ("self-reference — structurally impossible," repeated across the Knowledge Reference, Reasoning Trace, Judgment, Decision, and Outcome Implementation Designs).

**In the actual implementation**, this is doubly guaranteed: `KnowledgeReferenceId()` generates its value via `uuid.uuid4()` *inside* `KnowledgeReference.capture()`, which runs only *after* `KnowledgeReferenceService._verify_target()` has already completed. A caller cannot supply, as `target_id`, the identity of an object that does not yet exist and whose identity is not yet known to anyone. Even setting the INV-005/INV-008 argument aside, self-reference is mechanically unreachable through the current code path. No additional runtime check exists for this, and — per the analysis above — none is required for correctness. (A dedicated test proving this explicitly would be a worthwhile documentation improvement; its absence is not a correctness defect — see Section 17.)

## 9. Cycle Analysis

The identical DAG argument forecloses cycles of any length. For a two-member cycle (`A` targets `B`, `B` targets `A`) to exist, `B` would need to be already-accepted at the time `A` is captured (INV-005), and `A` would need to be already-accepted at the time `B` is captured — but exactly one of `A`/`B` is captured first, and at that moment the other does not yet exist to be referenced. No `update` operation exists anywhere in this codebase's convention (permanence, INV-009/010/011) that could retroactively insert a reference after the fact. The same reasoning excludes cycles of any length, not only pairs. **Cycles are structurally impossible**, for the same reason self-reference is, and this holds for the current implementation exactly as it holds for the general architecture — no additional validation is required.

## 10. Partial Referential Validation Analysis

This is the substantive question. OE-006 §5: *"Valid is necessary for acceptance. A candidate MUST NOT be accepted unless its state transition has yielded Valid under OE-005."* OE-006 §16: acceptance establishes *"that the accepted transition satisfies every applicable upstream invariant."* These are unconditional. If INV-004 (same-Case reference) is applicable — and it is, whenever a Knowledge Reference's target is a reference at all, which it always is — then accepting a candidate is a claim that INV-004 was actually checked and holds.

OE-005 §15 draws exactly the distinction this review needs: *"A particular implementation's failure to correctly compute the outcome of a complete subject is an implementation defect; it does not make the normative model itself partial, non-deterministic, or stateful."* This confirms that "the implementation cannot currently check X" is never, by itself, a license to proceed as if X holds — it is described as a **defect**, not as an accepted basis for provisional acceptance. OE-006 §9 removes any remaining ambiguity directly: *"This document does not introduce AcceptedResult, Rejected, Failed, Pending, Deferred, Cancelled, Partially Accepted, Unknown, or any warning state. A separate outcome concept is not forced by the adopted architecture and is explicitly rejected as unnecessary."* There is no "accepted, with a deferred invariant" status anywhere in the adopted acceptance model. Accepting a Knowledge Reference against an Observation/Decision/Outcome target today, without checking INV-004, is not "deferral" in any sense OE-006 recognizes — it is an ordinary acceptance that silently fails to establish what OE-006 §16 requires it to establish.

This reasoning applies symmetrically to the Reasoning Trace/Judgment case (Section 12) — both are instances of the same underlying condition: **an applicable invariant cannot currently be verified for this target type.** Treating the two situations differently (rejecting one pair, accepting the other three) is the specific defect, not either behavior in isolation. Answering the ten numbered sub-questions directly: (1) No — a structurally valid `DomainObjectType` may be rejected today for implementation-readiness reasons, but that is a fact about *why* verification currently fails, not license to skip verification for other types where the same underlying condition (an unverifiable applicable invariant) equally holds. (2) Yes, per OE-006 §5/§16 above. (3) Reject — OE-006 §9 forecloses "defer" and "accept provisionally" as recognized outcomes; "remain unavailable at the API level" is more restrictive than necessary, since a rejection can and should still be surfaced through the ordinary API (a 400-class response), not by removing the capability to submit the request at all. (4) No — see the symmetry argument above. (5) Yes, this asymmetry is exactly the defect. (6) No — see Section 13. (7) See Section 13. (8) Neither — DO-IMP-003 should support exactly the target types whose applicable invariants can be fully verified today (currently: Knowledge Reference only), not "all six" and not "zero." (9) The Reconciliation Plan's own claim (§18) that DO-IMP-003 "could ship... without affecting correctness" is a non-normative planning assertion (Section 5) and does not itself authorize the current behavior once checked against OE-005/006 directly. (10) The wire contract (`{caseId, target: {targetType, targetId}}`) is stable and need not change; only which `target_type` values the application layer currently *admits* will expand as Reasoning Trace, Judgment, and each of Observation/Decision/Outcome's own `case_id` corrections land — a validation-layer change, not a schema/contract change (mirroring the Decision/Outcome storage-permissive/admission-restricted precedent already established in this series).

**Classification: correct only if all unverifiable target types are consistently rejected.**

## 11. Same-Case Validation Analysis

Observation, Decision, and Outcome each lack `case_id` today (DO-REC-026, DO-REC-005, DO-REC-013 — none yet implemented). This is not a case of the validation *subject* being architecturally incomplete: OE-002 §3 ("Every Domain Object belongs to exactly one Case") makes same-Case membership a settled, determinate fact for every accepted Observation/Decision/Outcome instance, whether or not any particular implementation currently records which Case that is. This is precisely OE-005 §15's third category — "implementation inability to evaluate a complete subject" — not "incomplete validation subject" (which concerns the *candidate's own* specification, not a defect in the *implementation's own representation* of prior accepted state). Per Section 10's analysis, this inability does not license acceptance; it requires rejection, for exactly as long as the inability persists.

## 12. Prior-Acceptance Validation Analysis

Reasoning Trace and Judgment have no repository because neither has ever been implemented (DO-IMP-009, DO-IMP-004, neither shipped). This means something stronger than "cannot be verified": **no instance of either type has ever been captured or accepted anywhere in this system.** Therefore, for any candidate `target_id` claimed to be a Reasoning Trace or a Judgment, INV-005 ("a Domain Object MUST NOT reference another Domain Object that has not already been accepted") is not merely unverifiable — it is **determinately violated**, with certainty, because the referenced instance categorically does not exist in accepted state. This is not "implementation inability to evaluate" (Section 11's category); it is an ordinary, fully determinable INV-005 violation, of the same kind as supplying a fabricated Decision id that was never captured. The current implementation's own documentation (its module docstring, and `UnsupportedTargetTypeError`'s own docstring) overstates the uncertainty here — see Section 13.

## 13. Error-Taxonomy Analysis

The current exception hierarchy makes `UnsupportedTargetTypeError` a direct sibling of `TargetNotFoundError` under `KnowledgeReferenceError` (`atlas/core/domain/knowledge_reference/exceptions.py`), and its docstring states it *"does not claim the target does not exist, only that this implementation cannot yet determine whether it does."* Per Section 12, this claim is stronger than the facts support in the wrong direction: this implementation *can* determine that the target does not exist in accepted state — the determination is simply "no," with certainty, not "unknown." The correct classification is that a Reasoning Trace/Judgment target candidate is an **ordinary INV-005 violation** — the same normative category as `TargetNotFoundError` — with the "no repository exists yet" fact serving only as an explanation of *why* the answer is certainly no, not as grounds for a distinct validation-outcome category. Per Section 11, the Observation/Decision/Outcome INV-004 gap is a genuinely different condition (an implementation-inability gap, not a determinate violation) but, per Section 10, resolves to the identical required action: reject. **Required correction**: unify the rejection path for both conditions under one honestly-labeled category (e.g., expressing "an applicable invariant for this target type cannot currently be established," with `TargetNotFoundError`/`UnsupportedTargetTypeError` restructured so the latter is not presented as epistemically weaker than an ordinary rejection) — detailed in Section 17.

## 14. Acceptance-Lifecycle Analysis

No separate proposal, draft, pending, or acceptance workflow exists anywhere in the adopted architecture (OE-006 §9's own explicit rejection of Pending/Deferred/etc. as recognized states) or anywhere else in this codebase's own established convention (every sibling aggregate — Decision, Outcome, Observation, Hypothesis, Case — treats construction-plus-repository-insertion as the acceptance moment, with no intermediate state). The implementation's `KnowledgeReference.capture()` + `KnowledgeReferenceRepository.add()` correctly represents this: acceptance IS creation-and-persistence, atomically, matching INV-008. `recorded_at` is set exactly once, internally, at capture time — correctly representing INV-015's "acceptance time is event time," never user-supplied. A separate `accepted_at` field would not be forbidden by any explicit text, but would be strictly redundant with `recorded_at` under the adopted model and is correctly omitted per the Decision Standard's "smallest technical mechanism" test. The service and endpoint naming ("capture," `POST /knowledge-references`) correctly express this, consistent with every sibling module. **This part of the implementation requires no correction** — its only defect is the one already identified in Sections 10–13: acceptance is, today, sometimes occurring without the full Valid determination OE-006 §16 requires it to represent.

## 15. Implementation-versus-Report Verification

The prior DO-IMP-003 delivery report's description of the code was accurate as a description of *what the code does*: Observation/Decision/Outcome targets are genuinely checked for existence and accepted if found, without a same-Case check; Reasoning Trace/Judgment targets are genuinely rejected via a dedicated exception; 53 tests genuinely exist and genuinely pass, exercising exactly this behavior. No mismatch was found between the report and the actual code. The mismatch found by this review is between **the code (correctly reported) and the governing architecture** (Sections 10–13) — a canonical-correctness question the prior report did not itself resolve, since it characterized the deferral as an accepted, disclosed limitation rather than checking it against OE-005 §15's and OE-006 §9's own specific text.

## 17. Required Corrections, If Any

Stated precisely, not performed (per this task's own restriction):

1. In `atlas/core/application/knowledge_reference/capture_knowledge_reference.py`'s `_verify_target`, remove the branches that accept `DomainObjectType.OBSERVATION`, `DomainObjectType.DECISION`, and `DomainObjectType.OUTCOME`. Route all five of Observation, Decision, Outcome, Reasoning Trace, and Judgment through one consistent rejection path. Only `DomainObjectType.KNOWLEDGE_REFERENCE` remains an acceptable target today, since it is the only type for which both INV-005 and INV-004 are currently, fully verifiable.
2. In `atlas/core/domain/knowledge_reference/exceptions.py`, restructure so the rejection reason for Observation/Decision/Outcome (INV-004 unverifiable) and for Reasoning Trace/Judgment (INV-005 determinately violated — Section 12) are not presented as a single conflated "unsupported" idea, and so `UnsupportedTargetTypeError`'s docstring no longer claims uncertainty ("cannot yet determine whether it does") for the Reasoning Trace/Judgment case specifically, where the correct claim is certainty (it does not exist, because nothing of that type has ever been accepted).
3. Update the module docstring in `capture_knowledge_reference.py`, which currently frames the Observation/Decision/Outcome behavior as an accepted "deferral" — per Section 10, no such state is recognized by OE-006 §9, and the corrected docstring should state the target types are rejected, not accepted-with-a-gap.
4. Update tests: `TestCaptureAgainstEachSupportedTargetType`'s Observation/Decision/Outcome cases must assert rejection, not acceptance; `TestDeferredSameCaseValidation` (which currently documents and validates the very behavior found incorrect here) must be replaced with a test proving consistent rejection; corresponding API tests (`test_router.py`) and their dependency wiring change symmetrically.
5. `KnowledgeReferenceService`'s constructor dependencies on `ObservationRepository`, `DecisionRepository`, and `OutcomeRepository` become unnecessary once correction 1 lands, since none of those three types would remain an acceptable target; `dependencies.py` and `router.py` simplify accordingly.

None of these corrections requires a new architectural decision; all are derivable directly from OE-005/OE-006 as already adopted.

## 19. Open Questions

**Q1 — Once DO-REC-026/005/013 land `case_id` on Observation/Decision/Outcome, does re-enabling those target types in Knowledge Reference require any further architectural decision, or is it purely mechanical?** Purely mechanical, given the corrected structure recommended in Section 17: each type's own branch would simply add the same-Case check its own `case_id` field newly makes possible, with no schema or contract change to Knowledge Reference itself. Not resolved further here, since it is future implementation work, not a present architectural question.

## 20. Final Conclusion

**Outcome 2 — Ready after narrow correction.** Knowledge Reference targeting another Knowledge Reference is canonically correct and requires no change; self-reference and cycles are already, correctly, structurally impossible and require no change. The genuine defect is in referential validation: OE-006 §5, §9, and §16, read together with OE-005 §15, do not permit accepting a Knowledge Reference against a target type whose applicable invariant (INV-004 for Observation/Decision/Outcome; INV-005 for Reasoning Trace/Judgment) cannot currently be established — "accepted with a deferred invariant" is not a status this architecture recognizes. The correct, immediately implementable state is narrower than what was built: Knowledge Reference may, today, validly target only another Knowledge Reference, with every other adopted type's target-eligibility restored incrementally as each one's own prerequisite work lands, requiring no change to Knowledge Reference's own schema or API contract when it does.
