# Domain Object Implementation Reconciliation Plan

## 1. Title

Atlas Core — Domain Object Implementation Reconciliation Plan.

## 2. Status

Engineering planning artifact. Not a normative document; carries no Doctrine status. Where anything here conflicts with the Architecture Doctrine, OE-002 through OE-006, the Historical Decision Record, or a completed Implementation Design, those documents govern and this plan is wrong and must be corrected. This document does not invent, reinterpret, or resolve architecture; it only maps already-adopted architecture onto the repository's actual current state and sequences the engineering work required to close the gap.

## 3. Purpose

To determine precisely how the current repository must change so that its implementation faithfully realizes the already-adopted Atlas Core Domain Object architecture (OE-002 through OE-006, and the five completed Implementation Design documents), and to sequence that change into reviewable, independently verifiable engineering packages.

## 4. Scope

Covers: OE-002 §4's six canonical Domain Object types (Observation, Knowledge Reference, Reasoning Trace, Judgment, Decision, Outcome) and Case, the ownership boundary OE-002 §3.1 defines separately from — and not as a member of — that closed set (see docs/atlas_domain_object_architecture/Domain-Object-Type-Set-Discrepancy-Investigation.md, which this plan's own Section 8 and Reconciliation Register now reflect); every existing domain/persistence/application/API module that implements, partially implements, or contradicts any of them; every legacy Core Loop concept that overlaps semantically with an adopted type (Hypothesis, Evaluation, Learning, `reasoning_link`, Question, Interpretation, Conclusion, Evidence); shared typed-reference infrastructure; invariant-enforcement mapping; persistence/migration analysis; API reconciliation; test reconciliation; dependency ordering; and a phased delivery plan.

## 5. Non-Goals

This document does not: invent new domain semantics; resolve the OE-002 §5 internal-versus-referential coexistence question for Judgment, Decision, or Outcome (already correctly left open by three completed Implementation Designs); resolve whether Question, Interpretation, Conclusion, or Evidence reduce to an adopted type (no canonical source addresses this — Section 21); modify production code, tests, or migrations; or stage, commit, tag, or push anything.

## 7. Executive Finding

The governing ontology (OE-002 through OE-006, plus the five completed Implementation Designs) is settled and internally consistent. The repository's implementation is **substantially non-conformant**: three of the six canonical Domain Objects have **zero implementation** (Knowledge Reference, Reasoning Trace, Judgment); the three that exist (Observation, Decision, Outcome) deviate from their own canonical requirements on ownership, cardinality, nullability, and target-restriction grounds; and three legacy Core Loop aggregates (Hypothesis, Evaluation, Learning) are fully implemented as independent, persisted entities despite the Historical Decision Record explicitly naming two of them (Evaluation, Learning) as considered-and-rejected, reducible to Judgment — a canonical document has already answered this question, and the code has not yet caught up. Separately, Case — the ownership boundary (OE-002 §3.1), not a member of the six-type Domain Object Set — is now implemented (DO-IMP-001, committed) as the foundational aggregate every canonical type must eventually carry a `case_id` toward; it is not itself one of the "three that exist" among the six canonical types, and correcting an earlier substitution of Case for Observation in this document's own Section 8 and Reconciliation Register is itself one of this revision's corrections (per docs/atlas_domain_object_architecture/Domain-Object-Type-Set-Discrepancy-Investigation.md, Outcome 1). No canonical-versus-canonical contradiction was found anywhere; every discrepancy identified is an implementation gap or legacy carryover, not an ontological dispute. **Implementation-readiness outcome: Outcome 2 — Ready with explicit non-blocking risks** (Section 22).

## 10. Current Implementation Model

### 10.1 Case

**Does not exist.** `grep -rn "class Case"` and `grep -rln "case_id"` across `atlas/` both return zero hits. No aggregate, no field, no table. Every existing entity that needs an owner uses an ad hoc, object-specific field instead (Decision has `user_id`; Outcome, Evaluation, Learning, Hypothesis have no owner field at all — their ownership is only transitively implied through a chain of foreign-key-style references back to Decision). This is the single largest structural gap in the repository relative to the canonical model, since INV-002 requires every Domain Object to belong to exactly one Case, and nothing currently does.

### 10.2 Knowledge Reference

**Does not exist.** Zero domain, persistence, application, or API code under `atlas/core/`. The unrelated `atlas/domains/knowledge/` feature (Section 9) must not be reused or renamed into this role — it has its own, different fields, semantics, and callers, and repurposing it would smuggle unrelated legacy behavior into the canonical type under its name.

### 10.3 Reasoning Trace

**Does not exist as such.** The closest existing concept, `atlas/core/domain/reasoning_link/entity.py`, is four separate frozen dataclasses (`QuestionObservationLink`, `InterpretationHypothesisLink`, `HypothesisEvidenceLink`, `ConclusionDecisionLink`), each a single, hard-typed 1:1 pointer between exactly two Core-Loop aggregates plus a `linked_at` timestamp — structurally a point-to-point bridge/join record, not a set of typed supporting-object references directed at one independently-identified Trace object. Its own module docstring self-labels this **"PROVISIONAL STATUS"**, explicitly anticipating that "a later iteration will decide whether this responsibility belongs in the domain model, moves to pure in-memory application-layer orchestration, or take[s] some other shape entirely." It is wired into real code (`atlas/core/application/reasoning_link/*.py`, `atlas/core/infrastructure/persistence/reasoning_link/*.py`, `atlas/core/application/conversation/{orchestrator,composition}.py`) and is not dead code, but it is not, and does not purport to be, an implementation of Reasoning Trace.

### 10.4 Judgment

**Does not exist.** Zero domain, persistence, application, or API code anywhere. Every case-insensitive hit for "judgment" across `atlas/` is either ordinary-English prose/docstring text or an unrelated boolean flag (`user_judgment_required` in `atlas/temporary_workspace/schema.py`), never a domain type.

### 10.5 Decision

**Exists, substantially deviating from its own completed Implementation Design.**

- `atlas/core/domain/decision/entity.py` — fields: `id`, `user_id`, `decision_type`, `subject`, `investment_case`, `confidence`, `decided_at`, `recorded_at`, `source`. No `case_id`. No `commitment_content`/`matter_target_type`/`matter_target_id`.
- `atlas/core/infrastructure/persistence/decision/table.py` — a matching flat table, no CHECK constraints beyond SQLAlchemy column types, no minimum-presence or storage-permissive design (there is nothing to constrain — the alternate-form fields don't exist yet).
- `atlas/core/infrastructure/api/decision/{router,schemas}.py` — `POST /decisions`, `GET /decisions`, `GET /decisions/{decision_id}`; `CreateDecisionRequest` fields: `user_id`, `decision_type`, `subject`, `reason`, `confidence`, `decided_at`, `source` — mirrors the entity's current, non-canonical shape exactly.
- Tests: `tests/unit/domain/decision/{test_entity,test_value_objects}.py`, `tests/unit/infrastructure/persistence/decision/test_sqlalchemy_repository.py`, `tests/unit/infrastructure/api/decision/test_router.py` — all currently assert the present shape as correct (required `subject`/`decision_type`/`confidence`, no `case_id`).

### 10.6 Outcome

**Exists, substantially deviating from its own completed Implementation Design.**

- `atlas/core/domain/outcome/entity.py` — fields: `id`, `decision_id` (**required**, `DecisionId`), `statement` (**required**), `occurred_at` (**required**, timezone-validated), `recorded_at`, `note` (optional). No `case_id`. No generic `matter_target_type`/`matter_target_id`.
- `atlas/core/infrastructure/persistence/outcome/table.py` — `decision_id NOT NULL`, `statement NOT NULL`, no SQL foreign key (already matching this design's own no-FK convention, Section 13).
- `atlas/core/application/outcome/capture_outcome.py` — mandatorily verifies the referenced Decision exists before construction.
- **No API layer exists at all** — `atlas/core/infrastructure/api/outcome/` does not exist.
- Tests: `tests/unit/domain/outcome/{test_entity,test_value_objects}.py`, `tests/unit/application/outcome/test_capture_outcome.py`, `tests/unit/infrastructure/persistence/outcome/test_sqlalchemy_repository.py` — all currently assert mandatory `decision_id`/`statement` as correct; no API test exists because no API exists.

### 10.7 Reasoning Act

**No footprint anywhere.** Zero hits for `reasoning_act`/`ReasoningAct`/"reasoning act" across the entire repository (code, docs outside the two doctrine tracks, tests, migrations — none exist). The closest adjacent code — `RecognizedPattern`/`RecognizedStrategySignature` (`pattern_recognition`, `strategy_signature`), `DecisionReflection` (`decision_reflection`), `CoachingQuestion` (`decision_coach`) — are explicitly, self-documented as transient, non-persisted, recomputed-per-call value objects with no table, no repository, no identity beyond content. Nothing currently smuggles Reasoning Act back in under another name.

### 10.8 Other Legacy Concepts

- **Hypothesis** (`atlas/core/domain/hypothesis/entity.py`): fields `id`, `statement`, `formulated_at`, `recorded_at`, `note`. Its own docstring states it is "not an Observation, not Evidence, not a Decision, not an Outcome, not a truth claim, and not an Atlas-generated conclusion" and is "deliberately standalone." Fully wired: table, repository, API router (`atlas/core/infrastructure/api/hypothesis/router.py`), and a `reasoning_link` edge (`InterpretationHypothesisLink`, `HypothesisEvidenceLink`).
- **Evaluation** (`atlas/core/domain/evaluation/entity.py`): fields `id`, `outcome_id` (required), `statement`, `evaluated_at`, `recorded_at`, `note`. Fully wired: table, repository, application service.
- **Learning** (`atlas/core/domain/learning/entity.py`): fields `id`, `evaluation_id` (required), `statement`, `learned_at`, `recorded_at`, `note`. Fully wired: table, repository, application service.
- **Question, Interpretation, Conclusion, Evidence**: each an independent, similarly-shaped Core Loop aggregate (`atlas/core/domain/{question,interpretation,conclusion,evidence}/entity.py`), chained together via `reasoning_link`'s four bridge types. No canonical source — not OE-002, not the Historical Decision Record, not any completed Implementation Design — addresses any of these four by name.

### 10.9 Observation

**Added by this correction** (per docs/atlas_domain_object_architecture/Domain-Object-Type-Set-Discrepancy-Investigation.md, Outcome 1): this subsection was absent from the original plan because Observation had been incorrectly excluded from the plan's own six-type framing. Placed here, at the end of Section 10, rather than renumbered to its more natural position after 10.1, to avoid renumbering every existing subsection.

**Exists, substantially deviating from OE-002 §5.1 on ownership grounds; otherwise the closest-conforming of the pre-existing aggregates.**

- `atlas/core/domain/observation/entity.py` — fields: `id`, `subject`, `statement`, `observed_at`, `recorded_at`, `source` (optional), `note` (optional). **No `case_id`** — the same INV-002 ownership gap as Decision, Outcome, and Hypothesis.
- `atlas/core/infrastructure/persistence/observation/table.py` — `subject NOT NULL`, `statement NOT NULL`, `source`/`note` nullable, no foreign key. No CHECK constraint issue exists here at all: unlike Decision/Outcome, Observation has no alternate-form (content-or-reference) structure to enforce — OE-002 §5.1 requires only that informational content be preserved, and `statement` already satisfies that unconditionally.
- `atlas/core/infrastructure/api/observation/schemas.py` — `CreateObservationRequest`/`ObservationResponse`, already `CamelModel`-based, already camelCase (`observedAt`, `recordedAt`, etc.) — no serialization-convention fix is needed here, unlike Decision's original snake-case-only shape.
- Tests: `tests/unit/domain/observation/*`, `tests/unit/application/observation/test_capture_observation.py`, `tests/unit/infrastructure/persistence/observation/*`, `tests/unit/infrastructure/api/observation/test_router.py` — all currently assert the present, `case_id`-less shape as correct.
- **`subject`, `source`**: `subject` is extra structure beyond OE-002 §5.1's own minimal "informational content" requirement, and `source` is optional provenance metadata OE-002 does not address — both parallel Decision's own deferred `decision_type`/`confidence`/`source` fields (Section 12, DO-REC-008): permissible internal-content candidates, not resolved here.
- **Reference-target readiness**: Observation requires **no schema change at all** to become a valid typed-reference target once Knowledge Reference, Reasoning Trace, Judgment, Decision, or Outcome can reference it — referencing is entirely owned by the referencing object's own `target_type`/`target_id` pair (Section 11); Observation's own table needs only its `case_id` fix, independent of reference-eligibility.
- **Reconciliation item**: DO-REC-026 (Section 14); **delivery package**: DO-IMP-013 (Section 19), with the identical dependency shape as DO-IMP-006/DO-IMP-007 (soft-depends only on DO-IMP-001/DO-IMP-002).

## 11. Cross-Cutting Infrastructure Findings

- **No shared typed-reference infrastructure exists.** Grep across `atlas/core/domain/*/{entity,value_objects}.py` for `target_type`, `target_id`, `TargetType`, `matter_target`, `subject_target`, or any `PolymorphicRef`-style name returns zero matches anywhere. Every existing cross-aggregate pointer (`Outcome.decision_id`, `Evaluation.outcome_id`, `Learning.evaluation_id`, each `reasoning_link` bridge field) is a fixed, single-purpose, concretely-typed id — never polymorphic. This must be built from scratch (Section 12, DO-REC-021).
- **`CamelModel` (`atlas/core/infrastructure/api/serialization.py`) is correctly built and reusable as-is.** A plain `pydantic.BaseModel` subclass: `model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)`. Governed by ADR-004. Every new API schema in this plan (Case, Knowledge Reference, Reasoning Trace, Judgment, and the corrected Decision/Outcome/Observation schemas) must subclass this directly — no new serialization convention is introduced. Observation's existing schemas already do so correctly (Section 10.9) and require no serialization-layer change.
- **No migration/schema-versioning tool exists** (Section 9). Every persistence change in this plan is expressed as a hand-written, one-time transformation, not an Alembic revision.

## 13. Invariant Enforcement Matrix

| Invariant | Statement (abbreviated) | Enforcement layer(s) | Notes |
|---|---|---|---|
| INV-001 | Closed type sets | Domain construction (reject unknown `target_type`/claimed object type) + API validation | No database CHECK can enumerate "all adopted Domain Object types" safely without duplicating the enum in two places — use one shared `DomainObjectType` enum (Section 16) validated at both the domain constructor and the DB CHECK, generated from the same source. |
| INV-002 | Single Case ownership | Domain construction (require `case_id` at construction) + database `NOT NULL` column | Cannot be a foreign key today (no other Case-scoping mechanism exists) but must become one once Case exists as a table (Section 15). |
| INV-003 | Event-object Case correspondence | Application service (construct event with the same `case_id` as its object) | No dedicated Domain Event tables exist yet in this repository (events are, today, implicit in acceptance, not separately persisted rows) — flagged as an open architectural dependency for a future, separate investigation; out of scope for this plan, which only reconciles Domain Objects, not Domain Events (OE-003 explicitly excludes event persistence mechanics from its own scope). |
| INV-004 | Same-Case reference | Application service (validate target's `case_id == candidate.case_id` before construction) — **cannot be a database foreign key**, since the target may belong to any of six differently-tabled types | Requires a shared, repository-agnostic lookup port (Section 16). |
| INV-005 | Prior acceptance of referenced targets | Application service (target existence + acceptance check via each target type's own repository) — **cannot be a database foreign key** for the identical polymorphic reason as INV-004 | Ordinary FK cannot span six heterogeneous tables; this is a genuine, disclosed limit of relational foreign keys, not an oversight (Section 16). |
| INV-006 | Distinct identity | Domain construction (UUID generation) + database `PRIMARY KEY` | Already correctly enforced everywhere identity exists today. |
| INV-007 | Exactly one acceptance event per object | Application service (acceptance transaction constructs exactly one corresponding event) | Structurally trivial once each object's acceptance path is singular, per every completed Implementation Design. |
| INV-008 | Atomic acceptance/event occurrence | Application service, inside one database transaction | Already the pattern used by every existing `*Service.capture()` method (e.g. `OutcomeService.capture`). |
| INV-009/010/011 | Permanence, non-erasure | Repository boundary (no `update`/`delete` method exposed at all) | Already correctly enforced for Decision, Outcome, Hypothesis, Evaluation, Learning (all insert-only repositories today). |
| INV-012 | Root eligibility | Application service, at construction time, conditional on which form is used | Not yet enforceable for Judgment, Decision (partially), or Outcome (partially), since Case does not yet exist to be "first" in. |
| INV-013 | Reasoning Trace minimum support | Domain construction (reject empty supporting set) | To be built as part of Reasoning Trace (DO-REC-003). |
| INV-014 | Knowledge Reference single target | Domain construction (`target_type`/`target_id` required, non-nullable pair) | To be built as part of Knowledge Reference (DO-REC-002). |
| INV-015 | Acceptance time as event time | Domain construction (`recorded_at` always the acceptance clock; any represented time is a separate, distinctly named field, e.g. Outcome's `occurred_at`) | Already correctly separated for Outcome (`occurred_at` vs `recorded_at`) and Decision (`decided_at` vs `recorded_at`) in existing code — this specific distinction is one of the few things the legacy implementation already gets right. |
| Storage-permissive / admission-restricted (Decision, Outcome) | At least one realized form required; combined form representable but domain-unadmitted | Database: single `CHECK` (minimum presence, not XOR). Domain/API: reject combined form as Invalid with a distinctly-labeled, non-numbered finding. | Not yet built anywhere — the alternate-form fields do not exist in current schema at all (DO-REC-007, DO-REC-014). |

No invariant in this matrix can be enforced purely by an ordinary SQL foreign key where the referenced object's type is polymorphic (INV-004, INV-005) — this is stated explicitly per Section 8's own instruction not to overclaim foreign-key enforcement.

Full detail for the five most consequential items and DO-REC-026 (added by this correction) follows; the remaining items follow the identical field structure and are fully specified in the Engineering Delivery Packages (Section 19), where "required change" and "acceptance criteria" are stated per package rather than repeated twice.

**DO-REC-001 — Case aggregate does not exist**
*Current implementation*: none. *Canonical requirement*: every Domain Object belongs to exactly one Case (INV-002); Case's own semantics are limited to the ownership-boundary role (OE-002 §3.1) — no lifecycle, status, or additional field is forced. *Exact discrepancy*: zero code footprint; every existing entity either has no owner field or uses an ad hoc substitute (`Decision.user_id`). *Architectural source*: OE-002 §3.1, §3; INV-002. *Affected files/symbols*: none yet exist; new module `atlas/core/domain/case/`. *Required change*: introduce `Case` (`id: CaseId`) with a table, repository, and no API surface required by canon (an API MAY be added for operational convenience, but OE-002 does not force one). *Compatibility impact*: none (purely additive). *Migration impact*: none for this package alone; every downstream object that must gain `case_id` (Decision, Outcome, Hypothesis, Evaluation, Learning) requires a backfill policy decision once Case exists (Section 15, Section 21 Q3). *API impact*: none required. *Test impact*: new entity/persistence tests. *Dependencies*: none (root of the dependency graph). *Risk level*: High (blocks everything else). *Phase*: 1. *Acceptance criteria*: `Case` constructs, persists, and round-trips via a real repository; no other module yet depends on it.

**DO-REC-004 — Judgment has zero implementation**
*Current implementation*: none. *Canonical requirement*: `id`, `case_id`, required `characterization`, optional `{subject_target_type, subject_target_id}`, `recorded_at` (Judgment-Implementation-Design.md). *Exact discrepancy*: total absence. *Architectural source*: OE-002 §5.4; Judgment-Implementation-Design.md Section 30. *Affected files/symbols*: none yet exist; new module `atlas/core/domain/judgment/`. *Required change*: build domain/persistence/application/API layers per the completed design, using the shared typed-reference infrastructure (DO-REC-021) for the optional subject reference. *Compatibility impact*: none (additive). *Migration impact*: none for new rows; Judgment becomes the reduction target for Hypothesis, Evaluation, and Learning (DO-REC-016/017/018), which does carry migration impact for those three modules, not for Judgment itself. *API impact*: new `POST/GET /judgments` surface, `CamelModel`-based. *Test impact*: full new test suite mirroring the existing Decision/Outcome test shape (entity, value objects, persistence, API). *Dependencies*: DO-REC-001 (Case), DO-REC-021 (typed-reference infra). *Risk level*: High — blocks the Hypothesis/Evaluation/Learning reduction. *Phase*: 5. *Acceptance criteria*: Judgment constructs, rejects missing `characterization`, accepts either zero or one subject reference, persists, round-trips, and exposes a working API endpoint.

**DO-REC-007 — Decision entity lacks alternate-form matter fields entirely**
*Current implementation*: `subject: str` and `investment_case: str` are both effectively always required today (no nullable-alternation exists at all); no `matter_target_type`/`matter_target_id` pair exists. *Canonical requirement*: nullable `commitment_content` and/or nullable `{matter_target_type, matter_target_id}`, at least one required, storage-permissive/admission-restricted for the combined case (Decision-Implementation-Design.md Section 30, Section 34, and its appended Committed-To Matter Completeness Review). *Exact discrepancy*: today's `subject`/`investment_case` pair does not correspond to either canonical form cleanly — it is free text with no reference capability at all, and both fields are simultaneously mandatory rather than alternately required. *Architectural source*: OE-002 §5.5; Decision-Implementation-Design.md Sections 12, 30, 34. *Affected files/symbols*: `atlas/core/domain/decision/entity.py`, `value_objects.py`; `atlas/core/infrastructure/persistence/decision/table.py`. *Required change*: introduce nullable `commitment_content` (folding `subject`+`investment_case`'s legitimate free-text role into this single field, pending DO-REC-008's own resolution of whether they carry additional unresolved semantics) and nullable `matter_target_type`/`matter_target_id`; add a minimum-presence CHECK constraint (`commitment_content IS NOT NULL OR (matter_target_type IS NOT NULL AND matter_target_id IS NOT NULL)`), no XOR. *Compatibility impact*: breaking for any caller currently relying on `subject`/`investment_case` being distinct, always-present fields. *Migration impact*: transitional — existing rows already have non-null `subject`/`investment_case`; a data transformation must decide how to populate `commitment_content` from the two legacy fields (Section 15, Section 21 Q4) — a genuine data-policy question, not an ontological one. *API impact*: `CreateDecisionRequest`/`DecisionSummary` schemas change shape (Section 16). *Test impact*: full rewrite of `tests/unit/domain/decision/{test_entity,test_value_objects}.py` and related persistence/API tests (DO-REC-023). *Dependencies*: DO-REC-001, DO-REC-021. *Risk level*: High. *Phase*: 6. *Acceptance criteria*: content-only, reference-only, and neither-present cases behave per Decision-Implementation-Design.md Sections 33/34/39 exactly; combined-present is rejected with the distinctly-labeled finding, never silently accepted.

**DO-REC-011 — Outcome entity mandates `decision_id`**
*Current implementation*: `decision_id: DecisionId` is a required, non-nullable field; `OutcomeService.capture()` mandatorily verifies the Decision exists. *Canonical requirement*: "Outcome does not require a Decision" (OE-002 §5.6); a reference, where used, may target any of the six adopted types, never restricted to Decision (Outcome-Implementation-Design.md Section 14, Section 42). *Exact discrepancy*: today's Outcome cannot exist without a Decision, and cannot reference anything other than a Decision — both directly contradicted by canon. *Architectural source*: OE-002 §5.6 Relationships clause; Outcome-Implementation-Design.md Section 42 (already flags this as "a genuine, three-part existing-code/ontology mismatch... classified as requiring a future migration, not merely additive compatibility"). *Affected files/symbols*: `atlas/core/domain/outcome/entity.py`, `value_objects.py`, `atlas/core/application/outcome/capture_outcome.py`, `atlas/core/infrastructure/persistence/outcome/table.py`, `sqlalchemy_repository.py`. *Required change*: make `decision_id`-equivalent nullable and generalize it into `matter_target_type`/`matter_target_id`, unrestricted to any of the six types. *Compatibility impact*: breaking. *Migration impact*: transitional — existing rows all have a real `decision_id`; the transformation maps each to `matter_target_type = "decision"`, `matter_target_id = <the existing decision_id>` (a lossless, mechanical rewrite, not a policy question, since the value is already fully known). *API impact*: none pre-existing to break (no API layer exists yet, DO-REC-015), but the future API must be built against the corrected shape from day one. *Test impact*: full rewrite of `tests/unit/domain/outcome/*` and `tests/unit/application/outcome/test_capture_outcome.py` (DO-REC-024). *Dependencies*: DO-REC-001, DO-REC-021. *Risk level*: High. *Phase*: 7. *Acceptance criteria*: an Outcome can be constructed with content-only, reference-only (to any of the six types, not just Decision), or (representable-but-rejected) both; existing `decision_id` rows migrate losslessly to the generalized reference shape.

**DO-REC-017 / DO-REC-018 — Evaluation and Learning exist despite explicit rejection**
*Current implementation*: both fully persisted, independent aggregates (`Evaluation`: `id`, `outcome_id`, `statement`, `evaluated_at`, `recorded_at`, `note`; `Learning`: `id`, `evaluation_id`, `statement`, `learned_at`, `recorded_at`, `note`), each with its own table, repository, and application service. *Canonical requirement*: the Historical Decision Record states, verbatim: "An earlier candidate set of eight Domain Object types, additionally including Evaluation and Learning Event... Evaluation and Learning Event were each found reducible to Judgment: neither demonstrated a semantic operation, identity condition, validity condition, or relationship topology distinct from Judgment's own established characterization function. No forcing function was found for retaining either despite this finding." *Exact discrepancy*: this is a canonical document naming these exact two concepts and explicitly rejecting their independent existence — the strongest, most direct legacy/ontology contradiction found anywhere in this investigation. *Architectural source*: Historical-Decision-Record-Domain-Object-Architecture-Foundation.md, "Decision History: OE-002 — Domain Object Model." *Affected files/symbols*: `atlas/core/domain/{evaluation,learning}/*`, `atlas/core/infrastructure/persistence/{evaluation,learning}/*`, `atlas/core/application/{evaluation,learning}/*`, plus every caller (`decision_review`, `decision_timeline`). *Required change*: each Evaluation instance becomes a Judgment whose `characterization` is the existing `statement` and whose subject reference targets the existing `outcome_id` (as an Outcome-typed `matter`/subject target); each Learning instance becomes a Judgment whose subject reference targets the corresponding prior Judgment (formerly Evaluation) it was drawn from; the independent `evaluation`/`learning` modules are then retired. *Compatibility impact*: breaking for every current caller of `EvaluationRepository`/`LearningRepository`. *Migration impact*: data-carrying, non-mechanical — requires Judgment to exist first (DO-REC-004) and a real, one-time data transformation (not merely additive); this is a genuine data-policy question only in the sense of *sequencing* (must run after Judgment ships), not in the sense of losing information (every field maps cleanly). *API impact*: none pre-existing (`evaluation`/`learning` have no API routers today) — no external contract breaks. *Test impact*: retire `tests/unit/domain/{evaluation,learning}/*`, `tests/unit/application/{evaluation,learning}/*`; add Judgment-based equivalents; update `decision_review`/`decision_timeline` tests that currently construct `Evaluation`/`Learning` directly. *Dependencies*: DO-REC-004 (Judgment must exist first). *Risk level*: High (most severe legacy contradiction in the repository, but mechanically tractable). *Phase*: 9b. *Acceptance criteria*: no code constructs `Evaluation` or `Learning` after this package; every existing evaluation/learning row is represented as an equivalent Judgment with no information loss; `decision_review` and `decision_timeline` read the reduced Judgment-based data with unchanged observable behavior.

**DO-REC-026 — Observation entity has no `case_id`** *(added by this correction — Observation was omitted from the original register due to the same Case-for-Observation substitution corrected throughout this document; see docs/atlas_domain_object_architecture/Domain-Object-Type-Set-Discrepancy-Investigation.md)*
*Current implementation*: `atlas/core/domain/observation/entity.py` has fields `id`, `subject`, `statement`, `observed_at`, `recorded_at`, `source`, `note` — no `case_id`. *Canonical requirement*: every Domain Object belongs to exactly one Case (INV-002); Observation is one of OE-002 §4's six adopted Domain Objects and is not exempt. *Exact discrepancy*: identical in kind to Decision's and Outcome's own INV-002 gap (DO-REC-005, DO-REC-013) — no owner field of any kind exists. *Architectural source*: OE-002 §3, §5.1; INV-002. *Affected files/symbols*: `atlas/core/domain/observation/entity.py`; `atlas/core/infrastructure/persistence/observation/table.py`. *Required change*: add `case_id NOT NULL`. Unlike Decision/Outcome, no alternate-form/matter-reference correction is needed — Observation's own `statement` already unconditionally satisfies OE-002 §5.1's minimal content requirement, so this is a single-field addition, not a multi-field redesign. *Compatibility impact*: breaking for any caller constructing `Observation` without a Case context. *Migration impact*: transitional — existing rows need a `case_id` backfill, subject to the identical policy question already raised for Decision/Outcome/Hypothesis (Section 21 Q3), extended here to include Observation's own existing rows. *API impact*: `CreateObservationRequest`/`ObservationResponse` gain a `caseId` field; otherwise unchanged — Observation's schemas are already `CamelModel`-based and require no other correction. *Test impact*: update `tests/unit/domain/observation/*`, `tests/unit/infrastructure/persistence/observation/*`, `tests/unit/infrastructure/api/observation/test_router.py` to require and round-trip `case_id`. *Dependencies*: DO-REC-001 (Case). *Risk level*: High (ownership gap, but narrowly scoped — no matter-reference redesign needed). *Phase*: 13. *Acceptance criteria*: Observation requires and persists `case_id`; every existing test passes against the corrected shape; `subject`/`source` remain deferred, unresolved, permissible-content candidates (not resolved by this item).

**Deviation from the task brief's suggested ordering, and why**: the brief suggests Knowledge Reference before Judgment before Decision before Outcome before Reasoning Trace, with legacy removal after. Repository reality forces two changes: (1) **Case must come first**, since it is a hard dependency of every other package and does not appear in the brief's own ordering at all — this repository, unlike the brief's assumed starting point, has no Case implementation whatsoever; (2) **Judgment must ship before Decision/Outcome's own corrections are load-bearing for legacy reduction**, but Decision and Outcome's *own* corrections (DO-IMP-006/007) only hard-depend on DO-IMP-002 (typed-reference infra) and DO-IMP-001 (Case), not on Judgment or Knowledge Reference — so DO-IMP-006/007 may proceed in parallel with DO-IMP-003/004/005 once DO-IMP-002 lands, rather than waiting in strict sequence. **Migration dependencies**: DO-IMP-008 cannot retire `evaluations`/`learnings` until every existing row has a verified-equivalent Judgment row (Section 15); DO-IMP-005 has the identical constraint for `hypotheses`.

**Changes that should be kept in the same atomic delivery**: within DO-IMP-006 (Decision) and DO-IMP-007 (Outcome), the schema change, the domain-constructor change, and the corresponding test rewrite must land together — a schema change without the matching constructor/validation change would leave the database more permissive than the domain layer enforces, silently reopening the exact storage-permissive/domain-restrictive distinction each object's own design depends on.

## 21. Open Questions

**Q1 — What is the canonical disposition of Question, Interpretation, Conclusion, and Evidence?** No canonical source addresses these four types, unlike Evaluation and Learning (explicitly considered and rejected by the Historical Decision Record). *Competing interpretations*: (a) each reduces to an existing adopted type (Evidence → Knowledge Reference is the most textually plausible candidate, given Knowledge Reference's own "relies upon another Domain Object as knowledge" definition; Question/Interpretation/Conclusion are less obviously reducible); (b) each remains a disclosed, non-governing legacy concept indefinitely, parallel to Reasoning Act's own treatment; (c) a genuinely new architectural investigation is required. *Canonical support*: none, either way. *Why unresolved*: the original OE-002 investigation's own Historical Decision Record only names Evaluation and Learning Event as considered alternatives — it is silent on these four, and silence is not rejection. *Implementation consequence of deciding prematurely*: inventing a reduction here would violate this task's own explicit prohibition on introducing new domain semantics. *Smallest safe placeholder*: leave all four exactly as they are today, untouched by this plan (DO-IMP-011), disclosed as blocked. *Forcing function*: a dedicated, first-principles investigation structured identically to the six that produced OE-002 through OE-006.

**Q2 — Should `decision_type`/`confidence`/`source` be resolved as permissible internal content or removed?** Already flagged as open by both the Decision Implementation Design and this plan (DO-REC-008); not resolved here. *Smallest safe placeholder*: retain as non-constitutive compatibility columns (Section 19, DO-IMP-006). *Forcing function*: a dedicated future investigation into these three fields specifically, as already anticipated by Decision-Implementation-Design.md Section 39 Q2.

**Q3 — What Case-assignment policy applies to existing Decision/Outcome/Hypothesis/Observation rows that predate Case's existence?** No canonical source resolves this, because Case itself does not yet exist in any form the existing data could have referenced. *(Extended by this correction to explicitly include Observation's own existing rows, per DO-REC-026 — the question and its placeholder are identical in kind, not newly created by Observation's inclusion.)* *Competing interpretations*: (a) assign every pre-existing row to a single, synthetic "legacy" Case per owning user (using the existing `user_id`/`recorded_by`-equivalent field as the grouping key, since no other ownership signal exists); (b) require a manual, per-row assignment; (c) treat pre-existing rows as forever un-owned and exclude them from every Case-scoped query. *Why unresolved*: this is a data-policy decision, not an ontological one — Doctrine explicitly separates architecture (settled: every object needs exactly one Case) from this kind of implementation/migration-cost question. *Smallest safe placeholder*: do not backfill automatically; block DO-IMP-006/007/013's data-migration step specifically (not the schema-addition step) until an explicit backfill policy is chosen by the team. *Forcing function*: an explicit product/engineering decision, not an architectural one.

**Q4 — How should `subject` + `investment_case`'s existing content be combined into `commitment_content`?** *Competing interpretations*: concatenate with a separator; retain both as parts of one paragraph; treat one as primary and the other as supplementary. *Why unresolved*: OE-002 and the Decision Implementation Design specify only that `commitment_content` is free text — they do not, and could not, specify how two legacy free-text fields with independent product history should be merged; this is a data-transformation detail, not architecture. *Smallest safe placeholder*: do not run the transformation until this formatting choice is made explicitly and reviewed against a sample of real rows (Section 20).

**Q5 — Does a "Knowledge Reference Implementation Design" document exist under a different name?** Searched and confirmed absent under any name in `docs/atlas_domain_object_architecture/`. Not fabricated here. This plan derives Knowledge Reference's canonical shape directly from OE-002 §5.2 and the task brief's own restated canonical fields (Section 3.A of the task), which are fully consistent with OE-002's own text; no gap in derivability results from the missing standalone design document, but its absence is disclosed rather than silently assumed away.

## 24. Final Conclusion

The Atlas Core Domain Object architecture is settled; the repository is not yet conformant to it. Three of six adopted types (Knowledge Reference, Reasoning Trace, Judgment) have no implementation at all; the three that exist (Observation, Decision, Outcome) deviate from their own canonical requirements on ownership, cardinality, and target-restriction grounds; and three legacy aggregates (Hypothesis, Evaluation, Learning) persist independently despite a canonical document — the Historical Decision Record itself — already having named two of them by name and rejected their independent existence in favor of reduction to Judgment. Case, the ownership boundary (OE-002 §3.1, not a member of the six-type set), is separately and correctly implemented as of DO-IMP-001. Every discrepancy found traces to a specific governing source (Sections 13–14); none required reopening settled ontology, and none was resolved by implementation convenience — including this document's own earlier Case-for-Observation substitution, now corrected per docs/atlas_domain_object_architecture/Domain-Object-Type-Set-Discrepancy-Investigation.md. This plan is ready to execute, beginning with DO-IMP-001 (already committed), with the narrow, explicitly disclosed exceptions of DO-IMP-011 (blocked pending a dedicated future investigation into Question/Interpretation/Conclusion/Evidence) and the scoped data-policy questions (Section 21, Q3/Q4) that must be answered before their specific backfill steps proceed, including DO-IMP-013's own Observation backfill.
